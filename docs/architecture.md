# HJViewer 아키텍처

TeamViewer처럼 **모바일 앱(iOS/Android)에서 Windows PC 화면을 보고 제어**하는 원격 데스크톱 서비스입니다.
핵심 요구사항은 **어떤 방화벽·NAT 뒤에 있어도 연결되는 것**입니다.
오픈소스 [RustDesk](https://github.com/rustdesk/rustdesk)(클라이언트 1.5.0)와 [rustdesk-server](https://github.com/rustdesk/rustdesk-server)(1.1.17)를 포크하고, 방화벽 통과에 필요한 부분만 패치합니다.
1.6.0부터는 연세포탈 계정으로 로그인한 내 기기끼리 PC 비밀번호 없이 연결하고, 꺼진 PC를 같은 네트워크의 NAS로 켭니다(5절).

## 1. 방화벽을 넘는 원리

방화벽을 "뚫는" 것이 아니라 **양쪽 모두 밖으로만 연결**합니다. 거의 모든 네트워크가 허용하는 **HTTPS(TCP 443)**만 사용합니다.

```
 [Windows PC 에이전트]                [중계 서버 (클라우드)]                 [iOS / Android 앱]
        │  wss://서버/ws/id  (상시 연결)   ┌──────────────┐   wss://서버/ws/id        │
        ├──────────────────────────────▶ │ Caddy :443   │ ◀────────────────────────┤
        │                                │  ├─ /ws/id    → hbbs (ID·시그널링)       │
        │  wss://서버/ws/relay (필요 시)   │  ├─ /ws/relay → hbbr (중계)              │
        ├──────────────────────────────▶ │  └─ /api/*    → hjv-api (계정 경로만)    │
        │                                └──────────────┘                          │
        │                                                                          │
        └──────────── WebRTC P2P (UDP, 네트워크가 허용하면 직접 연결) ─────────────────┘
```

연결은 두 경로를 **동시에** 시도하고 먼저 성공하는 쪽을 씁니다(P2P 우선).

| 네트워크 상황 | 사용 경로 | 비고 |
|---|---|---|
| 가정·일반 NAT | WebRTC P2P (UDP 직접) | 지연 최소, 서버 대역폭 0 |
| UDP 차단, 443만 허용 (일반 회사망) | hbbr 중계 over `wss://…/ws/relay` | P2P 실패 후 약 2.5초 안에 전환 |
| 명시적 HTTP/SOCKS5 프록시만 허용 | 앱 네트워크 설정에 프록시 입력 → CONNECT 터널 위 wss | 패치로 지원 (upstream은 WS 연결이 프록시를 무시함). HTTPS 프록시는 미지원 |
| TLS 검사(복호화) 프록시 | 기기에 회사 루트 CA가 설치돼 있으면 통과 | 미설치 기기는 TLS 실패 → `hjv-probe`로 진단. `allow-insecure-tls-fallback` 옵션으로 허용할 수 있음(서버 인증은 약해지지만 세션은 종단 간 암호화로 보호). 계정 요청은 이 옵션과 상관없이 인증서를 확인한 연결로만 보냄(5-3) |
| 관리자가 원격제어 앱 범주·도메인을 명시적으로 차단 | 연결 안 됨 | 정책 차단은 우회하지 않습니다 (TeamViewer도 동일) |

서버에서 외부에 여는 포트는 **443(과 인증서 발급용 80)뿐**입니다. hbbs/hbbr의 포트(21115–21119)는 내부망에만 둡니다.

## 2. 구성 요소

| 구성 요소 | 역할 | 출처 |
|---|---|---|
| PC 에이전트 (Windows) | 화면 캡처·입력 주입. Windows 서비스로 실행되어 UAC·로그인 화면도 제어 | RustDesk 클라이언트 + `client/patches` |
| 모바일 앱 (Flutter) | 제어 측. 1.6.0부터 Android도 제어 전용입니다(6절) | 같은 코드베이스 |
| hbbs | 기기 ID·공개키 등록, 온라인 상태, 접속 요청·WebRTC 시그널링 전달 | rustdesk-server + `server/patches` |
| hbbr | P2P 실패 시 두 연결을 짝지어 암호화된 바이트를 그대로 전달 | rustdesk-server |
| Caddy | TLS 종료(Let's Encrypt 자동), 경로별 라우팅. 이미 웹 서버가 있는 서버는 nginx·Apache가 같은 일을 함 | `deploy/Caddyfile` |
| hjv-api (1.6.0) | 계정 API: 연세포탈 로그인, 내 기기 목록, 계정 키, PC 동기화와 신뢰 목록, 켜기 명령. 웹 서버 뒤 Unix 소켓에서만 받음 | `server/api` ([README](../server/api/README.md)) |
| hjv-relay (1.6.0) | PC와 같은 네트워크의 NAS에서 서버가 서명한 켜기 명령을 받아 매직 패킷을 보냄 | `relay/` ([PROTOCOL.md](../relay/PROTOCOL.md), [relay-dsm.md](relay-dsm.md)) |

**종단 간 암호화**: 세션 키는 두 기기가 직접 교환합니다. hbbs가 서명한 기기 공개키로 상대를 검증하고, WebRTC에서는 상대가 서명한 DTLS 지문으로 다시 검증합니다. 따라서 hbbs와 hbbr은 화면 내용을 볼 수 없습니다.
계정 요청(로그인, 내 기기 목록, PC 동기화)은 예외입니다. 서버까지의 TLS로만 보호되고, 앱은 인증서를 확인한 연결로만 보냅니다. 그래서 포탈 비밀번호는 서버 공개키로 따로 봉인하고, 모든 계정 요청에 그 기기의 계정 키 서명을 붙입니다(5-3).

## 3. 접속 순서

1. **PC 등록**: PC가 `wss://서버/ws/id`에 접속해 `RegisterPk`(ID, 공개키)를 보내고 연결을 유지합니다. hbbs는 10초마다 빈 프레임(하트비트)을 보내고 PC가 되돌려 보냅니다. 연결이 끊기면 즉시 오프라인 처리됩니다.
2. **접속 요청**: 앱이 `PunchHoleRequest`(대상 ID, WebRTC offer)를 보냅니다.
3. **전달**: hbbs가 PC의 상시 연결로 `PunchHole`(offer, 앱의 주소 키)을 보냅니다.
4. **응답**: PC가 새 wss 연결로 answer를 보내고, 중계 경로(hbbr)도 함께 준비합니다. 두 기기의 ICE 후보는 hbbs를 거쳐 오갑니다.
5. **경합**: 앱은 WebRTC P2P와 중계를 동시에 진행하고 P2P를 우선합니다. 2.5초 안에 P2P가 안 되면 중계를 씁니다.
6. **인증·세션**: 서로의 신원을 검증하고 세션 키를 교환한 뒤 PC 비밀번호, 수락 창, 또는 같은 계정 기기의 증명(5-6)으로 접속을 허용합니다.

## 4. upstream 대비 변경점

### 서버 (`server/patches`)
오픈소스 hbbs에는 방화벽 환경에 필요한 기능이 **빠져 있었습니다** (소스 분석 결과).

| 문제 | 영향 | 패치 |
|---|---|---|
| PC 등록을 UDP로만 받음 (TCP/WS의 `RegisterPk`에 `NOT_SUPPORT` 응답) | UDP가 막힌 PC는 **영원히 오프라인** | TCP/WS 등록 + 상시 연결 + 하트비트, 해당 연결로 요청 전달 |
| WebRTC offer/answer를 버리고 ICE 후보를 처리하지 않음 | 자체 서버로는 **P2P 불가**, 전부 중계 | offer·answer·`force_relay` 전달, ICE 후보 양방향 라우팅 |
| 응답 후 연결을 맵에서 제거 | answer 이후 ICE 후보 전달 불가 | 연결마다 송신 큐, 연결이 닫힐 때만 정리 |
| WS 클라이언트를 `IP:0`으로 식별 | 같은 회사(NAT) 사용자끼리 응답이 뒤섞임 | 프록시의 `X-Real-Port`로 구분 |
| WS로 온 `OnlineRequest` 무시 | 앱에서 기기 온라인 표시 안 됨 | WS 엔드포인트에서 응답 |
| hbbr이 동시에 도착한 중계 요청 두 개를 짝짓지 못함 (경쟁 상태) | 양쪽이 같은 순간 중계에 붙으면 세션이 30초 후 실패 | 찾기와 대기 등록을 한 락 안에서 처리 |

검증: 통합 테스트 `tests/tcp_signaling.rs`(2개)와 `tests/relay_pairing.rs`(동시 도착 100쌍)를 추가했습니다. 모두 패치 전 실패하고 패치 후 통과합니다.
마지막 hbbr 버그는 아래의 방화벽 E2E 검증에서 실제 클라이언트로 발견했습니다.

1.6.0의 패치 0004는 계정 기능을 위한 것입니다.
- 루프백 콘솔(127.0.0.1:21115)에 `hjv-pk <id>` 명령을 더합니다. 답은 한 줄 `HJVPK1 <id> <서명된 IdPk> <마지막 등록 뒤 초>`이고, 서명된 값은 hbbs가 컨트롤러에게 주는 것과 같은 바이트(hbbs 개인키로 서명한 ID와 공개키)입니다. hjv-api는 앱과 같은 hbbs 공개키로 이 서명을 확인한 뒤에만 그 키를 믿습니다. 콘솔에는 인증이 없으므로, 그 포트를 다른 프로그램이 차지해도 남의 PC를 계정에 묶을 수 없게 하려는 것입니다.
- 중계 요청(`RequestRelay`)을 상대 PC로 넘기기 전에 `token`, `control_permissions`, `controlled_context`를 지웁니다. 컨트롤러가 PC 주인이 꺼 둔 권한을 켜거나 토큰을 남의 PC로 보내지 못합니다.
- 시험: `tests/hjv_pk.rs`(서명, 모르는 ID, 긴 입력, hbbs 재시작 뒤).

알려진 한계 (upstream과 동일):
- **IP별 등록 제한**: 공인 IP 하나당 분당 약 30회, 하루 300개 ID까지 등록할 수 있습니다. PC 수백 대가 공인 IP 하나를 공유하는 대형 사무실에서는 서버 재시작 직후 일부 PC가 최대 1분 늦게 등록되고, 300대를 넘으면 새 ID 등록이 거부됩니다. 기업 고객을 받으려면 이 제한을 설정값으로 바꿔야 합니다.
- **서버 단일 인스턴스**: hbbs는 1대로 운영합니다(SQLite). 확장은 중계(hbbr)를 늘리는 방식입니다.

### 클라이언트 (`client/patches`)
- 빌드할 때 `HJV_SERVER`(도메인)와 `HJV_SERVER_KEY`(hbbs 공개키)를 넣으면 서버 주소·키가 고정되고, 사용자 설정 화면에서 숨겨집니다.
- **WebSocket을 강제**합니다. 신호와 중계는 항상 443을 쓰고, WebRTC는 기본으로 켭니다(upstream은 공식 서버에서만 켭니다).
- upstream 업데이트 확인과 자동 업데이트를 끕니다.
- 앱 이름은 `HJViewer`, Android/iOS 식별자는 `kr.ac.yonsei.hjviewer`입니다. 아이콘은 HJ 모노그램을 띄운 모니터입니다. 원본 SVG는 `client/icons`에 있고, `scripts/make-icons.sh`가 플랫폼별 파일을 모두 `client/overlay`에 다시 만듭니다(같은 원본이면 같은 파일). Windows 실행 파일 정보와 정보(About) 화면의 링크는 이 저장소를 가리킵니다.
- (hbb_common) **WebSocket 연결이 프록시 설정을 따릅니다.** upstream은 WS 연결에서 프록시를 무시해서(`to-do: websocket proxy`) 프록시로만 나갈 수 있는 회사망에서는 연결되지 않았습니다. HTTP CONNECT와 SOCKS5 터널 위에서 TLS와 WebSocket 핸드셰이크를 하도록 고쳤습니다. 테스트는 패치 전 실패, 패치 후 통과합니다.
- 1.6.0(패치 0030부터): 계정 기능(5절). 새 로직은 HJViewer 전용 파일(`src/hjviewer_account/`, `src/server/connection/hjv_account.rs`, `src/client/hjv_account.rs`)에 두고, 공용 파일에는 한 줄짜리 연결 코드만 넣습니다. 빌드 변수 `HJV_LOGIN_SEAL_PUBKEY`와 `HJV_TRUST_PUBKEYS`가 없으면 1.5.1과 똑같이 동작합니다(5-9). 앱은 Rust 1.75로 빌드됩니다.

검증: 전체 앱 빌드는 CI에서만 할 수 있습니다. 대신 설정 모듈을 실제 hbb_common/base 크레이트와 함께 별도로 실행해서 확인했습니다(`wss://<서버>/ws/id`와 `/ws/relay` 변환, 서버 고정, WebRTC 기본값). hbb_common 단위 테스트 101개도 모두 통과합니다.

### 방화벽 E2E 검증 ([e2e.md](e2e.md))

실제 HJViewer 클라이언트(Linux 빌드, 같은 Rust 코어) 두 대를 네트워크 네임스페이스에 넣고, 서버로 가는 TCP 443만 허용하는 방화벽을 걸어 검증했습니다.
등록, 비밀번호 로그인, 데이터 전달, **원격 화면 수신**이 모두 동작했습니다. 443만 열려 있으면 중계(wss)로, 피어 간 UDP가 열려 있으면 WebRTC P2P로 연결됩니다.

## 5. 계정과 비밀번호 없는 연결 (1.6.0)

연세포탈 계정으로 로그인한 기기끼리는 PC의 ID나 비밀번호 없이 연결합니다. 그 밖의 연결(다른 사람의 PC, 로그인하지 않은 앱, 1.5.x)은 지금처럼 ID와 PC 비밀번호로 합니다. 서버 쪽 형식은 [server/api/README.md](../server/api/README.md), 중계기 규약은 [relay/PROTOCOL.md](../relay/PROTOCOL.md)가 정합니다. 서버 설치와 운영은 [server-runbook.md](server-runbook.md) 7절, 개인정보는 [privacy.md](privacy.md)에 있습니다.

### 5-1. 구성

```
앱(아이폰·안드로이드·Windows) ──HTTPS 443──▶ nginx (rd.example.com, 다른 사이트와 함께 쓸 수 있음)
  │  계정 키(기기마다, 로그인 때 만듦)          ├ /ws/id, /ws/relay → hbbs·hbbr (그대로)
  │  모든 계정 요청에 X-HJV-Proof              ├ 계정 경로 → hjv-api (Unix 소켓, systemd가 쥠)
  │                                            │     ├ HTTPS → 연세 SSO
  │                                            │     ├ 127.0.0.1:21115 → hbbs 콘솔 hjv-pk (패치 0004)
  │                                            │     └ 목록 키·명령 키·봉인 키 (systemd 암호화 자격 증명)
  │                                            └ 그 밖의 /api/ → nginx가 404 JSON (그대로)
  │
  └─(연결: hbbs·hbbr·WebRTC, 종단 간 암호화)─▶ Windows PC 서비스(--server, SYSTEM, 로그온 전에도)
        Hash{salt, challenge, hjv_nonce}  ◀──      ├ HKLM\SOFTWARE\HJViewer\Account (허용 표시)
        LoginRequest{…, hjv_key_proof}  ──▶        ├ 신뢰 목록(서비스 설정 폴더)
                                                   └ 동기화: 기기 키 서명 ──HTTPS──▶ /api/hjv/pc/sync
                                                        ◀── 목록 키로 서명된 신뢰 목록 (+ 켜기 정보 보고)
NAS의 hjv-relay ──HTTPS long-poll, 중계기 키 서명──▶ /api/hjv/relay/poll ◀── 명령 키로 서명된 켜기 명령
NAS ──매직 패킷(자기 랜카드의 브로드캐스트, UDP 9·7)──▶ 꺼진 내 PC
```

- **연결 경로에는 hjv-api가 없습니다.** hjv-api가 멈춰도 원격 세션과 비밀번호 연결은 영향을 받지 않고, 비밀번호 없는 연결은 PC가 받아 둔 목록으로 최대 24시간 계속됩니다. 그래서 hjv-api의 장애는 하루 동안 드러나지 않다가 한꺼번에 나타날 수 있으므로 감시를 둡니다([server-runbook.md](server-runbook.md) 7-14).
- 하트비트, 기기 정보, 접속 기록 경로는 nginx가 본문을 읽지 않고 404로 답합니다. 1.5.x PC와 로그인하지 않은 PC는 hjv-api에 아무것도 보내지 않습니다.

### 5-2. 키

| 키 | 종류 | 만드는 곳 / 보관 | 쓰임 |
|---|---|---|---|
| 기기 키(있던 것) | Ed25519 | 앱이 만듦. `HJViewer.toml`. Windows에서는 그 PC의 모든 Windows 사용자가 씀 | 핸드셰이크의 SignedId, 로그인의 기기 서명, PC 동기화 서명 |
| 계정 키 | Ed25519 | 비밀번호 로그인마다 새로. 아이폰 Keychain(이 기기 전용, 잠금 해제 때만), 안드로이드 앱 데이터(클라우드 백업·기기 이전에서 뺌), Windows `%LOCALAPPDATA%\HJViewer-account\account-key.bin`(DPAPI 사용자 범위, 로밍 안 함) | 모든 계정 요청의 서명, 연결 증명. 같은 기기의 옛 키는 서버가 폐기 |
| 봉인 키 | X25519 | 사용자가 오프라인으로 만들어 서버의 암호화 자격 증명에 넣음. 공개키는 앱 빌드 변수 `HJV_LOGIN_SEAL_PUBKEY` | 로그인 비밀번호 봉인 열기 |
| 기록 키 | HMAC | 서버에서 | 기록과 저널의 계정·기기 꼬리표 |
| 목록 키 1·2 | Ed25519 | 1번은 서버에서, 2번은 오프라인. 공개키 둘을 앱 빌드 변수 `HJV_TRUST_PUBKEYS`로 고정 | 신뢰 목록 서명. 2번으로 바꾸면 PC가 1번 목록을 다시 받지 않음 |
| 명령 키 1·2 | Ed25519 | 목록 키와 같음. 공개키는 hjv-relay 빌드 변수 `HJV_COMMAND_PUBKEY`에만 | 켜기 명령 서명 |
| 중계기 키 | Ed25519 | hjv-relay가 NAS에서 처음 실행할 때 만듦(root 전용 폴더) | 중계기 요청 서명 |
| hbbs 서버 키(있던 것) | Ed25519 | hbbs | 기기의 (ID, 공개키) 서명 |

서명하는 바이트는 모두 용도별 문자열로 시작합니다: `hjv-login-v1`(기기 로그인), `hjv-ckey-v1`(계정 키 소유 증명), `hjv-req-v1`(계정 요청), `hjv-conn-v1`(연결 증명), `hjv-pc-v1`(PC 동기화), `hjv-trust-v1`(목록), `hjv-relay-v1`(중계기 요청), `hjv-wake-v1`(켜기 명령). `hjv-`로 시작하는 바이트는 protobuf로 해석될 수 없어서, 같은 기기 키가 서명하는 `IdPk`와 섞이지 않습니다. 키 오프라인 사본은 에이전트가 돌지 않는 곳에서 이동식 매체로 만들고, 프로젝트 폴더나 여러 사람이 쓰는 공유 폴더에 두지 않습니다.

### 5-3. 로그인과 계정 요청

- **봉인**: 앱은 비밀번호를 서버 봉인 공개키로 봉인합니다(`hjv-sealed-v1.<kid>.<봉인>`, libsodium sealed box). 봉인 안에는 비밀번호, 시각, 일회용 값, 기기 ID와 함께 이 로그인에서 새로 만든 **계정 공개키**(`ck`)와 그 키의 소유 증명(`cp`)이 들어 있습니다. TLS를 가로채는 장비(기기가 믿는 회사·MDM 루트)도 비밀번호를 보지 못하고 계정 키를 바꿔치기하지 못합니다.
- **SSO**: hjv-api는 명단에 있는 ID만 연세 SSO에 확인합니다(password grant). ID에 따라 달라지는 실패는 모두 같은 답과 같은 최소 지연으로 돌려주어 명단이 드러나지 않습니다. SSO가 이 서버를 거부하거나 연달아 실패하면 잠시 SSO 호출을 멈추고, 그동안 모든 로그인에 같은 503("연세 인증 서버에 지금 연결할 수 없습니다")을 줍니다.
- **기기 서명**: 설치된 Windows PC의 로그인에는 기기 키 서명이 붙습니다. hjv-api는 hbbs가 서명한 그 ID의 공개키(`hjv-pk`, 패치 0004)로 확인한 뒤에만 그 PC를 계정에 묶습니다. 이미 다른 계정에 묶인 PC는 거절합니다.
- **모든 계정 요청에 서명**: `X-HJV-Proof: v1.<t>.<n>.<sig>`. 계정 키로 `"hjv-req-v1" NUL 메서드 NUL 경로?쿼리 NUL t NUL n NUL SHA-256(본문) NUL SHA-256(토큰)`에 서명합니다. 서버는 토큰의 키로 서명을 확인하고, 시각 ±600초, 바꾸는 요청은 일회용 값 20분 재사용 거부를 봅니다. 앱의 TLS 재시도처럼 같은 요청을 바이트 그대로 짧은 시간 안에 다시 보낸 것은 재사용으로 보지 않고 첫 답을 다시 줍니다(로그인의 30초 재시도와 같은 방식). 그래서 토큰만 훔쳐서는(백업, 파일 공유, 가로채기 장비) 아무것도 못 합니다. 키를 쓸 수 없으면(잠긴 아이폰) 앱은 요청을 보내지 않고, 로그아웃하지도 않습니다.
- **시계**: 서명은 맞는데 시각만 창 밖이면 서버는 401·400 대신 409 `clock`과 서버 시각을 줍니다. 앱은 401·400에서만 스스로 로그아웃하므로 시계가 틀린 기기가 조용히 로그아웃되지 않고, 서버와의 차이를 배워 다음 요청부터 맞춰 보냅니다.
- **엄격한 TLS**: 계정 요청은 인증서 무시 재시도(`allow-insecure-tls-fallback`)를 쓰지 않습니다.
- **남에게 보내는 이름**: 로그인해도 다른 사람의 PC에 성명이나 포탈 ID를 보내지 않습니다. 1.5.1처럼 Windows 사용자 이름(휴대폰은 기기 이름)을 보냅니다.

### 5-4. PC를 계정에 묶기

- **로그인하면 켜짐**: 설치된 Windows PC에서 HJViewer에 로그인하면 hjv-api가 그 PC를 계정에 묶고(무작위 128비트 묶음 ID), 로그인 응답에 묶음 ID와 서버 시각 `login_at`을 줍니다. 앱은 기존 IPC로 서비스에 묶기 요청을 넣습니다. 서비스(SYSTEM)는 서버의 서명된 목록이 같은 묶음을 확인하고 그 로그인이 10분 안이었을 때만 `HKLM\SOFTWARE\HJViewer\Account`에 허용 표시를 씁니다. UAC나 따로 누르는 허용 단계는 없습니다. 그래서 IPC로 아무 값이나 넣어도, 예전 묶기 요청을 다시 넣어도 켜지지 않습니다.
- **끄기**: 그 PC의 Windows 사용자는 누구나 설정 → 계정에서 [끄기]를 누를 수 있습니다. 상태는 HKLM에 두므로 다른 사용자가 설정을 다시 써도 되돌아가지 않고, 다시 켜려면 묶인 계정으로 그 PC에서 다시 로그인해야 합니다.
- **로그아웃**: 그 PC를 묶은 사용자가 로그아웃하면 앱은 요청을 보내기 **전에** 서비스에 풀기 요청을 넣고, 서비스는 1초 안에 허용 표시를 지웁니다. 서버에 닿지 못해도 그 PC에서는 바로 꺼집니다. 401·400으로 앱이 스스로 로그아웃하는 경우에는 아무것도 풀지 않습니다.
- **재부팅, 업데이트, 제거**: 서비스는 Windows 로그온 전에도 HKLM과 받아 둔 목록으로 동작합니다. 다시 설치하거나 업데이트해도 허용 표시는 남고, 제어판의 제거만 지웁니다.
- **풀기는 서버의 한 곳**: 묶음을 푸는 모든 길(그 PC의 로그아웃, [이 PC 빼기], 다른 기기에서 빼기, 관리자 `binding revoke`, 계정 삭제, 180일 정리)은 `db::release_binding` 하나를 지나고, 묶음 ID를 180일 동안 무덤으로 남깁니다. 그 PC는 다음 동기화에서 서명된 `revoked`를 받아 허용 표시를 지웁니다.

### 5-5. 신뢰 목록과 동기화

- 묶인 PC의 서비스는 보통 2분마다 기기 키로 서명한 요청(`hjv-pc-v1`)을 `POST /api/hjv/pc/sync`로 보냅니다. 서버가 주는 간격(`HJV_API_TRUST_REFRESH`, 운영 120초)을 PC는 빌드 상수 5~300초로 자르므로, 서버에 닿는 PC는 늦어도 5분 안에 되돌리기를 받습니다. 묶이지 않은 PC는 보내지 않습니다.
- 답의 **신뢰 목록**은 그 계정의 폐기되지 않은 계정 공개키와 기기 ID·이름, 허용된 연결 종류, 가린 주인 이름을 담고, 목록 키로 서명됩니다(`hjv-trust-v1`). PC는 받은 바이트로 서명을 먼저 확인하고, 자기 ID·자기 키·자기 묶음·**이번 요청의 일회용 값**(`req`)에 대한 답인지, 고정한 키 번호가 바닥 이상인지, 수명이 72시간 이하인지 봅니다. 옛 목록을 다시 보내거나 되돌리는 공격이 통하지 않습니다.
- 수명은 **받은 시각부터** 셉니다(운영 24시간, `HJV_API_TRUST_TTL`, 빌드 상한 72시간). PC 시계와 서버 시계의 차이에 기대지 않고, 시계가 크게 틀리면 안전한 쪽(다시 받기, 일찍 만료)으로 실패합니다.
- 허용을 지우는 것은 **서명된** `revoked`뿐입니다. 서명 없는 답(`listed`, `unbound`)으로는 아무것도 지우지 않으므로, TLS를 가로챈 쪽이 거짓 답으로 허용을 지울 수 없습니다.
- 서버는 같은 PC가 10초 안에 다시 와도 429를 주지 않고, 그 사이 변경 번호가 그대로면 마지막 목록에 새 `req`만 넣어 다시 서명합니다. 기기 키를 가진 로컬 사용자가 요청을 쏟아부어 되돌리기를 늦추지 못합니다.
- **키 바뀜**: PC가 설정을 잃어 기기 키가 바뀌면 동기화 서명이 맞지 않습니다. 서버는 그 자리에서 hbbs에 묻고(한 PC 1분에 한 번), 진짜 hbbs가 새 키를 가졌으면 그 PC를 `needs-relogin`으로 표시합니다. 컨트롤러는 목록을 새로 받은 뒤 그 PC에 비밀번호 창을 띄우고, 그 PC에서 다시 로그인하면 비밀번호 없는 연결이 돌아옵니다.
- PC는 동기화에 앱 버전, 끄기 여부, 키·날짜별 받아들인 횟수(서버는 줄어드는 보고를 받지 않고 큰 값으로 합침), 거절 이유별 개수, 켜기 정보를 싣습니다. 서버는 누가 언제 어느 PC에 연결했는지 받지 않습니다.

### 5-6. 연결 증명

연결할 때는 서버를 부르지 않습니다.

1. 기능이 있는 PC(계정 빌드, 서비스 프로세스, 설치형)는 묶였는지와 상관없이 `Hash`에 32바이트 일회용 값(`hjv_nonce`, 필드 번호 1001)을 넣습니다. 값이 비면 `Hash`의 바이트는 1.5.1과 같습니다.
2. 컨트롤러는 다음을 모두 만족할 때만 `LoginRequest.hjv_key_proof`(필드 1001)에 증명을 넣습니다: 계정 빌드이고 로그인했으며 계정 키를 쓸 수 있음, 일회용 값이 있음, 세션이 암호화됨, 다른 서버(`id@서버`)가 아님, 연결 종류가 원격 화면·파일 전송·카메라(터미널은 서버 설정으로만 열 수 있고, 포트 포워딩·RDP는 늘 비밀번호), 대상이 **내 기기 목록**에 있고 `needs-relogin`이 아님.
3. **키 연속성**: 내 목록에 있고 `needs-relogin`이 아닌 PC에 연결할 때, 이 채널에서 확인한 PC 키가 목록에 묶인 그 PC의 키와 다르면 증명도 기억한 비밀번호도 보내지 않고 보안 경고 창(닫기만 있음)을 띄워 연결을 끝냅니다. hbbs 키를 훔쳐 중계를 가로채는 쪽에게 비밀번호 응답이 가지 않게 하려는 것입니다. 경고 창에는 목록에서 빼는 단추를 두지 않습니다. 가로채는 쪽이 경고를 일부러 띄워 사용자가 PC를 빼게 만들면, 다음 연결부터 이 확인이 없어지기 때문입니다.
4. 증명은 계정 키로 `"hjv-conn-v1" ‖ PC ID ‖ 확인한 PC 키 ‖ 일회용 값 ‖ 내 ID ‖ 연결 종류 ‖ 계정 공개키`에 한 서명입니다. 다른 연결·다른 PC로 다시 보내거나, 가짜 PC가 받아 진짜 PC로 넘기거나, 종류를 바꿔치기하면 모두 실패합니다. 기억한 비밀번호가 있으면 함께 보내므로, 증명이 거절돼도 왕복이 늘지 않습니다.
5. PC는 영구 비밀번호가 받아들여지는 설정인지("임시 비밀번호만"이면 거절), 비밀번호를 틀려 막힌 주소가 아닌지, 세션이 암호화됐는지, 허용 표시가 있고 꺼 두지 않았는지를 보고, **서명을 먼저** 확인한 뒤 받아 둔 목록에서 키·연결 종류·기기 ID를 봅니다. 목록이 없거나 지났을 때, 목록에 없는 키가 목록보다 나중에 등록된 키일 때(방금 로그인한 새 기기), 관리자가 연결마다 확인(`strict`)을 켰을 때는 한 번만 즉시 동기화합니다(최대 1.5초, 한 PC에 동시에 하나, 끝난 뒤 10초 안에는 다시 하지 않음). 서명이 틀린 증명은 동기화를 일으키지 않습니다.
6. 통과하면 **올바른 영구 비밀번호와 똑같이** 처리합니다. PC의 2FA, 클릭 승인 모드, 화이트리스트, 터미널의 Windows 관리자 로그인은 그대로입니다. 연결 창에는 "<기기 이름> · 같은 계정(<가린 주인>)"이 목록의 값으로 뜹니다.
7. 거절하면 비밀번호가 같이 오지 않은 경우 `"Empty Password"`를 보내고, 1.6.0 컨트롤러는 "비밀번호 없이 연결하지 못했습니다"가 붙은 비밀번호 창을 띄웁니다. 새 오류 문자열이 없으므로 1.5.x 컨트롤러도 지금처럼 동작합니다. 거절은 실패 횟수에 세지 않습니다.

| 컨트롤러 \ PC | 1.5.x·upstream | 1.6.0, 묶이지 않음·꺼 둠·로그아웃함 | 1.6.0, 켜짐 |
|---|---|---|---|
| 1.5.x·upstream | 지금과 같음 | 지금과 같음(일회용 값은 모르는 필드로 무시) | 지금과 같음 |
| 1.6.0, 로그인 안 함 / 남의 계정 | 지금과 같음 | 지금과 같음 | 지금과 같음(증명을 보내지 않음) |
| 1.6.0, 같은 계정 | 지금과 같음(일회용 값 없음) | 증명을 보내지 않거나 거절 → 거절 문구가 붙은 비밀번호 창 | **비밀번호 없이** |

### 5-7. 보장하는 것과 하지 않는 것

- PC가 비밀번호 없이 열리는 것은 다음을 모두 만족할 때뿐입니다: 그 계정에 지금 로그인된 기기의 키이고, 그 PC에서 그 계정으로 로그인해 묶은 뒤 로그아웃·끄기·빼기를 하지 않았고, 암호화된 세션이며, 서버가 그 기기와 PC를 아직 허용하고(서버에 닿지 못하면 최대 24시간 전의 상태), 허용된 연결 종류일 때입니다.
- 목록은 PC를 둘러싼 울타리가 아닙니다. ID와 PC 비밀번호를 아는 사람은 지금처럼 들어옵니다. PC마다 긴 영구 비밀번호를 정해 두는 것을 권합니다. 비밀번호 없는 연결이 안 되는 때(서버 장애가 하루 넘게 이어짐, 끄기, 로그아웃, 키 바뀜)에 쓰는 길입니다.
- 받아들인 남는 위험(결정 U1·U2·U4·U5):
  - 그 계정의 포탈 비밀번호(같은 서버의 WordPress 로그인 플러그인도 이 비밀번호를 평문으로 받음)나 로그인된 내 기기(잠금이 풀린 휴대폰, 내 Windows 계정으로 도는 프로그램)를 가진 사람은 그 계정에 묶인 모든 PC를 PC 비밀번호 없이 엽니다. 알아채는 방법은 다른 내 기기의 '새 기기 로그인' 알림과 '로그인한 기기' 목록입니다. TOTP, 짝 맺기, 연결마다 Face ID는 두지 않습니다.
  - 되돌리기(로그아웃, 빼기, 관리자 명령, 끄기 스위치)는 PC가 서버에 닿으면 보통 2분, 늦어도 5분 안에, 닿지 못하면 최대 24시간 뒤에 효과가 납니다.
  - 공용 PC: 그 PC의 어느 Windows 사용자든 HJViewer에 로그인하면 묶이지 않은 그 PC를 자기 계정에 엽니다. 다른 사용자는 [끄기]를 누를 수 있고, 가린 주인 이름과 주인 기기의 이름이 든 목록을 볼 수 있습니다.
  - hjv-api 서버가 장악되면(목록 키와 DB) 묶인 모든 PC에 자기 키를 넣은 목록을 줄 수 있습니다. 쫓아낸 뒤 목록 키를 2번으로 바꾸면 서버에 닿는 PC는 늦어도 5분 안에 회복하고, 닿지 못하는 PC는 그 목록을 최대 72시간 씁니다. 그 서버에서 root로 일하는 운영 에이전트는 결정 O1에 따라 "하지 말 것" 규칙으로만 막습니다([server-runbook.md](server-runbook.md) 7-0).
  - 증명은 세션 키 교환이 아니라 확인한 PC 키에 묶입니다. 그 PC의 기기 키와 hbbs 등록 가로채기를 함께 가진 쪽은 증명을 넘길 수 있습니다(비밀번호도 지금 같은 위험).
- 개발 PC처럼 AI 에이전트가 같은 Windows 사용자로 도는 PC는, 다른 내 기기의 '로그인한 기기'에서 그 PC의 계정 키만 로그아웃시켜 두면 들어오는 비밀번호 없는 연결만 받습니다.

### 5-8. 원격 켜기 (2단계)

- 서버나 휴대폰이 보낸 매직 패킷은 꺼진 PC의 네트워크에 닿지 못하므로, 같은 네트워크의 늘 켜진 NAS에서 **hjv-relay**가 대신 보냅니다. NAS에서 여는 포트는 없고, hjv-relay가 HTTPS로 서버에 long-poll(최대 20초)을 걸어 명령을 기다립니다.
- 중계기는 처음 실행할 때 자기 키를 만들고 등록 코드를 보입니다. 관리자가 그 PC 주인의 확인을 받은 뒤 `hjv-api admin relay approve <코드> --owner-of <PC ID>`로 승인합니다. 중계기는 아무 PC의 신뢰 목록에도 없으므로 PC에 연결할 권한이 없고, 켜기 명령만 받습니다.
- 켜기 명령은 TLS와 따로 명령 키로 서명되고(`hjv-wake-v1`, 60초 만료, 받는 중계기 지정), 명령 공개키는 hjv-relay 빌드에만 고정됩니다. 중계기는 자기 랜카드의 브로드캐스트로만, UDP 9·7로만, 3번씩 보내고, MAC은 4개, 분당 명령 10개·패킷 120개까지만 받습니다.
- 묶인 PC는 동기화에 유선 랜카드와 전원 정보를 싣고, 서버가 그 정보로 같은 네트워크의 중계기를 고르고 준비 상태를 판단합니다. 앱에는 MAC을 보내지 않습니다. 켜짐은 hbbs의 `hjv-pk` 등록 나이와 PC의 첫 동기화로 확인하고, 깨어난 PC는 연결이 없어도 10분 동안 다시 잠들지 않습니다.
- 앱에서는 꺼진 내 PC 카드의 "켜기"나 카드를 누를 때의 권유로 켭니다. 설치는 [relay-dsm.md](relay-dsm.md)에 있습니다.

### 5-9. 기능이 꺼진 빌드

계정 빌드는 `HJV_SERVER`, `HJV_LOGIN_SEAL_PUBKEY`, `HJV_TRUST_PUBKEYS`가 모두 있는 빌드입니다. 하나라도 없으면 로그인도 비밀번호 없는 연결도 없는 1.5.1 동작입니다. 일회용 값은 비고, 증명은 만들지 않고, 동기화 작업은 시작하지 않으므로 선 위의 바이트가 1.5.1과 같습니다. 빌드 변수를 넣는 방법은 [ci.md](ci.md)의 "계정 기능의 공개키"에 있습니다.

## 6. 플랫폼 제약

- **iOS**: 다른 앱에 입력을 주입하는 API가 없어서 **iPhone은 원격 제어할 수 없습니다**. 제어 측 전용입니다. 화면 공유(보기)는 ReplayKit 방송으로만 가능하며 추후 과제입니다.
- **Android**: 1.6.0부터 모든 Android 빌드(사이드로드 APK와 Google Play 빌드 모두)는 **제어 측 전용**입니다(Google Play 작업의 결정 D1). 피제어에 쓰던 접근성 서비스, 화면·소리 캡처 서비스, 오버레이, 부팅 수신기를 빼므로 Android 기기는 원격으로 볼 수 없습니다. 1.5.x까지의 APK는 피제어도 됐습니다(MediaProjection + 접근성 서비스).
- **보이스피싱 악용**: 원격제어 앱은 사기에 악용되는 대표 수단입니다. 국내 금융 앱은 원격제어 앱 실행을 탐지합니다. 스토어 심사와 사용자 신뢰를 위해 접속 수락 UI, 세션 중 표시, 접속 이력 같은 기능을 제품 요구사항에 넣어야 합니다.

## 7. 라이선스·상표

- RustDesk 클라이언트와 서버는 모두 **AGPL-3.0**입니다. 수정한 앱을 배포하거나 수정한 서버를 네트워크로 서비스하면, 해당 사용자에게 **수정본 소스를 제공할 의무**가 있습니다. 저장소가 비공개여도 이 의무는 남습니다.
- hjv-api(`server/api`)와 hjv-relay(`relay/`)는 이 저장소에서 새로 쓴 프로그램이고, 저장소의 다른 부분처럼 AGPL-3.0-only입니다. hjv-api는 `GET /api/hjv/source`로 라이선스와 소스 위치를 알립니다(웹 서버의 `/`는 함께 쓰는 사이트가 쓰므로).
- "RustDesk" 이름과 로고는 쓸 수 없습니다. 앱 이름, 아이콘, Windows 실행 파일 정보, 정보 화면 링크를 HJViewer로 바꿨습니다. Windows 실행 파일은 `HJViewer.exe`이고, Windows의 URL 스킴은 그에 따라 `hjviewer://`입니다. 모바일의 URL 스킴(`rustdesk://`)은 아직 upstream 그대로입니다.
- 저장소 루트의 `LICENSE`(AGPL-3.0 전문)와 `NOTICE`(upstream 저작권자와 변경 범위)가 고지이고, 내려받는 모든 빌드 결과물에도 라이선스·소스 위치·서드파티 고지 파일이 함께 들어갑니다. TestFlight 빌드에는 앱 정보 화면의 소스 링크만 있습니다.
- RustDesk의 프린터 드라이버 어댑터 DLL은 소스가 공개되지 않아 AGPL 배포 조건을 지킬 수 없으므로 Windows 빌드에서 뺐습니다(원격 인쇄 꺼짐).
