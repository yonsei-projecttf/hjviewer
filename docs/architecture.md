# HJViewer 아키텍처

TeamViewer처럼 **모바일 앱(iOS/Android)에서 Windows PC 화면을 보고 제어**하는 원격 데스크톱 서비스입니다.
핵심 요구사항은 **어떤 방화벽·NAT 뒤에 있어도 연결되는 것**입니다.
오픈소스 [RustDesk](https://github.com/rustdesk/rustdesk)(클라이언트 1.5.0)와 [rustdesk-server](https://github.com/rustdesk/rustdesk-server)(1.1.17)를 포크하고, 방화벽 통과에 필요한 부분만 패치합니다.
1.6.0부터는 연세포탈 계정으로 로그인한 내 기기끼리 PC 비밀번호 없이 연결하고, 꺼진 PC를 같은 네트워크의 NAS로 켭니다(5절).
같은 판부터 운영자가 서명한 버전 정책으로 앱의 최소 버전을 정하고, 새 버전을 서버에서 나눠 줍니다(8절).
1.8.0부터는 연세대학교 교직원용입니다. 서버는 로그인한 앱과 계정에 묶인 PC, 그리고 운영자가 정한 이용 비밀번호를 넣은 쪽의 연결과 등록만 받습니다(9절).
1.9.0부터는 로그인한 교직원이 만든 지원 코드와 지원 링크로 외부인의 PC 하나를 돕고, 그 PC의 연결 창은 서명으로 확인한 교직원 표시를 보입니다(5-10, 9절).

## 1. 방화벽을 넘는 원리

방화벽을 "뚫는" 것이 아니라 **양쪽 모두 밖으로만 연결**합니다. 거의 모든 네트워크가 허용하는 **HTTPS(TCP 443)**만 사용합니다.

```
 [Windows PC 에이전트]                [중계 서버 (클라우드)]                 [iOS / Android 앱]
        │  wss://서버/ws/id  (상시 연결)   ┌──────────────┐   wss://서버/ws/id        │
        ├──────────────────────────────▶ │ Caddy :443   │ ◀────────────────────────┤
        │                                │  ├─ /ws/id    → hbbs (ID·시그널링)       │
        │  wss://서버/ws/relay (필요 시)   │  ├─ /ws/relay → hbbr (중계)              │
        ├──────────────────────────────▶ │  └─ /api/*    → hjv-api (계정 경로만)    │
        │                                └──────────────┘                          │
        │                                                                          │
        └──────────── WebRTC P2P (UDP, 네트워크가 허용하면 직접 연결) ─────────────────┘
```

연결은 두 경로를 **동시에** 시도하고 먼저 성공하는 쪽을 씁니다(P2P 우선).

| 네트워크 상황 | 사용 경로 | 비고 |
|---|---|---|
| 가정·일반 NAT | WebRTC P2P (UDP 직접) | 지연 최소, 서버 대역폭 0 |
| UDP 차단, 443만 허용 (일반 회사망) | hbbr 중계 over `wss://…/ws/relay` | P2P 실패 후 약 2.5초 안에 전환 |
| 명시적 HTTP/SOCKS5 프록시만 허용 | 앱 네트워크 설정에 프록시 입력 → CONNECT 터널 위 wss | 패치로 지원 (upstream은 WS 연결이 프록시를 무시함). HTTPS 프록시는 미지원 |
| TLS 검사(복호화) 프록시 | 기기에 회사 루트 CA가 설치돼 있으면 통과 | 미설치 기기는 TLS 실패 → `hjv-probe`로 진단. `allow-insecure-tls-fallback` 옵션으로 허용할 수 있음(서버 인증은 약해지지만 세션은 종단 간 암호화로 보호). 계정 요청, 버전 정책, 설치 파일은 이 옵션과 상관없이 인증서를 확인한 연결로만 받음(5-3, 8-2) |
| 관리자가 원격제어 앱 범주·도메인을 명시적으로 차단 | 연결 안 됨 | 정책 차단은 우회하지 않습니다 (TeamViewer도 동일) |

서버에서 외부에 여는 포트는 **443(과 인증서 발급용 80)뿐**입니다. hbbs/hbbr의 포트(21115–21119)는 내부망에만 둡니다.

## 2. 구성 요소

| 구성 요소 | 역할 | 출처 |
|---|---|---|
| PC 에이전트 (Windows) | 화면 캡처·입력 주입. Windows 서비스로 실행되어 UAC·로그인 화면도 제어 | RustDesk 클라이언트 + `client/patches` |
| 모바일 앱 (Flutter) | 제어 측. 1.6.0부터 Android도 제어 전용입니다(6절) | 같은 코드베이스 |
| hbbs | 기기 ID·공개키 등록, 온라인 상태, 접속 요청·WebRTC 시그널링 전달 | rustdesk-server + `server/patches` |
| hbbr | P2P 실패 시 두 연결을 짝지어 암호화된 바이트를 그대로 전달 | rustdesk-server |
| Caddy | TLS 종료(Let's Encrypt 자동), 경로별 라우팅. 이미 웹 서버가 있는 서버는 nginx·Apache가 같은 일을 함. 1.6.0의 버전 정책 파일은 nginx 배치에서만 내줌(8절) | `deploy/Caddyfile` |
| hjv-api (1.6.0) | 계정 API: 연세포탈 로그인, 내 PC 목록, 계정 키, PC 동기화와 신뢰 목록, 켜기 명령, 새 앱 버전의 설치 파일(8-5). 웹 서버 뒤 Unix 소켓에서만 받음 | `server/api` ([README](../server/api/README.md)) |
| hjv-relay (1.6.0) | PC와 같은 네트워크의 NAS에서 서버가 서명한 켜기 명령을 받아 매직 패킷을 보냄 | `relay/` ([PROTOCOL.md](../relay/PROTOCOL.md), [relay-dsm.md](relay-dsm.md)) |
| hjv-release (1.6.0) | 개발 PC의 운영자 도구: 버전 정책 만들기와 확인, 사용자의 서명, 서버에 넣을 디렉터리와 hbbs 설정 값 | `tools/hjv-release` ([README](../tools/hjv-release/README.md)) |

**종단 간 암호화**: 세션 키는 두 기기가 직접 교환합니다. hbbs가 서명한 기기 공개키로 상대를 검증하고, WebRTC에서는 상대가 서명한 DTLS 지문으로 다시 검증합니다. 따라서 hbbs와 hbbr은 화면 내용을 볼 수 없습니다.
계정 요청(로그인, 내 PC 목록, PC 동기화)은 예외입니다. 서버까지의 TLS로만 보호되고, 앱은 인증서를 확인한 연결로만 보냅니다. 그래서 포탈 비밀번호는 서버 공개키로 따로 봉인하고, 모든 계정 요청에 그 기기의 계정 키 서명을 붙입니다(5-3).

## 3. 접속 순서

1. **PC 등록**: PC가 `wss://서버/ws/id`에 접속해 `RegisterPk`(ID, 공개키, 1.8.0부터 출입증)를 보내고 연결을 유지합니다. hbbs는 10초마다 빈 프레임(하트비트)을 보내고 PC가 되돌려 보냅니다. 연결이 끊기면 즉시 오프라인 처리됩니다.
2. **접속 요청**: 앱이 `PunchHoleRequest`(대상 ID, WebRTC offer, 1.8.0부터 출입증)를 보냅니다. 출입 확인을 켠 hbbs는 여기와 중계 요청에서 출입증을 확인합니다(9절).
3. **전달**: hbbs가 PC의 상시 연결로 `PunchHole`(offer, 앱의 주소 키)을 보냅니다.
4. **응답**: PC가 새 wss 연결로 answer를 보내고, 중계 경로(hbbr)도 함께 준비합니다. 두 기기의 ICE 후보는 hbbs를 거쳐 오갑니다.
5. **경합**: 앱은 WebRTC P2P와 중계를 동시에 진행하고 P2P를 우선합니다. 2.5초 안에 P2P가 안 되면 중계를 씁니다.
6. **인증·세션**: 서로의 신원을 검증하고 세션 키를 교환한 뒤 PC 비밀번호, 수락 창, 또는 같은 계정 기기의 증명(5-6)으로 접속을 허용합니다.

## 4. upstream 대비 변경점

### 서버 (`server/patches`)
오픈소스 hbbs에는 방화벽 환경에 필요한 기능이 **빠져 있었습니다** (소스 분석 결과).

| 문제 | 영향 | 패치 |
|---|---|---|
| PC 등록을 UDP로만 받음 (TCP/WS의 `RegisterPk`에 `NOT_SUPPORT` 응답) | UDP가 막힌 PC는 **영원히 오프라인** | TCP/WS 등록 + 상시 연결 + 하트비트, 해당 연결로 요청 전달 |
| WebRTC offer/answer를 버리고 ICE 후보를 처리하지 않음 | 자체 서버로는 **P2P 불가**, 전부 중계 | offer·answer·`force_relay` 전달, ICE 후보 양방향 라우팅 |
| 응답 후 연결을 맵에서 제거 | answer 이후 ICE 후보 전달 불가 | 연결마다 송신 큐, 연결이 닫힐 때만 정리 |
| WS 클라이언트를 `IP:0`으로 식별 | 같은 회사(NAT) 사용자끼리 응답이 뒤섞임 | 프록시의 `X-Real-Port`로 구분 |
| WS로 온 `OnlineRequest` 무시 | 앱에서 기기 온라인 표시 안 됨 | WS 엔드포인트에서 응답 |
| hbbr이 동시에 도착한 중계 요청 두 개를 짝짓지 못함 (경쟁 상태) | 양쪽이 같은 순간 중계에 붙으면 세션이 30초 후 실패 | 찾기와 대기 등록을 한 락 안에서 처리 |

검증: 통합 테스트 `tests/tcp_signaling.rs`(2개)와 `tests/relay_pairing.rs`(동시 도착 100쌍)를 추가했습니다. 모두 패치 전 실패하고 패치 후 통과합니다.
마지막 hbbr 버그는 아래의 방화벽 E2E 검증에서 실제 클라이언트로 발견했습니다.

1.6.0의 패치 0004는 계정 기능을 위한 것입니다.
- 루프백 콘솔(127.0.0.1:21115)에 `hjv-pk <id>` 명령을 더합니다. 답은 한 줄 `HJVPK1 <id> <서명된 IdPk> <마지막 등록 뒤 초>`이고, 서명된 값은 hbbs가 컨트롤러에게 주는 것과 같은 바이트(hbbs 개인키로 서명한 ID와 공개키)입니다. hjv-api는 앱과 같은 hbbs 공개키로 이 서명을 확인한 뒤에만 그 키를 믿습니다. 콘솔에는 인증이 없으므로, 그 포트를 다른 프로그램이 차지해도 남의 PC를 계정에 묶을 수 없게 하려는 것입니다.
- 중계 요청(`RequestRelay`)을 상대 PC로 넘기기 전에 `token`, `control_permissions`, `controlled_context`를 지웁니다. 컨트롤러가 PC 주인이 꺼 둔 권한을 켜거나 토큰을 남의 PC로 보내지 못합니다.
- 시험: `tests/hjv_pk.rs`(서명, 모르는 ID, 긴 입력, hbbs 재시작 뒤).

1.6.0의 패치 0005는 최소 버전을 위한 것입니다(8-4).
- `--hjv-min-controller-file`(또는 `HJV_MIN_CONTROLLER_FILE`)로 준 파일의 `MIN`보다 낮은 버전의 연결 요청(punch hole)을 `FROM` 시각부터 거절합니다. 열쇠 확인 바로 뒤, 상대를 찾기 전이라 상대 PC는 아무것도 듣지 못합니다. 답은 `PunchHoleResponse.other_failure`의 문구(`TEXT`)이고, 모든 판의 앱이 그 문구를 보이고 연결을 끝냅니다.
- 파일은 10초마다 다시 읽습니다. 잘못된 파일이면 이전 값을 그대로 쓰고 오류를 남깁니다. 파일이 없거나 `MIN=`이 비면 꺼집니다. 열쇠를 확인하지 않는 hbbs(`-k ""`)에서는 켜지지 않습니다. 문구에는 링크가 들어 있을 수 있으므로 로그에 파일 내용을 쓰지 않습니다.
- 시험: `tests/min_version.rs`(거절과 통과, 시각, 파일 바꾸기·비우기·지우기·잘못된 파일, 틀린 열쇠).

1.8.0의 패치 0006~0008은 교직원 전용 출입 제한을 위한 것입니다(9절).
- `--hjv-access-file`(또는 `HJV_ACCESS_FILE`)로 준 `access.conf`의 공개키로 연결 요청, 중계 요청, TCP·WebSocket 등록의 출입증을 오프라인으로 확인합니다. `MODE=off`(옵션이 없을 때도)는 0006 전과 같고, `count`는 세기만 하고, `enforce`는 거절합니다. 등록한 PC는 출입증이 끝나면 하트비트에서 끊습니다.
- 파일은 10초마다 다시 읽습니다. 출입 통제이므로 파일이 없거나 고장 나면 닫힘(모두 거절)이고, 끄는 길은 `MODE=off`입니다. 출입증 값은 로그에 쓰지 않습니다. 루프백 콘솔의 `hjv-access`가 판정의 개수를 한 줄로 답합니다.
- 시험: `tests/access.rs`와 `src/hjv_access.rs`의 단위 시험이 계약의 시험 벡터(`server/api/tests/vectors/access-tickets.json`의 사본)를 씁니다.

알려진 한계 (upstream과 동일):
- **IP별 등록 제한**: 공인 IP 하나당 분당 약 30회, 하루 300개 ID까지 등록할 수 있습니다. PC 수백 대가 공인 IP 하나를 공유하는 대형 사무실에서는 서버 재시작 직후 일부 PC가 최대 1분 늦게 등록되고, 300대를 넘으면 새 ID 등록이 거부됩니다. 기업 고객을 받으려면 이 제한을 설정값으로 바꿔야 합니다.
- **서버 단일 인스턴스**: hbbs는 1대로 운영합니다(SQLite). 확장은 중계(hbbr)를 늘리는 방식입니다.

### 클라이언트 (`client/patches`)
- 빌드할 때 `HJV_SERVER`(도메인)와 `HJV_SERVER_KEY`(hbbs 공개키)를 넣으면 서버 주소·키가 고정되고, 사용자 설정 화면에서 숨겨집니다.
- **WebSocket을 강제**합니다. 신호와 중계는 항상 443을 쓰고, WebRTC는 기본으로 켭니다(upstream은 공식 서버에서만 켭니다).
- upstream 업데이트 확인과 자동 업데이트를 끕니다. 1.6.0부터는 HJViewer 자신의 업데이트(8절)가 대신하고, upstream 경로(api.rustdesk.com, GitHub)는 고정 서버 빌드에서 봉인합니다.
- 앱 이름은 `HJViewer`, Android/iOS 식별자는 `kr.ac.yonsei.hjviewer`입니다. 아이콘은 HJ 모노그램을 띄운 모니터입니다. 원본 SVG는 `client/icons`에 있고, `scripts/make-icons.sh`가 플랫폼별 파일을 모두 `client/overlay`에 다시 만듭니다(같은 원본이면 같은 파일). Windows 실행 파일 정보와 정보(About) 화면의 링크는 이 저장소를 가리킵니다.
- 스플래시는 앱 아이콘을 앱 첫 화면과 같은 바탕색(라이트 `#FFFFFF`, 다크 `#18191E`) 가운데에 두고, 아래에 '연세대학교 프로젝트TF'를 작은 회색 글자로 둡니다. 바탕이 Flutter 첫 화면과 같아서 넘어갈 때 색이 바뀌지 않고, 시스템의 라이트·다크 설정을 따릅니다(앱 설정에서 다른 테마를 고르면 첫 화면에서 바뀜). Android 12 이상은 시스템 스플래시(`values-v31`, `values-night-v31`), Android 7–11은 `drawable-v23/launch_background.xml`, iOS는 `LaunchScreen.storyboard`(글자는 시스템 글꼴 라벨)를 씁니다. Windows는 창이 Flutter가 시작한 뒤에 나타나므로 바꾸지 않습니다. 글자 원본은 Noto Sans CJK KR의 윤곽선으로 만든 `client/icons/splash-text.svg`(`scripts/make-splash-text.py`)이고, Android 벡터와 iOS 이미지는 `scripts/make-icons.sh`가 만듭니다.

### 방화벽 E2E 검증 ([e2e.md](e2e.md))

실제 HJViewer 클라이언트(Linux 빌드, 같은 Rust 코어) 두 대를 네트워크 네임스페이스에 넣고, 서버로 가는 TCP 443만 허용하는 방화벽을 걸어 검증했습니다.
등록, 비밀번호 로그인, 데이터 전달, **원격 화면 수신**이 모두 동작했습니다. 443만 열려 있으면 중계(wss)로, 피어 간 UDP가 열려 있으면 WebRTC P2P로 연결됩니다.

## 5. 계정과 비밀번호 없는 연결 (1.6.0)

연세포탈 계정으로 로그인한 기기끼리는 PC의 ID나 비밀번호 없이 연결합니다. 그 밖의 연결(다른 사람의 PC, 로그인하지 않은 앱, 1.5.x)은 지금처럼 ID와 PC 비밀번호로 합니다. 서버 쪽 형식은 [server/api/README.md](../server/api/README.md), 중계기 규약은 [relay/PROTOCOL.md](../relay/PROTOCOL.md)가 정합니다. 서버 설치와 운영은 [server-runbook.md](server-runbook.md) 7절, 개인정보는 [privacy.md](privacy.md)에 있습니다.

### 5-1. 구성

```
앱(아이폰·안드로이드·Windows) ──HTTPS 443──▶ nginx (rd.example.com, 다른 사이트와 함께 쓸 수 있음)
  │  계정 키(기기마다, 로그인 때 만듦)          ├ /ws/id, /ws/relay → hbbs·hbbr (그대로)
  │  모든 계정 요청에 X-HJV-Proof              ├ 계정 경로 → hjv-api (Unix 소켓, systemd가 쥠)
  │                                            │     ├ HTTPS → 연세 SSO
  │                                            │     ├ 127.0.0.1:21115 → hbbs 콘솔 hjv-pk (패치 0004)
  │                                            │     └ 목록 키·명령 키·봉인 키 (systemd 암호화 자격 증명)
  │                                            └ 그 밖의 /api/ → nginx가 404 JSON (그대로)
  │
  └─(연결: hbbs·hbbr·WebRTC, 종단 간 암호화)─▶ Windows PC 서비스(--server, SYSTEM, 로그온 전에도)
        Hash{salt, challenge, hjv_nonce}  ◀──      ├ HKLM\SOFTWARE\HJViewer\Account (허용 표시)
        LoginRequest{…, hjv_key_proof}  ──▶        ├ 신뢰 목록(서비스 설정 폴더)
                                                   └ 동기화: 기기 키 서명 ──HTTPS──▶ /api/hjv/pc/sync
                                                        ◀── 목록 키로 서명된 신뢰 목록 (+ 켜기 정보 보고)
NAS의 hjv-relay ──HTTPS long-poll, 중계기 키 서명──▶ /api/hjv/relay/poll ◀── 명령 키로 서명된 켜기 명령
NAS ──매직 패킷(자기 랜카드의 브로드캐스트, UDP 9·7)──▶ 꺼진 내 PC
```

- **연결 경로에는 hjv-api가 없습니다.** hjv-api가 멈춰도 원격 세션과 비밀번호 연결은 영향을 받지 않고, 비밀번호 없는 연결은 PC가 받아 둔 목록으로 최대 24시간 계속됩니다. 그래서 hjv-api의 장애는 하루 동안 드러나지 않다가 한꺼번에 나타날 수 있으므로 감시를 둡니다([server-runbook.md](server-runbook.md) 7-14).
- 하트비트, 기기 정보, 접속 기록 경로는 nginx가 본문을 읽지 않고 404로 답합니다. 1.5.x PC와 로그인하지 않은 PC는 hjv-api에 아무것도 보내지 않습니다.

### 5-2. 키

| 키 | 종류 | 만드는 곳 / 보관 | 쓰임 |
|---|---|---|---|
| 기기 키(있던 것) | Ed25519 | 앱이 만듦. `HJViewer.toml`. Windows에서는 그 PC의 모든 Windows 사용자가 씀 | 핸드셰이크의 SignedId, 로그인의 기기 서명, PC 동기화 서명 |
| 계정 키 | Ed25519 | 비밀번호 로그인마다 새로. 아이폰 Keychain(이 기기 전용, 잠금 해제 때만), 안드로이드 앱 데이터(클라우드 백업·기기 이전에서 뺌), Windows `%LOCALAPPDATA%\HJViewer-account\account-key.bin`(DPAPI 사용자 범위, 로밍 안 함) | 모든 계정 요청의 서명, 연결 증명. 같은 기기(앱의 uuid나 기기 ID)의 새 로그인이 옛 키를 바꾸고, 계정의 키가 20개를 넘으면 가장 오래 쓰지 않은 키를 서버가 폐기 |
| 봉인 키 | X25519 | 사용자가 오프라인으로 만들어 서버의 암호화 자격 증명에 넣음. 공개키는 앱 빌드 변수 `HJV_LOGIN_SEAL_PUBKEY` | 로그인 비밀번호 봉인 열기 |
| 기록 키 | HMAC | 서버에서 | 기록과 저널의 계정·기기 꼬리표 |
| 목록 키 1·2 | Ed25519 | 1번은 서버에서, 2번은 오프라인. 공개키 둘을 앱 빌드 변수 `HJV_TRUST_PUBKEYS`로 고정 | 신뢰 목록 서명. 1.9.0부터 지원 코드를 넣은 PC 하나에 주는 지원 확인(access-tickets.md 3-7)도. 2번으로 바꾸면 PC가 1번 목록을 다시 받지 않음 |
| 명령 키 1·2 | Ed25519 | 목록 키와 같음. 공개키는 hjv-relay 빌드 변수 `HJV_COMMAND_PUBKEY`에만 | 켜기 명령 서명 |
| 중계기 키 | Ed25519 | hjv-relay가 NAS에서 처음 실행할 때 만듦(root 전용 폴더) | 중계기 요청 서명 |
| hbbs 서버 키(있던 것) | Ed25519 | hbbs | 기기의 (ID, 공개키) 서명 |

서명하는 바이트는 모두 용도별 문자열로 시작합니다: `hjv-login-v1`(기기 로그인), `hjv-ckey-v1`(계정 키 소유 증명), `hjv-req-v1`(계정 요청), `hjv-conn-v1`(연결 증명), `hjv-pc-v1`(PC 동기화), `hjv-trust-v1`(목록), `hjv-support-v1`(지원 확인, 1.9.0), `hjv-relay-v1`(중계기 요청), `hjv-wake-v1`(켜기 명령). `hjv-`로 시작하는 바이트는 protobuf로 해석될 수 없어서, 같은 기기 키가 서명하는 `IdPk`와 섞이지 않습니다. 키 오프라인 사본은 에이전트가 돌지 않는 곳에서 이동식 매체로 만들고, 프로젝트 폴더나 여러 사람이 쓰는 공유 폴더에 두지 않습니다.

### 5-3. 로그인과 계정 요청

- **봉인**: 앱은 비밀번호를 서버 봉인 공개키로 봉인합니다(`hjv-sealed-v1.<kid>.<봉인>`, libsodium sealed box). 봉인 안에는 비밀번호, 시각, 일회용 값, 기기 ID와 함께 이 로그인에서 새로 만든 **계정 공개키**(`ck`)와 그 키의 소유 증명(`cp`)이 들어 있습니다. TLS를 가로채는 장비(기기가 믿는 회사·MDM 루트)도 비밀번호를 보지 못하고 계정 키를 바꿔치기하지 못합니다.
- **SSO**: hjv-api는 포탈 ID와 비밀번호를 연세 SSO에 확인합니다(password grant). 같은 서버의 행정허브 WordPress 플러그인의 SSO 등록을 쓰고, 그 플러그인이 읽는 대로 답을 읽습니다. 사용자 정보에서는 그 사람의 코드(`pcode`)와 성명만 읽고, 이메일과 소속은 읽지도 보관하지도 않습니다. 교직원만 되는 것은 HJViewer의 ID 규칙 때문입니다. 입력한 ID를 대문자로 바꿔 Z나 Y로 시작하고 ZA로 시작하지 않아야 SSO에 묻고(아니면 SSO를 부르지 않고 "연세대학교 교직원의 연세포탈 ID로만 로그인할 수 있습니다"), SSO가 알려 준 pcode도 같은 규칙에 맞아야 그 사람의 고정 ID로 계정에 둡니다(아니면 "이 계정으로는 HJViewer를 쓸 수 없습니다"). 행정허브 플러그인은 Z와 B를 받고, 첫 글자를 더하는 것은 코드 한 줄입니다. 예외는 Apple 앱 심사용 데모 계정 하나입니다. 서버의 파일(`HJV_API_REVIEW_FILE`)에만 있는 규칙 밖의 ID로, 그 파일이 있는 동안 SSO 대신 파일의 비밀번호 해시로 로그인하고, PC를 묶지 못하고 새 버전을 받지 못하며, 자기가 만들지 않은 계정에는 들어가지 못합니다([server/api/README.md](../server/api/README.md)의 "The App Review account", [server-runbook.md](server-runbook.md) 7-17). 첫 글자를 더할 때는 그 글자로 시작하는 데모 계정을 먼저 지웁니다. 통과한 ID가 명단에 없으면 그 로그인에서 명단에 올립니다(`HJV_API_LOGIN=open`, 2026-10-14 사용자 결정). 명단은 "HJViewer를 써도 됨"을 뜻하고, 운영자는 항목을 지우는 대신 막습니다(`admin block`): 막을 때 그 계정의 토큰과 계정 키가 바로 폐기되고 그 PC들은 키 없는 목록을 받으며, 다음 로그인은 SSO가 비밀번호를 받아들인 뒤에 403 "이 계정은 관리자가 HJViewer 사용을 막았습니다"를 받습니다. 명단 방식(`HJV_API_LOGIN=list`)으로 바꾸면 처음처럼 명단에 있는 ID만 SSO에 확인합니다. ID에 따라 달라지는 실패는 모두 같은 답과 같은 최소 지연으로 돌려주어 명단이 드러나지 않습니다. SSO가 이 서버를 거부하거나 연달아 실패하면 잠시 SSO 호출을 멈추고, 그동안 모든 로그인에 같은 503("연세 인증 서버에 지금 연결할 수 없습니다")을 줍니다.
- **기기 서명**: 설치된 Windows PC의 로그인에는 기기 키 서명이 붙습니다. hjv-api는 hbbs가 서명한 그 ID의 공개키(`hjv-pk`, 패치 0004)로 확인한 뒤에만 그 PC를 계정에 묶습니다. 이미 다른 계정에 묶인 PC는 거절합니다.
- **모든 계정 요청에 서명**: `X-HJV-Proof: v1.<t>.<n>.<sig>`(`t`는 유닉스 초의 10진수, `n`은 16바이트의 base64url, `sig`는 서명의 base64url). 계정 키로 `"hjv-req-v1" NUL 메서드 NUL 경로?쿼리 NUL t NUL n NUL base64(SHA-256(본문)) NUL base64(SHA-256(토큰))`에 서명합니다. `t`와 `n`은 헤더의 글자 그대로, 해시는 패딩이 있는 표준 base64이고, 본문이 없으면 빈 바이트의 해시입니다. 서버는 토큰의 키로 서명을 확인하고, 시각 ±600초, 바꾸는 요청은 일회용 값 20분 재사용 거부를 봅니다. 앱의 TLS 재시도처럼 같은 요청을 바이트 그대로 짧은 시간 안에 다시 보낸 것은 재사용으로 보지 않고 첫 답을 다시 줍니다(로그인의 30초 재시도와 같은 방식). 그래서 토큰만 훔쳐서는(백업, 파일 공유, 가로채기 장비) 아무것도 못 합니다. 키를 쓸 수 없으면(잠긴 아이폰) 앱은 요청을 보내지 않고, 로그아웃하지도 않습니다.
- **시계**: 서명은 맞는데 시각만 창 밖이면 서버는 401·400 대신 409 `clock`과 서버 시각을 줍니다. 앱은 401·400에서만 스스로 로그아웃하므로 시계가 틀린 기기가 조용히 로그아웃되지 않고, 서버와의 차이를 배워 다음 요청부터 맞춰 보냅니다.
- **엄격한 TLS**: 계정 요청은 인증서 무시 재시도(`allow-insecure-tls-fallback`)를 쓰지 않습니다.
- **계정 삭제(1.9.1)**: 로그인한 앱은 계정 키로 서명한 요청 하나(`POST /api/hjv/account/delete`, 본문 `{"confirm":"delete-account"}`)로 자기 계정을 바로 지웁니다(App Store 지침 5.1.1(v)). 지우는 것은 관리자의 `user delete`와 같고 한 트랜잭션에서 끝납니다. PC는 묶음 무덤을 남기고 풀리고, 중계기는 폐기되며, 모든 토큰과 계정 키가 끝나 다른 기기는 다음 요청의 401로 로그아웃됩니다. App Review 계정은 명단 항목이 남아 다음 심사 로그인이 빈 계정을 새로 만듭니다. 운영자 기록에 앞 줄을 쓰지 못하면 지우지 않습니다. 백업을 복원하면 지운 계정이 돌아오는데, 그 줄의 꼬리표로 다시 지우기 때문입니다. 앱은 200을 받은 자리에서 이 기기를 로그아웃시키고, 같은 요청의 재시도는 지워진 토큰 대신 요청 해시로 첫 답을 받습니다.
- **남에게 보내는 이름**: 로그인해도 다른 사람의 PC에 성명이나 포탈 ID를 보내지 않습니다. 1.5.1처럼 Windows 사용자 이름(휴대폰은 기기 이름)을 보냅니다. 1.9.0부터 교직원이 만든 지원 코드를 넣은 PC 하나에는, 그 코드를 만든 기기가 연결할 때 "연세대 교직원(로그인 확인)"이 보입니다. 이름은 보이지 않습니다(access-tickets.md 3-7의 "지원 확인").

### 5-4. PC를 계정에 묶기

- **로그인하면 켜짐**: 설치된 Windows PC에서 HJViewer에 로그인하면 hjv-api가 그 PC를 계정에 묶고(무작위 128비트 묶음 ID), 로그인 응답에 묶음 ID와 서버 시각 `login_at`을 줍니다. 앱은 기존 IPC로 서비스에 묶기 요청을 넣습니다. 서비스(SYSTEM)는 서버의 서명된 목록이 같은 묶음을 확인하고 그 로그인이 10분 안이었을 때만 `HKLM\SOFTWARE\HJViewer\Account`에 허용 표시를 씁니다. UAC나 따로 누르는 허용 단계는 없습니다. 그래서 IPC로 아무 값이나 넣어도, 예전 묶기 요청을 다시 넣어도 켜지지 않습니다.
- **끄기**: 그 PC의 Windows 사용자는 누구나 설정 → 계정에서 [끄기]를 누를 수 있습니다. 상태는 HKLM에 두므로 다른 사용자가 설정을 다시 써도 되돌아가지 않고, 다시 켜려면 묶인 계정으로 그 PC에서 다시 로그인해야 합니다.
- **로그아웃**: 그 PC를 묶은 사용자가 로그아웃하면 앱은 요청을 보내기 **전에** 서비스에 풀기 요청을 넣고, 서비스는 1초 안에 허용 표시를 지웁니다. 서버에 닿지 못해도 그 PC에서는 바로 꺼집니다. 401·400으로 앱이 스스로 로그아웃하는 경우에는 아무것도 풀지 않습니다.
- **재부팅, 업데이트, 제거**: 서비스는 Windows 로그온 전에도 HKLM과 받아 둔 목록으로 동작합니다. 다시 설치하거나 업데이트해도 허용 표시는 남고, 제거만 지웁니다. 시작 메뉴의 "Uninstall"은 권한을 올리지 않고 돌므로, 허용 표시는 서비스를 멈춘 뒤 권한을 올려 도는 제거 스크립트가 지웁니다(`reg delete`).
- **풀기는 서버의 한 곳**: 묶음을 푸는 모든 길(그 PC의 로그아웃, [이 PC 빼기], 다른 기기에서 빼기, 관리자 `binding revoke`, 계정 삭제(관리자 `user delete`, 1.9.1부터 앱의 [계정 삭제] `POST /api/hjv/account/delete`), 180일 정리)은 `db::release_binding` 하나를 지나고, 묶음 ID를 180일 동안 무덤으로 남깁니다. 그 PC는 다음 동기화에서 서명된 `revoked`를 받아 허용 표시를 지웁니다.

### 5-5. 신뢰 목록과 동기화

- 묶인 PC의 서비스는 보통 2분마다 기기 키로 서명한 요청(`hjv-pc-v1`)을 `POST /api/hjv/pc/sync`로 보냅니다. 서버가 주는 간격(`HJV_API_TRUST_REFRESH`, 운영 120초)을 PC는 빌드 상수 5~300초로 자르므로, 서버에 닿는 PC는 늦어도 5분 안에 되돌리기를 받습니다. 다만 서버에 닿지 못하는 동안 PC는 30초부터 최대 10분까지 간격을 늘려 다시 묻기 때문에, 서버가 오래 멈췄다 돌아온 직후에는 10분까지 걸릴 수 있습니다. 묶이지 않은 PC는 보내지 않습니다.
- 답의 **신뢰 목록**은 그 계정의 폐기되지 않은 계정 공개키와 기기 ID·이름, 허용된 연결 종류, 가린 주인 이름을 담고, 목록 키로 서명됩니다(`hjv-trust-v1`). PC는 받은 바이트로 서명을 먼저 확인하고, 자기 ID·자기 키·자기 묶음·**이번 요청의 일회용 값**(`req`)에 대한 답인지, 고정한 키 번호가 바닥 이상인지, 수명이 72시간 이하인지 봅니다. 옛 목록을 다시 보내거나 되돌리는 공격이 통하지 않습니다.
- 수명은 **받은 시각부터** 셉니다(운영 24시간, `HJV_API_TRUST_TTL`, 빌드 상한 72시간). PC 시계와 서버 시계의 차이에 기대지 않고, 시계가 크게 틀리면 안전한 쪽(다시 받기, 일찍 만료)으로 실패합니다.
- 허용을 지우는 것은 **서명된** `revoked`뿐입니다. 서명 없는 답(`listed`, `unbound`)으로는 아무것도 지우지 않으므로, TLS를 가로챈 쪽이 거짓 답으로 허용을 지울 수 없습니다.
- 서버는 같은 PC가 10초 안에 다시 와도 429를 주지 않고, 그 사이 변경 번호가 그대로면 마지막 목록에 새 `req`만 넣어 다시 서명합니다. 기기 키를 가진 로컬 사용자가 요청을 쏟아부어 되돌리기를 늦추지 못합니다.
- **키 바뀜**: PC가 설정을 잃어 기기 키가 바뀌면 동기화 서명이 맞지 않습니다. 서버는 그 자리에서 hbbs에 묻고(한 PC 1분에 한 번), 진짜 hbbs가 새 키를 가졌으면 그 PC를 `needs-relogin`으로 표시합니다. 컨트롤러는 목록을 새로 받은 뒤 그 PC에 비밀번호 창을 띄우고, 그 PC에서 다시 로그인하면 비밀번호 없는 연결이 돌아옵니다. 다시 켜진 PC는 hbbs에 등록하기 전에 첫 동기화를 보내므로, 표시까지 약 2분(96~144초) 걸리고 그동안 컨트롤러에는 키 바뀜 경고가 뜹니다(2026-10-14 결정: 그대로 둠).
- **복제한 PC**(알려진 한계, 2026-10-14 결정): sysprep 없이 복제해 Windows의 MachineGuid가 같은 PC 둘(또는 한 PC의 두 Windows 사용자)이 같은 계정으로 로그인하면, 뒤의 로그인이 앞의 계정 키를 같은 기기의 옛 키로 보고 폐기해 서로 로그아웃시킵니다. 그때마다 다른 내 기기에 새 기기 알림이 뜹니다.
- PC는 동기화에 앱 버전, 끄기 여부, 키·날짜별 받아들인 횟수(서버는 줄어드는 보고를 받지 않고 큰 값으로 합침), 거절 이유별 개수, 켜기 정보를 싣습니다. 연결마다의 기록은 받지 않고, 계정 키·PC·날짜별 마지막 시각과 횟수만 받습니다.

### 5-6. 연결 증명

연결할 때는 서버를 부르지 않습니다.

1. 기능이 있는 PC(계정 빌드, 서비스 프로세스, 설치형)는 묶였는지와 상관없이 `Hash`에 32바이트 일회용 값(`hjv_nonce`, 필드 번호 1001)을 넣습니다. 값이 비면 `Hash`의 바이트는 1.5.1과 같습니다.
2. 컨트롤러는 다음을 모두 만족할 때만 `LoginRequest.hjv_key_proof`(필드 1001)에 증명을 넣습니다: 계정 빌드이고 로그인했으며 계정 키를 쓸 수 있음, 일회용 값이 있음, 세션이 암호화됨, 다른 서버(`id@서버`)가 아님, 연결 종류가 원격 화면·파일 전송·카메라(터미널은 서버 설정으로만 열 수 있고, 포트 포워딩·RDP는 늘 비밀번호), 대상이 **내 PC 목록**에 있고 `needs-relogin`이 아님.
3. **키 연속성**: 내 PC 목록에 있고 `needs-relogin`이 아닌 PC에 연결할 때, 이 채널에서 확인한 PC 키가 목록에 묶인 그 PC의 키와 다르면 증명도 기억한 비밀번호도 보내지 않고 보안 경고 창(닫기만 있음)을 띄워 연결을 끝냅니다. hbbs 키를 훔쳐 중계를 가로채는 쪽에게 비밀번호 응답이 가지 않게 하려는 것입니다. 경고 창에는 목록에서 빼는 단추를 두지 않습니다. 가로채는 쪽이 경고를 일부러 띄워 사용자가 PC를 빼게 만들면, 다음 연결부터 이 확인이 없어지기 때문입니다. 이 확인은 PC 키를 확인한 암호화된 채널에서만 합니다. 키를 확인하지 못해 암호화 없이 이어지는 연결은 앱이 먼저 "종단 간 암호화를 확인할 수 없습니다"라며 계속할지 묻고(1.5.1에도 있는 창), 사용자가 계속하기를 고르면 1.5.1처럼 비밀번호 경로로 갑니다. 터미널의 Windows 관리자 로그인, 포트 포워딩 창에 직접 넣은 비밀번호, 키 교환 뒤 24시간이 지난 채널의 로그인도 1.5.1처럼 이 확인을 받지 않습니다.
4. 증명은 계정 키로 다음 바이트에 한 서명입니다(길이는 바이트 수 1바이트, ID는 UTF-8).
   ```
   "hjv-conn-v1" 0x00
   u8 len(pc_id)  | pc_id     PC의 ID (LoginRequest.username)
   pc_pk[32]                  이 채널에서 확인한 PC 키 (PC는 자기 기기 공개키)
   nonce[32]                  이번 연결의 Hash.hjv_nonce
   u8 len(ctl_id) | ctl_id    컨트롤러 자신의 ID (LoginRequest.my_id)
   u8 kind                    0 원격 화면, 1 파일 전송, 2 카메라, 3 터미널, 4 포트 포워딩·RDP(1.6.0에서는 보내지 않음)
   ctl_pk[32]                 계정 공개키
   ```
   다른 연결·다른 PC로 다시 보내거나, 가짜 PC가 받아 진짜 PC로 넘기거나, 종류를 바꿔치기하면 모두 실패합니다. 기억한 비밀번호가 있으면 함께 보내므로, 증명이 거절돼도 왕복이 늘지 않습니다.
5. PC는 영구 비밀번호가 받아들여지는 설정인지("임시 비밀번호만"이면 거절), 비밀번호를 틀려 막힌 주소가 아닌지, 세션이 암호화됐는지, 허용 표시가 있고 꺼 두지 않았는지를 보고, **서명을 먼저** 확인한 뒤 받아 둔 목록에서 키·연결 종류·기기 ID를 봅니다. 목록이 없거나 지났을 때, 목록에 없는 키가 목록보다 나중에 등록된 키일 때(방금 로그인한 새 기기), 관리자가 연결마다 확인(`strict`)을 켰을 때는 한 번만 즉시 동기화합니다(최대 1.5초, 한 PC에 동시에 하나, 끝난 뒤 10초 안에는 다시 하지 않음). 서명이 틀린 증명은 동기화를 일으키지 않습니다.
6. 통과하면 **올바른 영구 비밀번호와 똑같이** 처리합니다. PC의 2FA, 클릭 승인 모드, 화이트리스트, 터미널의 Windows 관리자 로그인은 그대로입니다. 연결 창의 이름은 목록의 기기 이름이고, 1.9.0부터 확인 표시는 이름과 따로 IPC `Login`의 `hjv_mark`(`same-account`와 가린 주인)로 넘어가 '같은 계정 확인됨 · <가린 주인>'으로 보입니다(5-10). 연결은 받아들인 증명을 기록 하나(`hjv_proven`: 목록의 기기 이름과 가린 주인)로 로그온 응답보다 먼저 들고, 연결 창의 표시와 같은 연결의 다른 1.9.0 기능이 모두 이 기록을 읽습니다. 그 기기 이름은 기기가 로그인할 때 스스로 알린 값으로 서버가 정한 모델 이름이고, PC 로그에 남는 기기 ID도 그 기기가 알린 값입니다. 증명 없이 온 연결의 이름은 상대가 적은 값이며 확인 표시를 받지 못하고, 확인 표시를 흉내 내는 말이 들어 있으면 '확인되지 않은 이름'이 붙습니다(5-10). 2FA가 켜진 PC에는 같은 계정의 연결에도 수락 단추가 보입니다. 1.8.x까지는 이름 끝에 "· 같은 계정(<가린 주인>)"을 붙였고, 증명 없는 연결도 같은 글을 적을 수 있었습니다.
   1.9부터 같은 증명은 지원 코드를 넣은 PC에도 갑니다. 그 PC는 묶이지 않았으므로 증명으로 열지 않고, hjv-api가 그 PC에 준 지원 확인의 계정 키와 같으면 연결 창에 교직원 표시만 붙입니다(access-tickets.md 3-7). 수락은 지금처럼 그 PC 앞의 사람이 합니다.
7. 거절하면 비밀번호가 같이 오지 않은 경우 `"Empty Password"`를 보내고, 1.6.0 컨트롤러는 "비밀번호 없이 연결하지 못했습니다"가 붙은 비밀번호 창을 띄웁니다. 새 오류 문자열이 없으므로 1.5.x 컨트롤러도 지금처럼 동작합니다. 거절은 실패 횟수에 세지 않습니다.
8. **열린 세션 다시 보기(1.9.0, TV-W5)**: PC의 서비스는 증명으로 연 연결마다 그 증명의 계정 공개키, 연결 종류, 컨트롤러 ID를 메모리에만 둡니다(디스크와 서버에는 두지 않음). 동기화로 서명된 목록을 받아 둘 때마다(`active`나 `disabled`를 받아 둠, 서명된 `revoked`로 묶음을 지움), 그리고 그 PC에서 로그아웃해 묶음이 풀릴 때 열린 연결을 그 목록과 견주고, 5번의 키·연결 종류·기기 ID 확인을 지금 통과하지 못하는 연결을 1초 안에 끊습니다. 묶음이 바뀌었어도 새 목록에 그 키가 있으면 둡니다. 끊을 때 컨트롤러에 닫는 이유를 보냅니다: `active` 목록에서 키가 빠졌거나 기기 ID가 다르면 "이 기기의 로그인이 끝나 연결을 끊었습니다. (login ended, not allowed)", 그 밖(`revoked`, `disabled`, 그 PC에서의 로그아웃, 연결 종류가 빠짐, 그 키가 없는 다른 묶음)은 "이 PC가 비밀번호 없는 연결을 더 받지 않아 연결을 끊었습니다. (password-less ended, not allowed)". "not allowed"가 컨트롤러의 자동 다시 연결을 멈추고, 1.9.0 컨트롤러는 그 자리에 자기 언어의 문구를 보입니다. 원격 화면이었으면 PC를 잠그고(5-11), PC 로그에 한 줄 남깁니다. 목록이 지나기만 하면(서버에 닿지 못함), 동기화가 실패하거나 서명 없는 답이 오면 끊지 않고 새 연결만 막습니다(24시간 규칙). 비밀번호·클릭 승인·이용 비밀번호·지원 코드로 연 연결은 견주지 않고, 그 PC의 [끄기]도 열린 연결을 끊지 않습니다(동기화가 이어지므로 그 뒤의 폐기는 그대로 끊음).

| 컨트롤러 \ PC | 1.5.x·upstream | 1.6.0, 묶이지 않음·꺼 둠·로그아웃함 | 1.6.0, 켜짐 |
|---|---|---|---|
| 1.5.x·upstream | 지금과 같음 | 지금과 같음(일회용 값은 모르는 필드로 무시) | 지금과 같음 |
| 1.6.0, 로그인 안 함 / 남의 계정 | 지금과 같음 | 지금과 같음 | 지금과 같음(증명을 보내지 않음) |
| 1.6.0, 같은 계정 | 지금과 같음(일회용 값 없음) | 증명을 보내지 않거나 거절 → 거절 문구가 붙은 비밀번호 창 | **비밀번호 없이** |

### 5-7. 보장하는 것과 하지 않는 것

- PC가 비밀번호 없이 열리는 것은 다음을 모두 만족할 때뿐입니다: 그 계정에 지금 로그인된 기기의 키이고, 그 PC에서 그 계정으로 로그인해 묶은 뒤 로그아웃·끄기·빼기를 하지 않았고, 암호화된 세션이며, 서버가 그 기기와 PC를 아직 허용하고(서버에 닿지 못하면 최대 24시간 전의 상태), 허용된 연결 종류일 때입니다.
- 목록은 PC를 둘러싼 울타리가 아닙니다. ID와 PC 비밀번호를 아는 사람은 지금처럼 들어옵니다. PC마다 긴 영구 비밀번호를 정해 두는 것을 권합니다. 비밀번호 없는 연결이 안 되는 때(서버 장애가 하루 넘게 이어짐, 끄기, 로그아웃, 키 바뀜)에 쓰는 길입니다.
- 받아들인 남는 위험(결정 U1·U2·U4·U5):
  - 그 계정의 포탈 비밀번호(같은 서버의 WordPress 로그인 플러그인도 이 비밀번호를 평문으로 받음)나 로그인된 내 기기(잠금이 풀린 휴대폰, 내 Windows 계정으로 도는 프로그램)를 가진 사람은 그 계정에 묶인 모든 PC를 PC 비밀번호 없이 엽니다. 알아채는 방법은 다른 내 기기의 '새 기기 로그인' 알림과 '로그인한 기기' 목록입니다. 알림은 내 기기 하나에서 답할 때까지 기한 없이 남고, 지금 쓰는 기기보다 먼저 로그인한 기기에도, 답하기 전에 로그아웃했거나 로그아웃당한 기기에도 뜹니다. '로그인한 기기'에는 로그인이 끝난 기기도 30일 동안 어떻게 끝났는지와 함께 나옵니다. 알림의 앱 버전·기기 모델·기기 ID는 그 기기가 스스로 알린 값이라 포탈 비밀번호를 가진 쪽이 내 휴대폰과 똑같이 보이게 할 수 있고, 서버가 본 값은 로그인 시각과 학내·학외뿐입니다. 포탈 비밀번호를 바꿔도 이미 로그인한 기기는 남으므로, 바꾼 뒤에는 [다른 기기 모두 로그아웃]도 누릅니다. TOTP, 짝 맺기, 연결마다 Face ID는 두지 않습니다. 대신 휴대폰과 태블릿 앱에는 켜는 사람만 쓰는 '앱 잠금'(1.9.0, W13)이 있습니다. 켜 두면 앱을 새로 열 때와, 정한 시간(바로·1분·5분, 기본 1분) 이상 백그라운드에 있다가 돌아올 때 Face ID·Touch ID·지문 또는 기기 암호를 묻고, 그동안 열린 원격 세션을 포함한 앱 전체를 가립니다(세션은 아래에서 계속 돌고 입력은 닿지 않음). 생체 정보는 휴대폰의 운영체제가 확인하고 앱은 맞았는지만 받으며, 잠금에 관한 것은 서버에 보내지 않습니다. 기본은 꺼짐이므로, 켜지 않은 휴대폰에서는 위의 위험이 그대로입니다. 기기 암호를 아는 사람은 이 잠금도 엽니다.
  - 되돌리기(로그아웃, 빼기, 관리자 명령, 끄기 스위치)는 PC가 서버에 닿으면 보통 2분, 늦어도 5분 안에(서버가 오래 멈췄다 돌아온 직후에는 10분까지), 닿지 못하면 최대 24시간 뒤에 효과가 납니다. 1.9.0부터 PC는 그때 이미 열려 있는 비밀번호 없는 연결도 끊고, 그 PC에서 로그아웃하면 그 PC의 비밀번호 없는 연결을 바로 끊습니다(5-6의 8번). 남는 것은 1.9.0 전의 PC, 서버에 닿지 못하는 동안의 PC, 비밀번호로 연 연결입니다. 그때는 PC의 연결 창에서 끊거나, 내 기기에서 PC 비밀번호로 그 PC에 연결해 '원격 PC 다시 시작'을 누르거나, PC를 다시 시작합니다(1.6.0의 한계 U1-d를 1.9.0에서 좁힘).
  - 공용 PC: 그 PC의 어느 Windows 사용자든 HJViewer에 로그인하면 묶이지 않은 그 PC를 자기 계정에 엽니다. 다른 사용자는 [끄기]를 누를 수 있고, 가린 주인 이름과 주인 기기의 이름이 든 목록을 볼 수 있습니다.
  - hjv-api 서버가 장악되면(목록 키와 DB) 묶인 모든 PC에 자기 키를 넣은 목록을 줄 수 있습니다. 쫓아낸 뒤 목록 키를 2번으로 바꾸면 서버에 닿는 PC는 늦어도 5분 안에 회복하고, 닿지 못하는 PC는 그 목록을 최대 72시간 씁니다. 그 서버에서 root로 일하는 운영 에이전트는 결정 O1에 따라 "하지 말 것" 규칙으로만 막습니다([server-runbook.md](server-runbook.md) 7-0).
  - 증명은 세션 키 교환이 아니라 확인한 PC 키에 묶입니다. 그 PC의 기기 키와 hbbs 등록 가로채기를 함께 가진 쪽은 증명을 넘길 수 있습니다(비밀번호도 지금 같은 위험).
  - 열린 로그인(2026-10-14 사용자 결정): 명단 방식에서는 명단에 있는 ID(약 10개)만 연세 SSO에 닿았지만, 이제는 ID 규칙(Z나 Y로 시작, ZA 제외)에 맞는 포탈 ID는 무엇이든 hjv-api를 거쳐 SSO에 닿습니다. 그래서 hjv-api가 교직원 계정의 비밀번호를 시험하는 창구가 될 수 있고, 연세 SSO가 실패가 잦은 계정을 잠근다면 남의 연세 계정을 잠그는 데 쓰일 수 있습니다. 연세 쪽에서는 이 서버의 주소가 원인으로 보이고, SSO가 이 주소를 막으면 같은 서버의 WordPress 로그인도 멈춥니다. 그래서 명단에 없는 ID에는 한도를 따로 낮게 둡니다: ID마다 하루 실패 2번(`HJV_API_LIMIT_NEW_ID`), 그런 ID 모두 합쳐 SSO 호출 시간당 10번(`HJV_API_LIMIT_SSO_NEW`). 그 10번 가운데 한 ID와 한 주소(IPv6는 /64)는 각각 4분의 1(2번)까지만 쓰고, 처음 로그인이 성공하면 그 호출은 돌려받습니다. 그래서 같은 주소 뒤에서 여러 사람이 차례로 처음 로그인해도 막히지 않습니다. 하루에 명단 밖 ID로 SSO를 불러 아무도 로그인하지 못한 것은 많아야 240번이고, 명단에 있는 사람의 로그인은 이 몫과 상관없습니다. 위험을 줄일 뿐 없애지는 못합니다. 몫이 차면 그동안 처음 로그인하는 사람은 실패하고(미리 `allow import`한 ID는 영향 없음) 5분 점검이 경보합니다(`sso_new`). 주소 하나로는 몫을 채우지 못하지만, 주소 다섯 개(IPv6는 /64 다섯 개. IPv6 가입자는 /64를 여러 개 받는 일이 흔함)면 시간당 틀린 비밀번호 10번으로 채웁니다. 주소 몇 개를 가진 사람은 이렇게 적은 요청으로 처음 로그인을 계속 막을 수 있습니다. 그런 일이 이어지거나 경보가 이어지면 명단 방식으로 돌아갑니다([server-runbook.md](server-runbook.md) 7-13). 두 숫자는 사용자가 정합니다.
- 개발 PC처럼 AI 에이전트가 같은 Windows 사용자로 도는 PC는, 다른 내 기기의 '로그인한 기기'에서 그 PC의 계정 키만 로그아웃시켜 두면 들어오는 비밀번호 없는 연결만 받습니다.

### 5-8. 원격 켜기 (2단계)

- 서버나 휴대폰이 보낸 매직 패킷은 꺼진 PC의 네트워크에 닿지 못하므로, 같은 네트워크의 늘 켜진 NAS에서 **hjv-relay**가 대신 보냅니다. NAS에서 여는 포트는 없고, hjv-relay가 HTTPS로 서버에 long-poll(최대 20초)을 걸어 명령을 기다립니다.
- 중계기는 처음 실행할 때 자기 키를 만들고 등록 코드를 보입니다. 관리자가 그 PC 주인의 확인을 받은 뒤 `hjv-api admin relay approve <코드> --owner-of <PC ID>`로 승인합니다. 중계기는 아무 PC의 신뢰 목록에도 없으므로 PC에 연결할 권한이 없고, 켜기 명령만 받습니다.
- 켜기 명령은 TLS와 따로 명령 키로 서명되고(`hjv-wake-v1`, 60초 만료, 받는 중계기 지정), 명령 공개키는 hjv-relay 빌드에만 고정됩니다. 중계기는 자기 랜카드의 브로드캐스트로만, UDP 9·7로만, 3번씩 보내고, MAC은 4개, 분당 명령 10개·패킷 120개까지만 받습니다.
- 묶인 PC는 동기화에 유선 랜카드와 전원 정보를 싣고, 서버가 그 정보로 같은 네트워크의 중계기를 고르고 준비 상태를 판단합니다. 앱에는 MAC을 보내지 않습니다. 켜짐은 hbbs의 `hjv-pk` 등록 나이와 PC의 첫 동기화로 확인하고, 깨어난 PC는 연결이 없어도 10분 동안 다시 잠들지 않습니다.
- 앱에서는 꺼진 내 PC 카드의 "켜기"나 카드를 누를 때의 권유로 켭니다. NAS 설치는 [relay-dsm.md](relay-dsm.md), PC 준비(랜카드, BIOS, 빠른 시작)는 [wol-pc-setup.md](wol-pc-setup.md)에 있습니다.

### 5-9. 기능이 꺼진 빌드

계정 빌드는 `HJV_SERVER`, `HJV_LOGIN_SEAL_PUBKEY`, `HJV_TRUST_PUBKEYS`가 모두 있는 빌드입니다. 하나라도 없으면 로그인도 비밀번호 없는 연결도 없는 1.5.1 동작입니다. 일회용 값은 비고, 증명은 만들지 않고, 동기화 작업은 시작하지 않으므로 선 위의 바이트가 1.5.1과 같습니다. 빌드 변수를 넣는 방법은 [ci.md](ci.md)의 "계정 기능의 공개키"에 있습니다.

### 5-10. PC 연결 창이 보이는 것 (1.9.0)

접속 판정은 바꾸지 않습니다. 아래는 PC 앞 사람이 보는 표시이고, 모두 연결을 받는 프로세스(설치한 PC는 서비스가 띄운 연결 프로세스)가 정해 연결 창 프로세스(`--cm`)에 IPC로 넘깁니다.

- **확인 표시**: IPC `Login`에 `hjv_mark {kind, who}`를 더했습니다. `kind`는 `""`, `same-account`(5-6의 증명이 통과함, `who`는 목록의 가린 주인), `staff`(지원 코드를 넣은 PC에 그 코드를 만든 기기가 연결함, 아래 '교직원 표시', `who`는 빈 값), `unverified-name`(증명이 없고 이름이 표시를 흉내 냄)입니다. 연결 창은 `same-account`와 `staff`에만 방패 표시를 그리고, 이름 글에서는 표시를 읽지 않습니다. 모르는 `kind`는 그리지 않습니다. 한 연결이 2FA로 두 번 알려져도 같은 값이 갑니다(연결이 받아들인 증명을 기억함). 클릭 승인 갈래는 증명보다 먼저 판정하므로(5-6의 6), 클릭 승인만 받는 PC에서는 주인의 기기에도 같은 계정 표시가 없습니다. 표시 줄의 글은 `same-account` '같은 계정 확인됨 · <가린 주인>'(주인이 없으면 '같은 계정 확인됨', 영어 "Same account, verified · <masked owner>"), `staff` '연세대 교직원(로그인 확인)'("Yonsei faculty or staff (verified login)", access-tickets.md 5-3의 P4), `unverified-name` '확인되지 않은 이름'("Unverified name")입니다.
- **교직원 표시**(TV-W6): 지원 코드를 넣은 PC는 hjv-api가 서명한 지원 확인을 메모리에 둡니다(access-tickets.md 3-7). `LoginRequest`의 증명이 그 지원 확인의 계정 키이고 이 연결에 맞으면, 연결을 받는 프로세스가 승인 갈래보다 먼저 이 연결을 교직원 연결로 정하고, 연결 창에 상대가 적은 이름 대신 컨트롤러 ID(`123 456 789` 꼴)와 `staff`를 넘깁니다. 그래서 클릭 승인 갈래에서도 표시가 납니다. 연결 창은 표시 줄에 방패와 '연세대 교직원(로그인 확인)'(P4)을, 수락 단추 위에 P5를 보입니다. 이름 줄이 이미 ID이므로 그 아래 괄호 속 ID 줄은 없습니다. 이름은 보내지 않습니다. 이 표시는 아무것도 열지 않습니다. 비밀번호가 없으면 PC는 수락 단추가 있는 창을 띄우고 컨트롤러는 수락을 기다립니다.
- **흉내 검사**(고정 서버 빌드): 증명 없는 이름을 NFKC로 정규화하고 소문자로 바꾼 뒤 글자와 숫자만 남긴 글(공백, 구두점, 기호, 서식·제어 문자와 빈칸처럼 보이는 한글 채움 문자 U+115F, U+1160, U+3164, U+FFA0을 지움)에 `같은계정`, `sameaccount`, `확인됨`, `verified`, `교직원`, `staff`, `로그인확인`, 그리고 연결 창의 연락처 줄("HJViewer 관리자: …")을 흉내 내는 `hjviewer관리자`, `hjvieweradministrator`가 들어 있으면 `unverified-name`입니다(그냥 `관리자`, `administrator`는 흔한 계정 이름이라 넣지 않음). 그 이름을 연결 창에 넘기기 전에 제어 문자, 방향 제어 문자(U+202A–202E, U+2066–2069), 폭 없는 문자(U+200B–200F, U+2060–2064, U+FEFF, U+180E, U+061C), 한글 채움 문자(U+115F, U+1160, U+3164, U+FFA0)를 지웁니다(로그의 이름은 그대로). 다른 글자로 닮게 쓴 이름(예: 키릴 문자 'а')은 걸러내지 못합니다. 고정하지 않은 빌드는 upstream처럼 이름을 그대로 넘깁니다.
- **주의 줄**: 확인 표시가 없는 연결의 수락 카드와, PC의 이용 비밀번호 창(P2)과 지원 코드 창(P3)에 사칭 주의 한 줄과 관리자 연락처를 보입니다(글은 [access-tickets.md](access-tickets.md) 5-3). 연락처는 버전 정책의 `contact_ko`(8-2)이고, 앱은 `main_get_common("hjv-admin-contact")`로 읽습니다. 코드나 빌드에는 없습니다. 링크로 만들지 않습니다.
- **자리**: 연결 창(300 × 490)의 단추([수락]/[거부], [수락 및 권한 상승], [연결 끊기])와 그 위의 글(주의 상자, P5)과 녹화 줄은 늘 다 보입니다. 자리가 모자라면 권한 판이 줄고 그 안이 스크롤됩니다. 표시 줄은 두 줄까지 접힙니다.
- **녹화 중**: 컨트롤러는 녹화를 켜고 끌 때 이미 `Misc.client_record_status`를 보냅니다. PC는 인증된 연결에서 그 값이 바뀔 때만 IPC `HjvPeerRecording`으로 연결 창에 넘기고, 연결 창은 그 연결의 카드에 '녹화 중'을 보이며, 최소화돼 있었으면 연결 하나에 1분에 한 번까지 다시 띄웁니다. 연결 창은 상대가 녹화하는 동안 3초 뒤의 자동 최소화도 하지 않습니다. 통신 형식은 바뀌지 않습니다. 상대 앱이 알려 준 값이므로, 고친 앱이나 다른 프로그램의 녹화는 보이지 않습니다.
- **숨기기 고정**: 고정 서버 빌드는 `allow-hide-cm`을 `N`으로 고정합니다(설정 파일에 `Y`가 남아 있어도). 그래서 영구 비밀번호만 받는 PC도 연결마다 연결 창을 띄웁니다(6절의 '세션 중 표시').
- 연결 창의 IPC는 같은 Windows 사용자의 다른 프로그램이 흉내 낼 수 있습니다. 그런 프로그램은 이미 그 사용자의 화면과 입력을 가졌으므로, 이 표시는 그런 쪽을 막는 장치가 아닙니다.

### 5-11. 세션이 끝날 때 잠금과 화면 가리기 (1.9.0)

- 같은 계정 증명으로 열린 원격 화면 세션은 '끝나면 잠그기'의 기본이 **자동**입니다. PC가 그 세션을 들일 때 잠겨 있었거나 로그인 화면이었으면 끝날 때 잠그고, 아니면 잠그지 않습니다. 같은 PC에 다른 원격 화면 세션이 남아 있으면 자동은 잠그지 않습니다. 다시 붙어 바뀐 같은 세션의 옛 연결은 다른 세션으로 치지 않습니다(세션의 마지막 연결이 잠급니다, upstream과 같음). 컨트롤러는 내 PC마다 자동·늘·안 함을 고르고 `OptionMessage.hjv_end_lock`(필드 1001: 0 없음, 1 자동, 2 늘, 3 안 함, 4 전환)으로 보냅니다. 이 필드를 한 번 받으면 그 연결에서는 그 값이 이깁니다. 이 필드가 없으면 upstream 필드를 씁니다: `Yes`는 늘, `No`는 안 함, 없으면 같은 계정 세션은 자동, 그 밖은 안 함(upstream 기본). 보기 전용을 켜고 끌 때 컨트롤러가 함께 보내는 upstream `No`는 고른 것으로 치지 않고, 보기 전용을 끌 때의 `Yes`(upstream의 '세션 종료 후 잠금'이 켜짐)는 늘로 칩니다.
- '시작 때 잠김'은 세션 키(컨트롤러 ID와 세션 번호)마다 PC 서비스의 메모리에만 둡니다. 그 세션의 연결이 열려 있는 동안과 마지막 연결이 끝난 뒤 10분 동안 남아, 다시 붙은 연결도 처음 값을 이어받습니다(둘 중 하나라도 잠겨 있었으면 잠김). 끝나면서 PC를 잠갔으면 바로 지웁니다. '같은 계정 세션인가'는 이어받지 않고 늘 그 연결의 새 증명(5-6의 6의 기록)에서 정합니다. PC는 같은 계정 세션의 `PeerInfo.platform_additions`에 `hjv_end_lock: {"v":1,"locked":…}`를 실어 컨트롤러가 닫기 단추에 자물쇠를 보이고 내 PC의 메뉴(자동·늘·안 함, '연결할 때 화면 가리기')를 보이게 합니다.
- 휴대폰이 같은 PC의 파일 전송으로 바꿀 때(TV-W7)는 원격 화면을 닫기 직전에 그 닫기가 전환임을 보내므로(`OptionMessage.hjv_end_lock` 4와 upstream `No`, 저장하지 않음) 그 닫기에서는 잠그지 않습니다. 그 닫기가 잠갔을 잠금은 세션 키의 줄에 남습니다(10분이 지나도). 원격 화면으로 돌아온 세션(휴대폰의 세션 번호는 같음)은 처음 값을 이어받아 끝날 때 스스로 판정하고, 돌아오지 않으면 그 세션의 마지막 연결(파일 전송)이 끝나고 30초 뒤 그 세션의 연결이 없을 때 PC가 잠급니다. 자동이면 그때 다른 컨트롤러의 원격 화면 세션이 있을 때는 잠그지 않습니다. 1.8.x PC는 upstream `No`만 읽어 잠그지 않습니다.
- 잠그는 끝(오류로 끝난 연결은 잠그지 않음), 키보드 권한, 다시 붙은 세션의 예외는 upstream과 같습니다. 서버의 목록에서 빠져 끊긴 원격 화면 세션(5-6의 8)은 늘 잠급니다. 들어오기 전(2단계 인증 코드를 기다리던) 연결은 끊기만 합니다. 잠글 때 PC 로그에 `hjv: end lock: <auto|always|forced>, locked at start <true|false>` 한 줄을 남기고(ID 없음), 전환 뒤에 잠그면 `hjv: end lock: <auto|always> after a switch, locked at start <true|false>`를, 전환의 닫기에서는 `hjv: end lock: <auto|always> owed to a switch, …`를 남깁니다.
- 컨트롤러는 내 PC(PC가 `hjv_end_lock`을 알린 세션)마다 세션 메뉴(데스크톱 '화면' 메뉴의 '끝나면 이 PC 잠그기', 휴대폰 '화면 옵션')에서 자동·늘·안 함을 고르고 PeerConfig의 `hjv-end-lock`에 둡니다. 로그인 때와 고를 때 `hjv_end_lock`과 함께 upstream 필드(늘일 때만 `Yes`)를 보내므로 1.8.x PC는 늘·안 함을 압니다. 남의 PC와 1.8.x PC의 메뉴는 upstream의 '세션 종료 후 잠금'입니다.
- 닫기 단추(데스크톱 도구 막대의 닫기, 휴대폰 아래 막대의 연결 끊기)에는 끝나면 PC를 잠그는 것이 확실할 때만 자물쇠가 붙습니다: 늘, 또는 자동이고 PC가 '시작 때 잠김'을 알렸을 때. 보기 전용이거나 키보드 권한이 없으면 붙지 않습니다. 같은 PC에 다른 원격 화면 세션이 남아 자동이 잠그지 않는 경우는 컨트롤러가 알 수 없습니다. 탭과 창의 ×에는 자물쇠가 없습니다(그래도 같은 규칙으로 잠급니다). 휴대폰의 닫기 확인 창에는 "연결을 끝내면 PC를 잠급니다."가 붙습니다.
- 컨트롤러는 내 PC마다 '연결할 때 화면 가리기'(PeerConfig `hjv-hide-on-connect`, 기본 끔)를 두고, 켜면 첫 화면 뒤에 개인정보 보호 모드를 켭니다. 이 스위치는 그 세션의 상태를 바꾸지 않습니다. 저절로 켜지 못하면 상자 대신 세션에 한 번 토스트를 보이고, 저절로 켜졌을 때 upstream의 '개인정보 보호 모드 켜짐' 상자는 보이지 않습니다. PC가 화면 가리기를 허락하지 않으면 이 스위치는 끄기만 됩니다. 남의 PC에는 이 스위치가 없습니다. upstream이 지난 세션의 상태를 기억해 다시 켜던 동작은 고정 서버 빌드에서 어느 PC에도 쓰지 않습니다.
- 1.8.x 컨트롤러로 1.9 PC에 들어온 같은 계정 세션도 자동으로 잠그되 자물쇠는 보이지 않습니다. 1.9 컨트롤러로 1.8.x PC에 들어가면 늘·안 함만 통하고 메뉴는 upstream의 켜고 끄기입니다.
- 고정 서버 빌드가 아니면 upstream과 똑같이 잠급니다.

### 5-12. 원격 준비 점검 (1.9.0)

- Windows PC(제어 전용 빌드 아님)의 설정 → 계정에 '원격 준비' 카드가 있습니다. 설치하지 않은 PC에는 설치 줄만 보입니다. 설치와 자동 시작, 로그인(출입 확인), 영구 비밀번호와 승인 방식, 전원 연결 때의 절전, 유선 랜카드의 깨우기, 빠른 시작, 같은 망의 켜기 중계기, 조작이 없으면 끊기와 끝나면 잠금을 줄마다 보입니다. 로그인한 PC에 꼭 필요한 줄(설치·자동 시작, 영구 비밀번호와 승인 방식, 절전)이 남으면 PC 홈의 알림 자리에 한 줄(access-tickets.md 5-3의 G4)을 보입니다.
- 값은 그 PC의 앱이 그 PC에서 읽습니다. 서버에 묻는 것은 중계기 하나뿐이고, 이미 있는 `GET /api/hjv/devices/{id}/wol`을 이 PC 자신의 ID로 부릅니다. 새로 서버에 보내는 값은 없습니다.
- HJViewer가 바꾸는 것은 사용자가 [절전 안 함]을 누를 때의 **지금 전원 계획의 '전원 연결 시' 절전·최대 절전 시간**뿐이고, 로그인한 Windows 사용자의 권한으로 바꿉니다(정책이 정했으면 바꾸지 못함). 바꾸기 전 값을 그 사용자의 설정에 두고 [되돌리기]로 되돌립니다. 영구 비밀번호, 승인 방식, 조작이 없으면 끊기는 보안 설정과 같은 잠금 풀기를 거쳐 바꿉니다. 랜카드, BIOS, 빠른 시작은 바꾸지 않고 방법만 보입니다.

## 6. 플랫폼 제약

- **iOS**: 다른 앱에 입력을 주입하는 API가 없어서 **iPhone은 원격 제어할 수 없습니다**. 제어 측 전용입니다. 화면 공유(보기)는 ReplayKit 방송으로만 가능하며 추후 과제입니다.
- **Android**: 1.6.0부터 모든 Android 빌드(사이드로드 APK와 Google Play 빌드 모두)는 **제어 측 전용**입니다(Google Play 작업의 결정 D1). 피제어에 쓰던 접근성 서비스, 화면·소리 캡처 서비스, 오버레이, 부팅 수신기를 빼므로 Android 기기는 원격으로 볼 수 없습니다. 1.5.x까지의 APK는 피제어도 됐습니다(MediaProjection + 접근성 서비스).
- **보이스피싱 악용**: 원격제어 앱은 사기에 악용되는 대표 수단입니다. 국내 금융 앱은 원격제어 앱 실행을 탐지합니다. 스토어 심사와 사용자 신뢰를 위해 접속 수락 UI, 세션 중 표시, 접속 이력 같은 기능을 제품 요구사항에 넣어야 합니다. 1.9.0에서 수락 창의 확인 표시와 사칭 주의 줄, 녹화 표시, 연결 창 숨기기 고정을 넣었습니다(5-10). 1.9.0부터 접속 이력은 PC마다 그 PC 안에만 두는 '들어온 연결' 목록(90일, 설정 → 보안, 설치한 PC만)이 채웁니다. 서버에는 지금처럼 연결마다의 기록을 두지 않습니다([privacy.md](privacy.md) 4절).

## 7. 라이선스·상표

- RustDesk 클라이언트와 서버는 모두 **AGPL-3.0**입니다. 수정한 앱을 배포하거나 수정한 서버를 네트워크로 서비스하면, 해당 사용자에게 **수정본 소스를 제공할 의무**가 있습니다. 저장소가 비공개여도 이 의무는 남습니다.
- hjv-api(`server/api`), hjv-relay(`relay/`), hjv-release(`tools/hjv-release`)는 이 저장소에서 새로 쓴 프로그램이고, 저장소의 다른 부분처럼 AGPL-3.0-only입니다. hjv-api는 `GET /api/hjv/source`로 라이선스와 소스 위치를 알립니다(웹 서버의 `/`는 함께 쓰는 사이트가 쓰므로).
- "RustDesk" 이름과 로고는 쓸 수 없습니다. 앱 이름, 아이콘, Windows 실행 파일 정보, 정보 화면 링크를 HJViewer로 바꿨습니다. Windows 실행 파일은 `HJViewer.exe`이고, Windows의 URL 스킴은 그에 따라 `hjviewer://`입니다. 휴대폰도 1.9부터 `hjviewer://`를 받습니다. upstream과 같은 `rustdesk://`는 1.9.0에서만 함께 받았고 1.9.1에서 뺐습니다. 고정 서버 빌드는 링크에 든 비밀번호를 쓰지 않고, 링크로 여는 연결은 한 번 묻습니다(access-tickets.md 5-3의 LK1).
- 저장소 루트의 `LICENSE`(AGPL-3.0 전문)와 `NOTICE`(upstream 저작권자와 변경 범위)가 고지이고, 내려받는 모든 빌드 결과물에도 라이선스·소스 위치·서드파티 고지 파일이 함께 들어갑니다. TestFlight 빌드에는 앱 정보 화면의 소스 링크만 있습니다.
- 1.6.0부터 앱 안에서 받은 새 버전에는 고지 파일이 붙지 않습니다. 그래서 업데이트 화면과 정보 화면에 그 판의 소스 태그와 이 저장소 주소를 보입니다. 문 2(8-5)는 고지 파일도 패키지 옆에 함께 내줍니다. 문 2의 페이지는 바깥 사이트를 가리키지 않고, 소스 코드(출시 태그)를 받는 곳은 그 알림 파일의 SOURCE에 있다고 말합니다(사용자 요청, 2026-10-14, hjv-api 3b283b2). AGPL 6(d)의 '목적 코드 옆의 분명한 안내'는 그 SOURCE 고지가 맡습니다.
- RustDesk의 프린터 드라이버 어댑터 DLL은 소스가 공개되지 않아 AGPL 배포 조건을 지킬 수 없으므로 Windows 빌드에서 뺐습니다(원격 인쇄 꺼짐). 1.9.0부터 설정에는 프린터 탭과 보안의 '원격 프린터 허용'도 없습니다(U39).

## 8. 최소 버전과 업데이트 (1.6.0)

운영자가 서명한 **버전 정책**으로 플랫폼마다 앱의 최소 버전과 최신 버전을 정하고, 새 버전의 설치 파일을 서버에서 나눠 줍니다. 1.5.1에는 업데이트 기능이 없었습니다. 사용자의 절차는 [distribution.md](distribution.md), 서버 작업은 [server-runbook.md](server-runbook.md), 정책 도구는 [tools/hjv-release/README.md](../tools/hjv-release/README.md), hjv-api의 형식은 [server/api/README.md](../server/api/README.md)의 "Updates"에 있습니다. 앱이 정책을 받아들이는 규칙(8-3)의 기준은 이 저장소의 참조 모델 `tools/hjv-release/tests/vectors/model.py`와 그것으로 만든 시험 벡터(같은 폴더)입니다. 도구의 `tools/hjv-release/src/trust.rs`와 앱의 규칙(클라이언트 패치의 `src/hjviewer_update/trust.rs`)을 같은 벡터로 시험합니다.

### 8-1. 구성

```
개발 PC (사용자)
  hjv-release policy       → 정책 초안 (출처 확인 포함)
  hjv-release sign         → 서명된 정책 (사용자가 키 비밀번호 입력)
  hjv-release publish-dir  → 서버의 incoming/ → 서버 확인 스크립트가 서명과 해시를 다시 봄
                                               → 설치 파일 먼저: /srv/hjviewer-updates/pkg
                                               → 정책 나중:      /etc/hjviewer/version-policy.json

서버 (nginx, rd.example.com, 443)
  GET /api/hjv/version   → nginx가 정책 파일을 그대로 내줌(공개, 로그인 전에도, hjv-api가 멈춰도)
  /api/hjv/update/…      → hjv-api 문 1
  /api/hjv/u/…           → hjv-api 짧은 링크
  /api/hjv/get/…         → hjv-api 문 2
  /api/hjv/s/…           → hjv-api 지원 링크 (1.9.0)
                           (네 길 모두 hjv-api가 확인한 뒤 설치 파일을 직접 보냄, 8-5)
  hbbs                   ← /etc/hjviewer/min-controller.conf (10초마다 다시 읽음)

앱 (1.6.0 이후)
  정책 받기 → 서명 확인 → 판정 → 배너·업데이트 화면, 나가는 연결 막기
  문 1에서 받기 → 크기·SHA-256 확인 → 설치 (Play·iPhone은 스토어·TestFlight, 1.9.1부터 App Store 설치본은 App Store)
```

- 모든 요청은 앱이 이미 쓰는 443(같은 호스트)으로 갑니다. 서버로 443만 열린 방화벽 뒤의 PC도 새 구멍 없이 정책과 설치 파일을 받습니다.
- 정책은 Caddy와 Apache 배치에서는 내주지 않습니다(404). 그런 배치의 앱은 정책을 받지 못해 아무것도 막지 않습니다.

### 8-2. 버전 정책

- 파일은 봉투 하나입니다(JSON 한 줄, 16 KiB 이하). 정책 텍스트 `p`와 그 서명이 들어 있고, 세대가 2 이상이면 루트 선언 `root.p`와 그 서명도 들어 있습니다. 서명하는 바이트는 `hjv-version-v1` NUL `p`와 `hjv-version-root-v1` NUL `root.p`입니다. 5-2의 다른 서명과 섞이지 않습니다.
- 정책 텍스트에는 세대(`epoch`), 세대 안의 순번(`seq`), 발행 시각(`issued`), 서버 이름(앱의 `HJV_SERVER`와 같아야 함), 그리고 항목 `windows`, `android`(파일 설치본), `android_play`(Play 설치본), `ios`가 있습니다. 항목마다 `min`, `latest`, 유예(`grace_until`과 그때까지의 하한 `grace_min`), `os_min`, 안내 글, 소스 태그, Windows·Android의 패키지(파일 이름, 크기, SHA-256), Windows의 무인 설치 시각(`auto_install_after`)이 있습니다. 정책 텍스트의 `contact_ko`(선택, 200자, URL 없음)는 관리자 연락처 한 줄입니다. 앱은 업데이트 화면과, 1.9.0부터 PC의 수락 창·P2·P3의 주의 줄과 정보 화면에 "HJViewer 관리자: <글>"로 보입니다(`main_get_common("hjv-admin-contact")`, 5-10. 연결 창 프로세스도 같은 Windows 사용자의 `HJViewer_update.json`에서 읽음). 정보 화면은 정책에 연락처가 없으면 관리자 줄을 보이지 않습니다(바로 위 줄이 "만든 곳: 프로젝트TF"이고, 만든 곳은 연락할 수 있는 관리자가 아니므로). 앱이나 빌드에는 연락처가 없습니다. 서명된 값이라 서버를 가로챈 쪽도 바꿀 수 없습니다.
- **정책에는 URL이 없습니다.** 앱은 내려받을 주소를 자기 빌드의 서버 이름으로 스스로 만듭니다. 그래서 올바르게 서명된 정책도 사용자를 다른 사이트로 보낼 수 없습니다. 안내 글도 링크로 만들지 않습니다.
- 앱은 서명을 먼저 확인한 뒤 해석하고, 다시 직렬화하지 않습니다. 정책과 설치 파일은 인증서를 확인한 TLS로만 받습니다(인증서 무시 재시도 없음). ETag를 쓰지 않으므로, 서명 없는 304 답으로 기기를 옛 정책에 묶어 둘 수 없습니다.
- 판정은 `ok`(최신), `available`(새 버전, 배너), `grace`(최소 버전 아래, 유예 중), `required`(나가는 연결을 막고 업데이트 화면), `unknown`(정책을 받은 적 없음, 막지 않음)입니다. Android는 설치 출처(`installerStore`)로 `android`와 `android_play` 중 자기 항목을 고릅니다.
- 앱은 각 프로세스의 설정 폴더 `HJViewer_update.json`에 마지막으로 받아들인 봉투와 루트 선언을 두고, 시작할 때마다 그 빌드의 키로 다시 확인합니다. 네트워크를 막아도 이미 아는 최소 버전은 풀리지 않습니다. 정책을 받지 못하면 마지막 정책을 그대로 씁니다.
- 빌드에 박는 값은 공개 저장소 파일 `client/update-keys.env`의 셋입니다: `HJV_UPDATE_PUBKEY`(서명 키, 두 개까지), `HJV_UPDATE_ROOT_PUBKEY`(루트 키, 두 개까지), `HJV_POLICY_FLOOR`(빌드할 때 서버에 있던 정책의 위치. 그보다 오래된 정책은 받지 않음). CI는 이 파일에서만 읽고 시크릿으로는 받지 않습니다([ci.md](ci.md)의 "업데이트 키와 릴리스 기록"). 그래서 빌드 저장소의 권한만으로는 앱이 믿는 키를 바꿀 수 없습니다.

### 8-3. 키와 신뢰 규칙

| 키 | 번호 | 두는 곳 | 하는 일 |
|---|---|---|---|
| 서명 키 1 | 1~100 | 개발 PC에 비밀번호로 암호화해 둠(`~/hjviewer-secrets/`), 오프라인 사본 | 보통의 모든 정책: 새 버전, 최소 버전 올리기, 무인 설치 멈추기 |
| 서명 키 2 | 1~100 | 오프라인 매체 | 다음 교체용. 키 1을 잃거나 도난당했을 때 |
| 루트 키 101, 102 | 101~199 | 각자 다른 비밀번호로, 서로 떨어진 오프라인 매체에 | 루트 선언: 완화(최소 버전 내리기, 유예 늘리기, 항목 빼기), 서명 키 폐기, 새 세대 |

- 키 만들기와 서명은 사용자만 합니다. 도구는 비밀번호를 터미널에서만 받고, 에이전트는 서명하지 않습니다. CI와 운영 서버에는 비밀키가 없습니다. 그래서 서버나 빌드 저장소가 뚫려도 정책을 위조할 수 없습니다.
- 루트 키는 **깨끗한 컴퓨터**에서만 만들고 엽니다. 개발 PC의 시스템, 프로그램, 에이전트가 돌지 않는 컴퓨터입니다(예: 이것만을 위한 라이브 부팅 매체). 도구도 그 컴퓨터에서 공개 저장소의 릴리스 태그로 빌드합니다(개발 PC의 `build/signer/hjv-release`는 서명 키의 서명에만 씀. [ci.md](ci.md)의 "서명하는 hjv-release"). 루트 키의 비밀번호는 개발 PC에서 치지 않습니다. 연습할 때도 같습니다. 그래서 루트 키는 도구가 공개된 뒤(1.6.0의 첫 push 뒤)에 만듭니다([distribution.md](distribution.md)의 "순서").
- 받아들이는 규칙은 다섯 문장으로 줄일 수 있습니다.
  1. 항목은 시간에 따라 무엇을 막는지 말합니다. `grace_until` 전에는 `grace_min` 미만을, 그 뒤에는 `min` 미만을 막습니다. 새 정책은 기기가 지금 기준으로 삼는 것보다 어느 때에도 덜 요구하지 않을 때만 받습니다. 항목마다 보고, PC가 함께 쓰는 Android 두 항목도 함께 봅니다.
  2. 덜 요구하는 것은 루트 **선언**뿐입니다. 선언마다 새 세대를 열고, 폐기한 키와 **기준**(그 세대 첫 정책의 요구 부분)을 담습니다. 도구는 서버에 지금 있는 정책에서만 기준을 만듭니다.
  3. 기기는 선언을 먼저 받고, 같은 봉투의 정책이 어떻게 되든 선언은 지킵니다. 가진 두 서명 부분 가운데 나중 것이 이깁니다. 선언의 세대에 속한 정책을 받기 전까지는 그 선언의 기준을 지키고, 새 정책을 그 기준과 비교합니다.
  4. 루트 키로 서명한 정책에도 특별한 권한은 없습니다. 세대 2부터의 정책은 모두 그 세대의 선언과 함께 옵니다.
  5. 보통의 일은 모두 서명 키로 합니다. 루트 키는 완화, 폐기, 기준 바꾸기를 위해 사고마다 한 번 선언에 서명합니다. 사용 중인 모든 빌드가 박은 서명 키 가운데 쓸 수 있는 것이 없을 때만 정책에도 서명합니다.
- 그래서 서명 키를 훔친 쪽도 키를 폐기하거나, 세대를 올리거나, 덜 요구하는 정책을 낼 수 없습니다. 루트 키가 새 세대와 폐기로 언제든 되찾습니다. 같은 세대 안에서 순번은 1000보다 많이 건너뛸 수 없습니다.
- 앱이 설치하는 것은 지금 세대의 정책으로, 빌드의 하한 이상이고 폐기되지 않은 키로 서명된 것이 가리키는 패키지뿐입니다. 자기 버전 이하로는 아무것도 설치하지 않습니다.
- 정책에는 만료가 없습니다. 만료가 사용자를 가둘 수 있기 때문입니다. 대신 빌드의 하한이 옛 정책의 재전송을 막고, 정보 화면에 발행 시각을 보입니다.
- 운영자의 절차(새 버전, 최소 버전 올리기, 비상 멈춤, 키 도난과 교체, 루트 키 연습)는 [tools/hjv-release/README.md](../tools/hjv-release/README.md)에 있습니다.

### 8-4. 네 겹의 강제

| 겹 | 누가 | 무엇을 보나 | 1.5.x에 닿나 | 보이는 것 |
|---|---|---|---|---|
| 앱 스스로 | 1.6.0 이후 앱 | 자기 버전과 정책 | 아니요 | 배너, 업데이트 화면, 나가는 연결 막힘 |
| PC가 로그인에서 | 1.6.0 이후 PC(연결을 받는 프로세스) | 컨트롤러가 알린 버전과 플랫폼(Windows, Android, iOS만) | 예, IP 직접 연결도 | 컨트롤러에 "로그인 오류"와 문구 |
| 컨트롤러가 PC를 | 1.6.0 이후 컨트롤러 | 연결한 Windows PC의 버전 | 해당 없음 | 알림과 설치 안내뿐, 연결은 그대로 |
| hbbs(패치 0005) | 서버 | 연결 요청의 버전(플랫폼은 모름) | **예. 컨트롤러가 PC에 닿기 전의 유일한 거절이라, 1.5.x PC로 가는 연결에는 이것뿐**(첫 정책을 받은 1.6.x PC는 로그인에서 이미 거절) | "연결 오류"와 문구(링크) |

- hbbs의 기준은 하나입니다. `MIN`은 모든 항목의 `min` 가운데 가장 낮은 값이고, `FROM`부터 거절합니다. 플랫폼별 차이는 앱과 PC가 맡습니다. 값은 `hjv-release hbbs-conf`가 정책에서 만듭니다. 최소 버전을 유예와 함께 올리는 동안에는 새 `FROM`(새 유예 끝)이 될 때까지 지금 파일을 그대로 둡니다. 새 파일을 먼저 넣으면 그때까지 아무도 거절하지 않게 되기 때문입니다. `hbbs-conf`는 그동안 파일을 쓰지 않고 다시 돌릴 시각을 알려 줍니다.
- PC의 Android 기준은 `android`와 `android_play` 중 낮은 쪽입니다. PC는 컨트롤러의 설치 출처를 모르기 때문입니다.
- 거절 문구에는 늘 `version not allowed`가 들어 있습니다. 1.5.1은 이 말이 있어야 자동으로 다시 연결하지 않고, 1.6.0 이후 앱은 이 말로 버전 거절을 알아보고 정책을 바로 다시 받습니다.
- 정책을 받은 적 없는 앱과 PC는 막지 않습니다(실패 개방). 서버 장애가 곧 사용자 잠금이 되면 안 되기 때문입니다. 1.5.x에 대한 확실한 강제는 hbbs와 PC의 거절입니다.
- 버전은 앱이 스스로 알리는 값이라 접근 통제가 아닙니다. 서버 공개키를 가진 upstream RustDesk가 더 높은 번호를 보내면 통과합니다.
- 오래된 PC는 거절하지 않습니다. 사람이 없는 PC를 원격으로 고칠 길을 남기기 위해서입니다. 컨트롤러는 알리기만 하고, 1.6.0 미만 Windows PC에는 로그인한 컨트롤러가 짧은 링크(8-5)를 만들어 줄 수 있습니다.
- 업데이트 공개키가 있는 고정 서버 빌드의 대화 상자는 서버나 상대가 보낸 문구 안의 주소를 링크로 만들지 않습니다. 업데이트 안내는 서명된 정책에 근거한 앱 자신의 화면으로만 합니다.

### 8-5. hjv-api가 설치 파일을 내주는 네 길

설치 파일(Windows exe, Android APK)은 nginx가 아니라 hjv-api가 확인한 뒤 직접 흘려보냅니다. 파일은 `/srv/hjviewer-updates/pkg`(root:hjviewer-api 0750, 파일 0640)에 있어서, nginx와 같은 서버의 웹 사이트(PHP) 사용자는 읽을 수 없습니다. 정책 파일만 nginx가 정적으로 내줍니다.

| 길 | 경로 | 누가 쓰나 | 확인 |
|---|---|---|---|
| 문 1 | `GET /api/hjv/update/{windows,android}/{버전}` | 1.6.0 이후 앱, 설치된 PC의 서비스 | 로그인 토큰과 계정 키 서명(`X-HJV-Proof`), 또는 계정에 묶인 PC의 기기 서명(`hjv-update-v1`, ±600초, 그 PC의 OS 패키지만) |
| 짧은 링크 | `POST /api/hjv/update/{windows,android}/link`로 만들고 `GET /api/hjv/u/XXXX-XXXX`로 받음 | 로그인한 컨트롤러가 원격 PC의 브라우저를 위해, 그리고 Android 7.0 미만 기기가 자기 브라우저를 위해 | 40비트 코드(Crockford base32 8자), 10분, 내려받기 세 번, 계정·플랫폼·버전·파일 이름에 묶임, 메모리에만 |
| 문 2 | `GET /api/hjv/get/{32자리 16진수}/` | 1.5.x 사용자(이행 기간만) | 128비트 비밀 코드(`/etc/hjviewer/door2.conf`에 닫는 시각과 함께) |
| 지원 링크(1.9.0) | `GET /api/hjv/s/<link>/`(페이지)와 `…/<link>/HJViewer-<버전>.exe` | 교직원이 만든 지원 코드를 받은 외부인의 브라우저 | 128비트 값, 그 코드가 열린 동안(최대 10분, 코드를 쓰면 끝남), 내려받기 세 번, 만든 계정에 묶임, 메모리에만([access-tickets.md](access-tickets.md) 3-7) |

- 받을 수 있는 버전은 정책의 그 항목 `latest`뿐입니다. 파일 이름은 요청이 아니라 정책에서 가져오고, 크기가 정책과 같은 보통 파일만 엽니다. hjv-api는 정책의 서명을 확인하지 않습니다. root만 쓰는 파일이고, 앱이 받은 파일의 크기와 SHA-256을 확인하기 때문입니다.
- 내려받는 이름: 문 1은 `HJViewer-<버전>.exe`(설치 화면을 열지 않는 이름)입니다. 짧은 링크는 설치된 PC면 `HJViewer-<버전>-install.exe`, 아니면 `HJViewer-<버전>.exe`입니다. 문 2는 두 이름을 모두 내줍니다. 패커가 자기 파일 이름이 `install.exe`로 끝나면 설치 화면을 열기 때문입니다. 지원 링크는 늘 `HJViewer-<버전>.exe`입니다(설치하지 않고 실행).
- 한도: 동시에 4개(`HJV_API_DOWNLOADS_MAX`, 넘으면 503과 `Retry-After: 60`), 계정이나 PC마다 하루 10번(`HJV_API_LIMIT_UPDATE`), 짧은 링크는 계정마다 하루 20개, 인증이나 코드가 틀린 요청은 주소마다 하루 30번(`HJV_API_LIMIT_UPDATE_FAIL_IP`)입니다. 지원 링크는 코드마다 세 번이고, 지원 링크의 404는 이 실패로 세지 않습니다(128비트 값은 맞힐 수 없음). 올바른 토큰, 서명, 코드가 있는 요청은 주소 때문에 거절하지 않습니다. 같은 공인 주소 뒤의 정상 사용자를 막지 않기 위해서입니다. 속도는 초당 3,840,000바이트(중계 세션의 상한과 같음)입니다.
- 기록: 내려받기와 링크마다 hjv-api의 기록에 꼬리표(계정, PC, 주소)로만 남깁니다. 코드는 저장하지 않습니다. nginx는 `/api/` 아래의 접속 기록을 남기지 않고, 짧은 링크, 문 2, 지원 링크의 경로는 오류 기록도 남기지 않습니다. 지원 링크의 내려받기는 `update` 기록의 `support-windows`(만든 계정의 꼬리표)입니다. 자세한 것은 [privacy.md](privacy.md) 2절에 있습니다.
- 브라우저로 받는 길(짧은 링크, 문 2, 지원 링크, Android 7.0 미만)은 서명된 해시를 거치지 않습니다. 그래서 운영 에이전트가 서버에 넣기 전에 서명과 해시를 대조하고, 공개 저장소 태그의 메모에 SHA-256을 적고, 문 2는 짧게 열고, 원격 설치는 HJViewer 파일 전송을 먼저 권합니다.

### 8-6. 기기마다 받는 길

| 기기 | 받는 길 | 확인 |
|---|---|---|
| 설치된 Windows PC | 서비스(SYSTEM)가 문 1에서 기기 서명으로 받아 새 exe를 `--update`로 실행. 정책의 무인 설치 시각부터 고리(0~2일)와 퍼짐(하루 안)에 따라, 연결이 없을 때. 최소 버전 아래면 기한 뒤, 24시간 쉬지 못하면 새벽 2~5시에 10분 알림 뒤. 주 창의 [지금 업데이트]는 서비스에 신호만 보냄(UAC 없음) | 서명된 크기와 SHA-256. SYSTEM과 관리자만 쓰는 보호된 폴더와, 확인부터 실행까지 쓰기·삭제를 막은 핸들. 설치 직전 30분 안에 서버가 정책을 확인해 준 때만(사람이 누른 때는 빼고) |
| 설치하지 않은 Windows 실행본 | 앱이 문 1에서 토큰으로 받아 '다운로드'에 두고, 사용자가 [지금 실행] | 서명된 크기와 SHA-256, 실행 직전에 다시 해시 |
| Android 파일 설치본 | 앱이 문 1에서 토큰으로 받아 시스템 설치기에 넘김 | 서명된 크기와 SHA-256, 패키지 이름, 서명 인증서(휴대폰 안). 그다음 Android의 같은 서명 키와 더 높은 versionCode |
| Android Play 설치본 | Play 스토어 | Play 앱 서명. 정책은 버전만 말함 |
| iPhone | TestFlight 앱(1.9.1부터 App Store에서 설치한 앱은 App Store) | Apple 서명. 정책은 버전만 말함. 두 설치본이 정책의 `ios` 항목 하나를 함께 씀(App Store 배포를 시작하면 App Store에 나온 버전으로만 올림, 런북 8-2) |

- 설치된 PC의 무인 설치는 1.6.0에 들어 있습니다. 1.5.1 PC는 1.6.1을 손으로 설치하므로, 모두에게 처음 쓰이는 것은 1.6.1 다음 버전입니다. 최소 버전(1.6.1) 아래인 1.6.0 시험 설치본 PC는 첫 정책을 받으면 1.6.1을 강제로 설치합니다. Windows에는 되돌리기가 없어서 고리로 나눠 내고, 문제가 보이면 운영자가 정책으로 멈춥니다. 무인 설치 시각을 지우고, 최소 버전 아래 PC의 강제 설치까지 멈추려면 그 패키지를 거둡니다.
- `--update`는 설치 때의 상태(서비스 인자, 바로 가기, 방화벽 규칙)를 옮기지 않습니다. 새 판에 그런 변화가 있으면 그 판의 업데이트 코드에 넣어야 합니다.
- upstream의 업데이트 확인과 자동 설치는 고정 서버 빌드에서 봉인합니다. `--update`가 읽는 맞춤 설정 파일(`custom.txt`) 단계도 건너뜁니다.
- 새 패커는 풀어 쓸 파일 하나라도 쓰지 못하면(옛 HJViewer가 실행 중) 아무것도 실행하지 않고 안내 창을 띄웁니다. 옛 파일과 새 파일이 섞여 실행되지 않게 하려는 것입니다. 사람 없이 실행된 패커(`--update`)는 창 없이 끝납니다.
- 새 패커는 개인정보 보호 모드의 RuntimeBroker를 복사하기 전에 그 프로세스를 끄는 `taskkill`을 Windows 시스템 폴더(`GetSystemDirectoryW`)에서 실행합니다(클라이언트 패치 0046). upstream처럼 이름만 주면 패커가 있는 폴더를 먼저 찾는데, 설치하지 않은 실행본은 새 버전을 '다운로드'에서 실행하고, 웹 페이지는 그 폴더에 묻지 않고 파일을 둘 수 있기 때문입니다.

### 8-7. 기능이 꺼진 빌드

- 업데이트 공개키나 `HJV_SERVER`가 없는 빌드는 정책을 확인하지 않습니다. 업데이트 화면, 배너, 최소 버전 강제가 없고, 대화 상자의 링크도 1.5.1처럼 그대로입니다.
- 패커 보호(8-6의 마지막 두 항목)만은 `HJV_SERVER`가 있는 고정 서버 빌드면 업데이트 공개키와 상관없이 켜집니다. 키 없는 고정 서버 빌드도 옛 HJViewer가 실행 중이면 새 파일을 풀지 않고 안내 창을 띄웁니다.
- 키 하나라도 규칙(번호, 형식, 약한 키, 겹침)을 어기면 그 빌드는 키 전체를 쓰지 않고 꺼집니다. 그래서 CI가 출시 빌드의 키 파일을 엄격히 확인합니다.
- E2E 빌드(`hjv-e2e`)는 시험 서버 이름 `hjv.test`와 이 저장소의 시험 키일 때만 켜집니다. 출시 빌드에 시험 키가 있으면 CI가 실패합니다.
- 버전을 찍지 않은 로컬 빌드는 1.5.0을 알립니다. 운영 서버가 강제를 시작하면 거절되므로, 개발에는 로컬 서버나 `scripts/set-client-version.sh`로 버전을 찍은 빌드를 씁니다.

## 9. 교직원 전용 출입 제한 (1.8.0)

1.8.0부터 HJViewer는 연세대학교 교직원용입니다. 연세포탈로 로그인한 사람은 쓰고, 로그인하지 않은 사람은 운영자가 정한 **이용 비밀번호**를 아는 경우에만 그때그때 씁니다. 1.9.0부터는 로그인한 교직원이 만든 **지원 코드**로도 로그인하지 않은 PC 하나가 2시간 동안 연결을 받습니다. 연결을 거는 쪽(컨트롤러)과 서버에 등록하는 PC를 모두 확인합니다. 형식과 판정의 기준은 [access-tickets.md](access-tickets.md)(계약)입니다. 서버 작업은 [server-runbook.md](server-runbook.md) 9절, 사용자 안내는 [distribution.md](distribution.md)의 "1.8.0: 교직원 전용"에 있습니다.

### 9-1. 구성

```
hjv-api (출입증 키: 자격 증명 hjviewer-api-ticket-key, 사용자가 서버에서 만듦)
  로그인 답의 hjv.access, POST /api/hjv/ticket → 교직원 출입증 (24시간, 휴대폰 ctl, Windows 앱 both)
  POST /api/hjv/pc/sync의 access              → 묶인 PC 출입증 (72시간, both)
  POST /api/hjv/guest (이용 비밀번호)          → PC 하나의 출입증 (12시간, 컨트롤러 ctl, PC pc)
  POST /api/hjv/support-code (교직원의 앱)     → 지원 코드 (10분, 한 번; 메모리에만) + 지원 링크·대기 번호
  GET  /api/hjv/support-code/wait              → 그 기기가 만든 코드를 넣은 PC의 ID·키 (최대 20초 잡음)
  POST /api/hjv/guest의 code (지원 코드)       → 그 PC 하나의 출입증 (2시간, pc) + 지원 확인(목록 키), 1.9.0부터
  GET  /api/hjv/s/<link>/                      → 지원 링크 페이지와 HJViewer.exe (1.9.0)
  심사 계정 (review.conf의 PC=)                → 데모 PC에만 닿는 ctl (24시간, UNTIL까지)

앱 (1.8.0)
  출입증을 읽지 않고 그대로 실음 → PunchHoleRequest.token, RequestRelay.token, RegisterPk 필드 1001

hbbs (서버 패치 0006~0008, /etc/hjviewer/access.conf: MODE, KEY, NOT_BEFORE, TEXT)
  공개키로 서명을 오프라인 확인 → 거절은 "access not allowed" (1.8.0은 자기 글로 바꿔 보임)
```

- 출입증은 `t1.<kid>.<본문>.<서명>`이고, 본문은 가진 쪽(`staff`, `review`, `guest`), 쓸 자리(`ctl`은 연결과 중계 요청, `pc`는 등록, `both`는 셋 다), 계정 꼬리표, 등록할 PC의 ID와 키, 닿는 PC(`to`), 만든 때와 끝나는 때입니다(계약 2절).
- hbbs는 공개키만 가지므로 확인만 하고 출입증을 만들지 못합니다. 앱 빌드에는 출입증 키가 없어서, 키를 바꾸거나 형식을 고쳐도 앱을 다시 빌드하지 않습니다.
- 출입증은 서버를 쓸 자격일 뿐입니다. PC 안으로 들어가는 것은 지금처럼 PC 비밀번호, 수락 창, 같은 계정의 증명(5-6)이 정합니다.
- hjv-api가 멈춰도 가진 출입증은 끝날 때까지 쓰입니다. 그래서 교직원과 묶인 PC는 hjv-api의 짧은 장애에 연결이 끊기지 않습니다.

### 9-2. MODE

| `MODE` | hbbs가 하는 일 | 앱에 보이는 것 |
|---|---|---|
| `off`(옵션이 없을 때도) | 확인하지 않음. 0006 전과 같음 | 1.7.0까지와 같음 |
| `count` | 거절하지 않고 판정을 이유별로 셈(콘솔 `hjv-access`) | 1.7.0까지와 같음 |
| `enforce` | 출입증이 없거나 맞지 않는 연결 요청·중계 요청·등록을 거절하고, 출입증이 끝난 등록을 끊음 | 컨트롤러: A1(로그인, 이용 비밀번호) 또는 A2, 로그인하지 않은 앱의 연결 화면에 G3, 꺼졌거나 받아들여지지 않은 PC에는 교직원 전용 서버의 오프라인 글. PC: 홈과 빠른 지원 창의 P1([로그인], [이용 비밀번호 넣기], 지원 코드를 받는 hjv-api면 [지원 코드 넣기]), 상태 줄과 트레이(Windows)의 "서버에 연결되지 않음" |

- 파일이 없거나 고장 나면 닫힘(모두 거절)입니다. 출입 통제이므로 파일을 지워도 열리지 않고, 끄는 길은 `MODE=off`입니다(계약 6-3). 바꾸면 10초 안에 듣고 재시작이 필요 없습니다.
- 1.8.0의 앱은 서버가 거절할 때만 묻습니다. 그래서 `MODE=off`인 서버에서는 1.7.0까지와 같고, 1.8.0을 먼저 퍼뜨린 뒤 `enforce`로 바꿀 수 있습니다(출시일 순서는 [server-runbook.md](server-runbook.md) 9-6). 다른 점은 설치했지만 로그인하지 않은 Windows PC의 홈에 로그인 안내(G2)가 모드와 상관없이 보이는 것 하나입니다.
- 앱은 `GET /api/hjv/access`(토큰 없음, 계약 3-6)로 지금 모드를 알아 둡니다. hjv-api가 hbbs 콘솔의 `hjv-access`에서 모드만 옮기고(30초 묶음), 개수는 옮기지 않습니다. 앱은 이것을 안내에만 씁니다: `enforce`와 닫힘이면 G3과, 로그아웃과 "내 PC에서 빼기", 다른 기기 로그아웃의 확인 창에 "누군가 그 PC에서 다시 로그인할 때까지 원격으로 연결할 수 없다"는 줄(L1, L2, L3)을, 오프라인과 원격 다시 시작에 교직원 전용 서버의 글을 보이고, 모르면 그 줄을 조건으로 보입니다. 지원 코드를 아는 hjv-api(1.9.0과 함께 내는 것)의 답에는 지금 지원 코드를 출입증으로 바꿔 주는지(`codes`, `count`나 `enforce`이고 출입증 키가 있을 때)도 있고, PC는 그때만 P1에 [지원 코드 넣기]를 보입니다. 판정은 언제나 hbbs가 합니다.

### 9-3. 앱

- **컨트롤러**: 그 대상의 이용 비밀번호 출입증, 없으면 로그인의 출입증을 `Client::start` 한 곳에서 싣습니다. 그래서 다시 연결할 때마다, 포트 포워딩의 로컬 연결마다 그때의 출입증을 씁니다. 로그인한 앱은 거절되면 출입증을 한 번 새로 받아 다시 해 보고, 그래도 거절되면 A2([닫기] [다시 연결])를 보입니다. 로그인하지 않은 앱은 A1 창("교직원 전용 서버")에서 [로그인]을 고르거나, "이용 비밀번호가 있나요?"를 눌러 이용 비밀번호를 넣습니다.
- **PC**: 묶인 PC의 출입증, 이용 비밀번호나 지원 코드의 PC 출입증, 설치하지 않은 실행본의 로그인 출입증 가운데 쓸 수 있는 첫 것을 `RegisterPk`에 싣습니다. 등록이 거절된 동안(`NOT_DEPLOYED`) 홈과 빠른 지원 창의 ID 위에 P1을 보이고(로그인한 PC는 거절이 약 60초 이어진 뒤 계정 카드의 까닭으로), 그동안 ID를 흐리게 해 그 ID로 연결할 수 없다고 알리고, 상태 줄과 Windows의 트레이 안내도 "서버에 연결되지 않음"으로 바꾸고, 출입증이 오면 30초를 기다리지 않고 다시 등록합니다. 설치된 PC는 창 없이 트레이로만 도는 일이 많아서 트레이 안내도 바꾸고, 1.9.0부터 트레이 아이콘에 주황 점을 붙이고, 메뉴에 [로그인…]·[이용 비밀번호 넣기…]를 두고, 거절이 60초 이어지면 Windows 알림을 한 번 보입니다(access-tickets.md 5-3의 TR1–TR3). 거절된 PC는 1.9.0부터 20초마다 다시 등록합니다(access-tickets.md 3-3).
- **이용 비밀번호**: 앱은 기억하지 않습니다. 봉인해 `POST /api/hjv/guest`로 보내 PC 하나의 출입증으로 바꾸고 바로 버립니다. 컨트롤러의 출입증은 그 대상으로 가는 마지막 세션이 닫힐 때까지 메모리에, PC의 출입증은 IPC로 넘긴 등록 프로세스(설치한 PC는 서비스)의 메모리에 둡니다. PC의 홈은 끝나는 시각과 [끝내기]를 보이고, [끝내기]는 IPC의 빈 값으로 등록 프로세스에서 그 출입증을 지웁니다. 설치한 PC는 PC를 다시 시작하거나 서비스가 서버 프로세스를 새로 띄울 때(Windows 로그아웃·사용자 전환, 업데이트)도 그 출입증을 잃습니다. 그래서 사람이 없을 때도 연결받으려면 PC를 계정에 묶어 둡니다(로그인해 둠). 앱의 설정과 설치 화면(G1), 그리고 설치했지만 로그인하지 않은 Windows PC의 홈(G2, 홈을 처음 열 때 로그인 창을 한 번 엶)이 이것을 알립니다.
- **잠기지 않게**: 묶인 PC에서 로그아웃하거나 그 PC를 내 PC 목록에서 빼면 묶인 PC 출입증이 없어지고, `enforce`에서는 누군가 그 PC에서 다시 로그인할 때까지 오프라인입니다. 그래서 그 확인 창이 서버 모드에 맞춰 이것을 알리고, 그 PC를 지금 누가 원격으로 보고 있으면 "로그아웃할 때 비밀번호 없는 연결은 끊기고, 다른 연결도 끝난 뒤에는 다시 들어올 수 없다"는 줄을 더합니다(1.9.0, 5-6의 8번).
- **휴대폰**은 등록하지 않으므로 컨트롤러 쪽(A1, A2, G3)과, 교직원의 로그인이면 지원 코드를 만드는 쪽(S1, S2)만 있습니다.
- 계정 기능이 없는 빌드는 아무것도 싣지 않습니다. 연결 요청의 token은 지금과 같고, `RegisterPk`는 1.7.0과 바이트까지 같습니다.

### 9-4. hjv-api

- 출입증 키는 hjv-api의 자격 증명에만 있습니다. `selfcheck`가 그 공개키를 `HJV_API_TICKET_PUBKEYS`(곧 hbbs의 `KEY=`)와 대조하고, 공개된 시험 키가 있으면 실패로 합니다.
- 이용 비밀번호는 `/etc/hjviewer/guest.conf`(`HJV_API_GUEST_FILE`)에 PBKDF2 해시와 끝나는 때(`UNTIL`, 90일까지)로 있습니다. 사용자가 자기 터미널에서 `deploy/guest-conf.py`로 만들고, 바뀌면 hjv-api가 다시 읽습니다. 틀린 비밀번호와 받지 않는 상태는 같은 401과 같은 지연입니다.
- 한도: 주소마다 실패 10분에 5번·하루 20번, 모든 시도 시간당 60번(주소 하나는 그 4분의 1까지), 주소마다 출입증 하루 50개. 해시 계산은 한도 뒤, 동시에 둘까지입니다.
- 지원 코드(1.9.0, 계약 3-7): 로그인한 교직원의 앱이 `POST /api/hjv/support-code`로 만들고, 로그인하지 않은 PC가 `POST /api/hjv/guest`에 이용 비밀번호 대신 실어 그 PC의 2시간짜리 `guest`/`pc` 출입증으로 바꿉니다. 코드는 hjv-api의 메모리에만, 키를 쓴 해시로 찾게 최대 20분 있고, 다시 시작하면 모두 끝납니다. 1.9.0부터는 지원 링크(이것도 키를 쓴 해시로 찾음)와 대기 번호(그대로)도 함께 두고, 지원 링크의 페이지를 위해 코드 자체도 열린 동안만(최대 10분) 둡니다. 시도는 이용 비밀번호의 한도에 함께 세고, `guest.conf`는 보지 않습니다. 만든 계정이 막히거나 그 코드를 만든 기기의 계정 키가 끝나면(로그아웃, revoke) 코드도 끝납니다.
- 출입증 값과 지원 코드는 저장하지도 기록하지도 않습니다. 이용 비밀번호의 시도는 결과, 시각, 주소의 꼬리표로, 지원 코드는 만들 때마다 만든 계정의 꼬리표로, 바꾸려는 시도마다 결과, 시각, 주소의 꼬리표와 (찾았으면) 만든 계정의 꼬리표로 6개월 기록합니다([privacy.md](privacy.md) 3절).

### 9-5. 보장하는 것과 하지 않는 것

- **보장**: 출입 확인을 켠 서버에서는 교직원(로그인), 교직원 계정에 묶인 PC, 이용 비밀번호를 넣은 쪽, 교직원이 만든 지원 코드를 넣은 PC(1.9.0부터, 2시간), 심사 계정(데모 PC만)만 연결을 걸고 PC로 등록합니다. 이용 비밀번호 한 번은 그때 연결하는 PC 하나에만, 지원 코드 하나는 먼저 넣은 PC 하나에만 닿습니다.
- **하지 않는 것**
  - 출입증은 무기명입니다. 복사한 출입증은 수명 동안 쓰입니다. 그래서 앱은 서버로 가는 wss로만 보내고, 고정 서버 빌드는 안전하지 않은 TLS 대체를 끕니다. 끊어야 하면 `NOT_BEFORE`를 씁니다(계약 6-4).
  - hbbr은 확인하지 않습니다. 중계 요청은 hbbs가 확인하지만, 중계 서버에 직접 붙는 쪽은 막지 않습니다(지금과 같음).
  - upstream의 uuid 신뢰 방식: 오프라인 ID의 키는 그 uuid와 마지막 주소를 아는 쪽이 바꿀 수 있습니다.
  - 이용 비밀번호는 아는 사람 누구나 씁니다. 퍼지면 `guest.conf`를 바꾸고, 이미 나간 출입증까지 끊으려면 `NOT_BEFORE`를 함께 씁니다.
  - 지원 코드도 무기명입니다. 10분 안에 코드를 먼저 넣은 PC 하나가 씁니다. 코드를 만든 계정을 막으면 그 계정의 열린 코드가 끝나고, 이미 바꾼 출입증까지 끊으려면 `NOT_BEFORE`입니다. `guest.conf`를 지워도 지원 코드는 그대로 됩니다.
- 고정 서버 빌드는 직접 IP 접속, LAN 검색, 안전하지 않은 TLS 대체를 끈 채로 고정합니다. 직접 IP 접속은 hbbs를 거치지 않아 출입 확인도 거치지 않고, LAN 검색은 같은 망의 누구에게나 ID와 이름을 알려 주기 때문입니다. 1.9.0부터 설정은 세 줄을 보이지 않고 '발견됨' 탭도 없으며, 연결 상자의 ⓘ는 PC의 ID만 말합니다(U37).
- 교직원이 만드는 일회용 코드는 1.9.0의 지원 코드입니다(10분, 한 번, PC 하나, 출입증 2시간; 계약 3-7).
