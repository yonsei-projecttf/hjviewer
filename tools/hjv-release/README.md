# hjv-release

HJViewer의 **서명된 버전 정책**(최소 버전과 강제 업데이트)을 만들고, 서명하고, 확인하는 운영자 도구입니다. 앱은 `https://<서버>/api/hjv/version`에서 이 정책을 받아, 빌드에 박힌 공개키로 서명을 확인한 뒤에만 따릅니다.

- 에이전트가 하는 일: 정책 초안 만들기(`policy`), 확인(`verify`), 서버로 보낼 디렉터리 모으기(`publish-dir`), 서버 설정 값(`hbbs-conf`, `floor`), 주 1회 점검(`check`).
- **사용자만 하는 일: 키 만들기(`keygen`), 서명(`sign`), 보관소의 파일 무효(`void`)와 들이기(`archive adopt`).** 이 명령은 터미널에서 키 비밀번호나 `yes`를 받습니다. 터미널이 없으면(스크립트, CI, 에이전트의 셸) 실행을 거부합니다. 비밀번호는 표준 입력, 환경 변수, 인자로 받지 않습니다.
- 앱이 정책을 받는 규칙(1.6.0의 신뢰 규칙)은 이 저장소의 참조 모델 `tests/vectors/model.py`와 그 시험 벡터(`tests/vectors/`)가 정합니다. 도구의 `src/trust.rs`가 같은 단계와 거절 코드로 그 규칙을 따르고, 서명하기 전에 앱이 받을지 확인합니다.
- 이 도구는 비밀키, 비밀번호, 문 2 코드를 화면·로그·오류에 쓰지 않습니다.

이 문서의 예시는 서버 이름을 `rd.example.com`으로 씁니다.

## 빌드

```sh
cd tools/hjv-release
cargo build --release --locked        # target/release/hjv-release
cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test --locked
```

명령은 저장소 맨 위에서 실행합니다. `--keys`를 주지 않으면 `client/update-keys.env`를 읽습니다. `hjv-release help`가 모든 명령과 옵션을 보여 줍니다.

종료 코드: 0 성공, 1 거부나 오류, 2 모르는 명령, 3 `check`의 경고.

## 1. 키 (한 번, 사용자만)

키는 넷입니다. 앱 빌드에는 네 공개키가 모두 들어갑니다. **서명 키의 번호는 1-100, 루트 키의 번호는 101-199입니다.** `keygen`, `keys --production`, CI의 키 확인이 다른 번호를 거부합니다. 그래서 루트 키의 번호가 폐기될 수 있는 서명 키 번호와 섞이지 않습니다.

| 키 | 번호 | 쓰는 곳 | 두는 곳 |
|---|---|---|---|
| 서명 키 1 | 1 | 릴리스마다 정책 서명 | 개발 PC `~/hjviewer-secrets/hjviewer-update-1.key` + 오프라인 사본 |
| 서명 키 2 | 2 | 다음 교체용, 키 1이 새면 대신 서명 | 오프라인 매체에만 |
| 루트 키 | 101 | 루트 선언: 완화, 키 폐기, 새 세대 | 오프라인 매체에만. 비밀번호 따로 |
| 루트 키 | 102 | 101과 같음(하나를 잃어도 새 빌드 하나로 끝나게) | 101과 다른 오프라인 매체에, 따로 보관. 비밀번호 따로 |

```sh
hjv-release keygen --role signing --id 1   --out ~/hjviewer-secrets/hjviewer-update-1.key
hjv-release keygen --role signing --id 2   --out /media/usb1/hjviewer-update-2.key
hjv-release keygen --role root    --id 101 --out /media/usb1/hjviewer-update-root-101.key   # 깨끗한 컴퓨터에서
hjv-release keygen --role root    --id 102 --out /media/usb2/hjviewer-update-root-102.key   # 깨끗한 컴퓨터에서
```

- 비밀번호를 두 번 묻습니다(12자 이상). **비밀번호를 잊으면 그 키는 다시 쓸 수 없습니다.** 두 루트 키는 서로 다른 비밀번호로 만듭니다.
- 키 파일은 비밀번호로 암호화한 파일입니다(권한 0600). 이미 있는 파일은 덮어쓰지 않습니다.
- 표준 출력에는 공개 줄 `N:<base64>` 한 줄만 나옵니다. 이 줄을 `client/update-keys.env`에 넣습니다.

```sh
# client/update-keys.env (공개 파일. 앱 빌드가 읽음)
HJV_UPDATE_PUBKEY=1:<서명 키 1의 공개 줄 값>,2:<서명 키 2의 공개 줄 값>
HJV_UPDATE_ROOT_PUBKEY=101:<루트 키 101의 공개 줄 값>,102:<루트 키 102의 공개 줄 값>
HJV_POLICY_FLOOR=1:0
```

- 공개 줄을 다시 보려면 `hjv-release pubkey --key FILE`(비밀번호 필요).
- 키 파일을 확인하려면 `hjv-release keys --production`. 형식이 틀리거나, 비어 있거나, 번호가 범위 밖이거나, 이 저장소의 시험 키가 들어 있으면 실패합니다. 약한 키와 주 부분군 밖의 점도 거부합니다. `--policy <서버의 정책>`을 주면 그 정책의 루트 선언이 폐기한 서명 키를 박고 있는지도 봅니다(X6).
- 키 집합의 이름은 지문(서버, 번호 순서로 쓴 서명 키 줄, 번호 순서로 쓴 루트 키 줄의 SHA-256)입니다: `keys --server rd.example.com`이 출력합니다.

### 보관소(아카이브)

`~/hjviewer-policy-archive`(다른 곳이면 `--archive DIR`)에 `sign`이 쓴 파일이 모두 있습니다. 도구는 새 정책과 선언을 늘 이 보관소와 견줍니다.

| 파일 | 쓰는 명령 |
|---|---|
| `policy-e<세대>-s<seq>.json` | `sign`이 쓴 봉투 그대로(`archive adopt`로 들인 것 포함) |
| `declaration-e<세대>.json` | `sign`이 서명한 루트 선언의 root 부분 `{k, p, s}` |
| `void-e<세대>-s<seq>` | `void`: 그 정책은 컴퓨터 밖으로 나가지 않았음 |
| `keyset-<지문 16자리>.env` | 기록된 키 집합: 빌드가 박은 두 키 줄과 `# versions: 1.6.0 1.6.1 …`. 처음 `sign`, `floor --live`, `archive adopt --keys`가 씀 |

- **보관소에는 `sign`, `floor --live`, `void`, `archive adopt`만 씁니다.** `policy`와 `verify`는 읽기만 합니다. 저장소 안(특히 에이전트가 worktree를 만들고 지우는 `build/`)에는 두지 않습니다. 시험 키의 키 파일로는 기본 보관소를 쓰지 않습니다: 쓰는 명령은 `--archive`를 직접 줘야 하고, 읽는 명령(`policy`, `verify`, `check`)은 `--archive`가 없으면 빈 보관소로 읽습니다.
- **서명한 파일은 `void`하지 않는 한 낸 것으로 칩니다.** 낼 것이 아니면 서명하지 않습니다.
- `sign` 뒤에는 보관소를 서명 키의 오프라인 매체에 복사합니다. 깨끗한 컴퓨터(3장 5-0)는 그 사본으로 일하고, 거기서 생긴 파일은 다시 개발 PC의 보관소로 옮깁니다.
- 지우는 것은 키 집합 기록뿐이고, 운영자가 손으로 지웁니다: 관리자 보고(`hjv-api admin report`)에 그 키 집합으로 만든 빌드의 기기가 하나도 없을 때만(3장 5-9).

## 2. 릴리스마다

1. (에이전트) `client/version.env`를 올리고, `HJV_POLICY_FLOOR`를 **서버에 걸린 정책**의 위치로 바꿉니다: `curl -s https://<서버>/api/hjv/version -o /tmp/live.json` 뒤 `hjv-release floor --live /tmp/live.json`이 그 줄을 출력합니다. 보관소에 있는 파일만 받고, 이 빌드의 키 집합(과 버전)을 보관소에 기록합니다. push하고 빌드 저장소에서 빌드합니다.
2. (에이전트) 산출물을 `build/release-<버전>/`에 받습니다(`gh run download <실행 번호> -R <빌드 저장소> -D build/release-<버전>`). 산출물 디렉터리마다 `release.json`이 있어야 합니다(아래 "출처 확인"). 검토하고 올린 커밋에 태그 `client-<버전>`을 만듭니다.
3. (에이전트) 초안을 만듭니다. `--prev`는 보관소의 마지막 파일입니다(X11). **새 패키지가 든 초안은 빌드한 지 7일 안에 만듭니다.** `policy`가 그 실행의 산출물을 GitHub에서 직접 받아 패키지와 대조하는데, 산출물은 7일 뒤 지워집니다.

   ```sh
   hjv-release policy --prev ~/hjviewer-policy-archive/policy-e1-s7.json \
       --release-dir build/release-1.6.1 \
       --auto-after windows=+2d --notes build/release-1.6.1/notes.txt \
       --ios-valid 263120249 \
       --out build/policy/draft-8.json
   ```

4. **(사용자)** 터미널에서 서명합니다. 도구가 바뀌는 내용을 보여 주고 키 비밀번호를 묻습니다. 요약의 "새 패키지" 줄에 나온 SHA-256을 GitHub의 빌드 실행 요약에 적힌 값과 눈으로 대조합니다. `sign`은 빌드도 네트워크도 보지 않으므로, 초안에 적힌 해시가 그 빌드의 것인지는 이 대조가 마지막 확인입니다.

   ```sh
   hjv-release sign --key ~/hjviewer-secrets/hjviewer-update-1.key \
       --out build/policy/version-policy-8.json build/policy/draft-8.json
   ```

   `sign`은 봉투와 새 선언을 보관소에 넣고 그 파일 이름을 출력합니다. 보관소를 서명 키의 오프라인 매체에 복사합니다.

5. (에이전트) 확인하고, 서명된 정책을 보낼 디렉터리에 넣습니다.

   ```sh
   hjv-release verify --server rd.example.com \
       --prev ~/hjviewer-policy-archive/policy-e1-s7.json build/policy/version-policy-8.json
   hjv-release publish-dir --policy build/policy/version-policy-8.json \
       --release-dir build/release-1.6.1 --out build/publish-1.6.1
   ```

6. 사용자가 승인하면 `build/publish-1.6.1/`을 서버의 자기 홈으로 보내고, 허브-운영에게 런북 8-2의 네 값을 알려 줍니다: 버전, 위치(`policy-e<세대>-s<seq>.json`의 `e<세대>-s<seq>`), 정책 파일의 SHA-256(`sign`이 출력), `--relaxes`(보통 없음). `incoming/`은 root:root 0700이라 바로 보낼 수 없고, 허브-운영이 홈의 디렉터리를 `incoming/<버전>-<위치>`로 옮깁니다. 서버에서는 서명과 해시를 다시 확인한 뒤 **패키지를 먼저, 정책을 나중에** 넣습니다(`docs/server-runbook.md` 8-2). 서버 확인에 `--relaxes`는 루트 선언으로 일부러 완화할 때만 줍니다(`sign`이 목록을 출력).

### 첫 정책 (1.6.1, 3장 5-1)

2026-10-14에 사용자가 만들어 서명한 첫 정책(세대 1, seq 1, 서명 키 1)입니다. 모든 항목의 최소 버전이 1.6.1이고 유예가 없습니다(사용자 결정). 쓴 명령은 이렇습니다.

```sh
hjv-release policy --prev none --server rd.example.com --release-dir build/release-1.6.1 \
    --allow-input check_only --min all=1.6.1 --auto-after windows=none \
    --ios-valid 262871353 --latest ios=1.6.1 \
    --os-min windows=10 --os-min android=24 --os-min ios=13.0 \
    --contact "설치 파일은 관리자에게 받으세요." --out build/policy/draft-1.json
```

- `--allow-input check_only`: 빌드 저장소의 `build.yml`이 `check_only` 입력을 넘기는데, 도구가 아직 그 입력을 모릅니다(`docs/ci.md`의 "릴리스 기록"). 도구는 모르는 입력을 넘기는 `build.yml`을 거부하므로 이 옵션으로 허락합니다(아래 "출처 확인" 3번).
- `--latest ios=1.6.1`: TestFlight 빌드 262871353은 출시 실행(릴리스 디렉터리의 iOS 산출물은 빌드 262871309)이 아니라 같은 커밋의 iOS만 돌린 실행에서 왔습니다. 도구는 `--ios-valid`의 빌드 번호를 릴리스 디렉터리의 iOS 산출물과 맞춰 버전을 알아내므로, 다른 실행의 빌드면 버전을 `--latest ios=V`로 줍니다.
- 유예: 첫 정책의 항목은 유예를 물을 때만(`--grace-days`, `--grace-until`) 유예 쌍을 받습니다(아래 표의 e, `grace_min` 0.0.0). 이 정책은 묻지 않았으므로 서버에 넣는 즉시 1.6.1 미만을 막습니다. 정책을 받은 1.6.x PC는 1.6.1 미만의 컨트롤러(1.5.x와 1.6.0)를 바로 거절하고, 1.6.0 앱은 업데이트 화면으로 바뀝니다. 1.5.1 앱은 정책을 읽지 않습니다. Android 5.1~6.0 휴대폰은 1.6.1을 설치할 수 없습니다(minSdk 24. 정책의 `os_min`도 24).
- `--play-live`는 Google Play 내부 트랙에 그 버전이 출시(completed)된 뒤에만 줍니다. Play에는 아직 완료된 출시가 없어서 이 정책에는 `android_play` 항목이 없습니다. 나온 뒤의 정책에서 넣습니다(5-5). `android_play` 항목이 없는 동안에는 Play로 설치한 앱이 앱 안 안내 없이 PC에서 `android` 항목의 최소 버전으로, hbbs에서 `MIN`으로 거절됩니다. `policy`가 "바뀌는 것"에 그렇게 알립니다.
- `--auto-after windows=none`: 1.5.1 PC에는 업데이트 기능이 없어 1.6.1은 손으로 설치하므로, 이 정책에는 무인 설치 시각을 두지 않습니다. 다만 최소 버전 아래인 1.6.0 시험 설치본 PC(내 기기 목록에 있는 설치된 PC)는 1.6.1을 강제로 설치합니다. `none`은 강제 설치를 멈추지 않습니다(5-6). 무인 설치 시각을 처음 넣은 정책은 1.7.0의 seq 3입니다(`--auto-after windows=+2d`, 2026-10-17 22:13(KST)부터). 그때 계정에 묶인 1.6.1 PC는 운영자 PC 하나였고, 사용자 결정으로 그 PC를 [지금 업데이트]로 먼저 올렸으므로 무인 설치가 실제로 도는 것은 다음 버전부터입니다. 그때부터는 이 옵션을 주지 않으면 초안을 만든 때부터 2일 뒤에 고리별로 설치를 시작합니다(게시가 늦어지면 그만큼 짧아짐).
- seq 1의 `sign`이 보관소를 시작하고(`policy-e1-s1.json`) 1.6.1의 키 집합을 기록했습니다. 서버에 넣은 뒤(런북 8-2) 리허설(3장 5-14)을 합니다. 서버에 넣은 것은 2026-10-14 23:30쯤(KST)입니다.
- **따로 강제하는 정책은 없습니다.** 옛 계획의 둘째 정책(seq 2: 모든 항목의 최소 1.6.0, 유예 14일) 가운데 남은 것은 hbbs의 최소 컨트롤러 파일(4장, 런북 8-3)뿐입니다. 이 정책으로 만든 파일은 `MIN=1.6.1`, `FROM`=정책의 발행 시각이라, 넣는 즉시 서버를 거치는 1.5.x 컨트롤러를 모두 거절합니다. 넣을지와 때는 사용자가 따로 정합니다. 문 2(런북 8-4)도 따로 정합니다. 2026-10-14에는 사용자 결정으로 둘 다 했습니다: 문 2를 23:24(KST)에 열고(2026-11-30 0시까지), S1 문구의 hbbs 파일을 23:43에 넣었습니다. 런북 7-9의 관문과 사용자 안내 전입니다.

### 항목이 막는 것: `min`과 유예 쌍

항목은 시간에 따라 막는 것을 적습니다. `grace_until`과 `grace_min`은 함께 있거나 함께 없고, `grace_min`은 `min`보다 낮습니다.

- 유예 쌍이 있으면: `grace_until` 전에는 `grace_min` 미만을 막고(그 위는 유예), `grace_until`부터는 `min` 미만을 막습니다.
- 없으면: 늘 `min` 미만을 막습니다.

새 정책은 기기가 비교하는 정책보다 **어느 때에도 덜 막지 않을 때만** 받습니다(항목마다, Android 두 항목은 함께). 덜 막는 것은 루트 선언만 합니다. 그래서 도구가 쌍을 이렇게 정합니다(4-2의 a-f).

| 경우 | 도구가 쓰는 것 |
|---|---|
| a. 최소 버전 그대로 | 쌍도 그대로. `--grace-days 0`은 쌍을 없앰(남은 유예가 있으면 yes). 더 이른 `--grace-until`은 앞당김(yes). 늦추거나 새로 두면 완화(`--relax`, 쌍이 없던 항목에는 `--grace-min P=V`도) |
| b. 올림, 남은 유예 없음 | 기한 = 준 값 또는 한국 시각 0시 + 7일, `grace_min` = 지금 강제 중인 `min` |
| c. 올림, 앞선 올림의 유예가 남음 | 기본은 같은 기한과 그 `grace_min`. 더 이른 기한도 같은 `grace_min`. **더 늦은 기한이면 `grace_min` = 예고된 `min`(유예 중이던 버전이 바로 막힘, yes)** |
| d. 내림 | 완화(`--relax`). 쌍 없음 |
| e. 새 windows·ios 항목, Android 쌍의 첫 항목 | 준 유예 또는 7일, `grace_min` 0.0.0. 첫 정책에서는 유예를 줄 때만 |
| f. 형제(android/android_play)가 있는 새 Android 항목 | 형제와 같은 `min`이면 형제의 쌍을 그대로. 더 높으면 b·c처럼. 더 낮으면 완화 |

`--grace-min P=V`는 쌍이 있거나 생기는 항목의 `grace_min`을 직접 정합니다. 그 값이 덜 막게 하면 완화입니다.

### `policy`의 옵션

`P`는 `windows`, `android`, `android_play`, `ios` 중 하나입니다.

| 옵션 | 뜻 |
|---|---|
| `--prev FILE\|none` | 보관소의 마지막 파일(X11). 처음에만 `none`(이때 `--server` 필요) |
| `--archive DIR` | 보관소. 기본은 `~/hjviewer-policy-archive` |
| `--release-dir DIR` | 새 빌드의 산출물. Windows·Android의 `latest`는 여기 있는 패키지로만 오릅니다 |
| `--min P=x.y.z`, `--min all=x.y.z` | 최소 버전. 올릴 때 유예 옵션을 주지 않으면 기본 7일입니다 |
| `--grace-days [P=]N` | 오늘(한국 날짜)부터 N일 뒤 한국 시각 0시까지 유예. `0`은 유예 없이 바로 |
| `--grace-until [P=]T` | 유예 끝. `2026-11-23`(한국 시각 0시) 또는 `2026-11-22T15:00:00Z` |
| `--grace-min P=x.y.z` | 유예 동안에도 막을 버전(위 표). `--relax`로 유예가 없던 항목에 유예를 줄 때는 꼭 줍니다 |
| `--latest P=x.y.z` | `latest`를 이 값으로 고정. iOS·Play에서 버전을 직접 말할 때, 그리고 내릴 때(`--relax`) |
| `--hold P` | 이 항목은 그대로 둠 |
| `--auto-after windows=+2d\|T\|none` | 설치된 Windows PC의 무인 설치 시작. 새 Windows 버전을 낼 때 주지 않으면 초안을 만든 때(정책의 발행 시각)부터 2일 뒤입니다(`+2d`도 같음). 게시가 늦어지면 그만큼 짧아지므로, 늦어지면 `policy`로 초안을 다시 만듭니다. `none`은 무인 설치를 하지 않거나 멈춤(강제 설치는 멈추지 않음: `--withdraw-package`) |
| `--withdraw-package P` | P(windows, android)의 패키지를 거둬들임: 앱 안 내려받기, 무인 설치, 강제 설치가 멈춥니다. 완화가 아니어서 서명 키로 합니다. 더 높은 `latest`가 나올 때까지 패키지 없이 갑니다 |
| `--os-min P=V` | `latest`가 도는 가장 낮은 OS(ios `13.0`, android API 수준 `24`, windows `10`) |
| `--contact TEXT`, `--notes [P=]FILE` | 안내 문구와 알림 글. URL은 넣을 수 없습니다 |
| `--ios-valid BUILD` | 운영자가 TestFlight에서 확인한 빌드 번호(VALID, 내부 그룹에서 시험 중) |
| `--play-live VERSIONCODE` | 운영자가 Play 내부 트랙에서 출시(completed)를 확인한 versionCode |
| `--move-to-play`, `--no-move-to-play` | 사이드로드 Android 앱에 Play로 옮기기 안내 |
| `--relax`, `--drop P` | 덜 요구하는 정책: 새 루트 선언(새 세대)과 함께. `--drop`은 항목을 뺌(`--relax`를 뜻함) |
| `--revoke-key N` | 서명 키 N(1-100) 폐기: 새 루트 선언(새 세대). 루트 키 번호는 폐기하지 않습니다 |
| `--new-epoch` | 다른 변경 없이 새 루트 선언(기준 다시 잡기, 리허설) |
| `--live FILE` | 서버의 정책(`https://<서버>/api/hjv/version`에서 받은 파일). 위 넷에는 꼭 줍니다. `--prev`와 바이트까지 같고 보관소에 있어야 합니다(X10) |
| `--root-signs-policy` | 루트 키가 정책에도 서명. 기록된 모든 빌드가 박은 서명 키가 없을 때만(X9) |
| `--seq N` | seq를 직접 정함. 보통은 쓰지 않습니다. 이전 정책에서 1000 넘게 띄울 수 없습니다 |
| `--repo DIR`, `--build-repo`, `--public-repo`, `--allow-input NAME`, `--attest` | 출처 확인 설정 |

`--held`는 없어졌습니다. 완화가 늘 새 세대의 루트 선언이므로, 꺼져 있던 앱도 선언을 먼저 받고 그 기준과 비교합니다.

### 도구가 거부하는 것

고칠 수 없는 실수를 서명 전에 막습니다(`policy`, 서명 전 `sign`, `verify`).

| | 거부하는 것 | 빠져나갈 길 |
|---|---|---|
| X1 | 루트 선언 없이 이전 정책보다 덜 막는 정책: 항목을 뺌, latest를 내림, 최소 버전을 내림, 유예 끝을 늦추거나 새로 둠, 최소 버전을 올리면서 지금 막는 버전을 풀어 줌, 다른 Android 항목보다 덜 막는 새 항목 | `--relax --live`(루트 키, 새 세대) |
| X2 | 이전 선언과 보관소의 모든 세대보다 높지 않은 세대, 이전에 폐기한 키를 빼먹은 선언, 101-199를 폐기하는 선언, 1-100 밖의 `--revoke-key` | 없음: 루트 키는 폐기하지 않습니다 |
| X4 | `--prev`를 가진 앱이나 키 파일의 하한으로 새로 설치한 앱이 받지 않는 봉투, 자기 선언의 기준보다 덜 막는 정책 | 앱의 거절 코드와 이유 |
| X5 | 16 KiB가 넘는 봉투 | 알림 글을 줄임 |
| X6 | `floor --live`, `keys --production --policy`: 서버의 선언이 폐기한 서명 키를 키 파일이 박고 있음 | 그 키를 뺀 키 파일 |
| X7 | 패키지와 출처, 같은 버전의 다른 해시, `min > latest`, iOS·Play 확인, `os_min` 규칙, 문구의 URL과 제어 문자, 발행보다 이른 무인 설치, 이 PC 시계보다 300초 넘게 미래이거나 이전 정책보다 이른 발행 시각. 패키지 없는 windows·android 항목은 거둬들일 때(`--withdraw-package`)와 같은 latest로 패키지 없이 이어 갈 때만. 거둬들인 패키지를 같은 버전에 다시 붙이기 | 더 높은 버전 |
| X8 | (도구만) 이전 정책의 가장 낮은 `min`보다 낮은 새 항목: hbbs의 `MIN`이 내려감 | `--relax --live` |
| X9 | 쓸 수 있는 서명 키가 있는데 `--root-signs-policy` | 그 서명 키로 서명 |
| X10 | `--live` 없는 새 선언, `--prev`와 다른 `--live`, 보관소에 없는 `--prev`(다른 곳에서 서명됨: 도둑맞은 키이거나 옮기지 않은 의식 파일) | 서버의 파일을 받음. 보관소에 없으면 3장 5-8 2번 |
| X11 | 보관소가 같은 위치에 다른 정책을 가짐. 선언 없는 정책의 `--prev`가 보관소의 마지막 파일(무효가 아닌 가장 높은 위치)이 아님. seq가 그 세대에서 보관소가 가진 위치(무효 포함)보다 높지 않음 | 그 파일을 `--prev`로. 잘못 서명했고 나가지 않았으면 `void` |
| X12 | 기록된 키 집합 가운데 박지 않은 것이 있는 키로 서명(정책의 서명 키, 정책에 서명하는 루트 키, 새 선언의 루트 키). 기록되지 않은 키 집합의 키 파일로 `sign` | 다른 키. 서명 키가 없으면 `--root-signs-policy`. 관리자 보고에 그 빌드가 없으면 기록을 지움. 새 빌드의 키 파일이면 `floor --live`로 먼저 기록 |

그 밖에: 위치는 직전 + 1(보관소 기준), 새 선언은 그 위의 세대 seq 1입니다. 직전 정책은 서명과 형식을 다시 확인합니다. 정책에는 어떤 URL도 넣지 않습니다.

### 출처 확인

새 Windows·Android 패키지마다 `policy`가 확인합니다. 하나라도 틀리면 초안을 만들지 않습니다.

1. `release.json`의 실행이 빌드 저장소 `build.yml`의, 손으로 시작한, 성공한 실행인지(`gh api repos/<빌드 저장소>/actions/runs/<실행 번호>`). 업로드 같은 잡 하나가 실패해 실행이 성공하지 않았으면 빌드 저장소에서 그 실행을 'Re-run failed jobs'로 다시 돌리고, 성공으로 끝나면 같은 실행 번호로 진행합니다. 그래도 안 되면 같은 태그 커밋으로 새로 실행합니다. 이때 실패한 실행이 TestFlight나 Google Play에 빌드를 하나도 올리지 않았으면 버전을 그대로 두고, 하나라도 올라갔으면 `client/version.env`의 버전을 올려 새로 빌드합니다(`docs/ci.md` "릴리스 기록").
2. 그 실행이 부른 워크플로가 공개 저장소의 `client-build.yml` 하나이고, `release.json`의 소스 커밋(40자리)과 같은 커밋인지.
3. 그 실행 커밋의 `build.yml`이 문서(`docs/ci.md`)의 모양 그대로인지: job 하나, `uses:`와 `source_ref`가 같은 커밋으로 고정, 자기 단계 없음, 모르는 입력 없음.
4. 그 커밋이 이 저장소의 태그 `client-<버전>`과 같은지.
5. **릴리스 디렉터리의 패키지와 `release.json`이 바로 그 실행의 산출물인지.** 도구가 `gh run download <실행 번호>`로 그 실행의 산출물을 임시 디렉터리(0700, 끝나면 지움)에 직접 받아, SHA-256이 같은 파일이 둘 다 있는지 봅니다. 하나라도 없으면 초안을 만들지 않습니다.

- 5번이 없으면, `release.json`에 정상 실행의 번호만 적어 둔 다른 빌드의 파일도 1~4번을 통과합니다. 빌드 저장소에 쓸 수 있는 사람은 다른 실행으로 그런 디렉터리를 만들 수 있습니다. `release.json`도 그 실행이 쓴 파일 그대로여야 하므로, 거기 적힌 플랫폼·버전·빌드 번호도 검토한 빌드가 쓴 값입니다.
- 산출물은 7일 뒤 지워집니다(`docs/ci.md`). 지워진 뒤에는 그 빌드로 새 패키지의 정책을 만들 수 없습니다. 버전을 올려 다시 빌드합니다. 이미 정책에 들어간 패키지는 다시 확인하지 않으므로, `min`만 올리는 정책 같은 것은 언제든 만들 수 있습니다.
- `gh`가 로그인되어 있어야 합니다(Actions 읽기 권한).
- `--attest`를 주면 `gh attestation verify`도 통과해야 합니다. 서명자를 부른 워크플로(`client-build.yml`)와 검토한 커밋(`--signer-digest`)으로 고정합니다. 요금제가 비공개 저장소의 출처 증명을 지원하고 `gh`가 그 명령을 가진 버전일 때만 쓸 수 있습니다(Ubuntu 패키지의 gh 2.45에는 `gh attestation`이 없습니다). 실제 GitHub에서는 아직 시험하지 못했습니다.

CI가 산출물 디렉터리마다 넣는 `release.json`:

```json
{"platform":"windows","version":"1.6.1","build":"1.6.1.41","file":"HJViewer.exe",
 "size":25400320,"sha256":"<소문자 hex 64자>","source_sha":"<공개 저장소 커밋 40자리>",
 "run_id":"<빌드 저장소 실행 번호>","workflow":".github/workflows/build.yml"}
```

- `platform`은 `windows`, `android`, `ios`. `build`는 Windows 파일 버전, Android versionCode, iOS 빌드 번호입니다.
- `build`와 `run_id`는 문자열이나 숫자 모두 됩니다. 모르는 필드는 무시합니다.
- 같은 디렉터리에 `SHA256SUMS`가 있으면 그 줄도 파일과 같아야 합니다.

### 서명

```sh
hjv-release sign --key FILE [--key FILE] [--live FILE] --out FILE DRAFT
```

- 서명 전에 초안을 처음부터 다시 검사합니다. 초안에 적힌 설명은 믿지 않습니다. 새 선언의 `base`는 정책에서 다시 계산해 같아야 하고, 세대와 폐기 목록을 보관소와 이전 선언으로 확인합니다(X2). 새 선언은 `--live`가 초안의 이전 정책과 같고 보관소에 있어야 합니다(X10). 선언 없는 정책은 보관소의 마지막 파일 다음이어야 합니다(X11).
- 초안은 에이전트가 만든 파일이므로, 초안에서 온 글은 터미널을 움직일 수 없게 보여 줍니다. 초안의 확인 기록(notes)은 `policy`가 쓰는 모양(한 줄, 한글과 ASCII, 300자, 20줄까지)이 아니면 초안째 거부하고, 제어 문자는 어디서 왔든 `\u{1b}`처럼 글자로 바꿔 씁니다. 확인 기록은 "초안에 적힌 것"으로 따로 표시합니다.
- 아래는 목록으로 보여 주고 `yes`를 직접 입력해야 진행합니다.
  - **루트 키를 엶: "이 컴퓨터는 깨끗한 컴퓨터(3장 5-0)"**. 개발 PC에서는 루트 키를 열지 않습니다.
  - 서명 키 폐기, 새 세대(모든 앱이 이 기준을 앞으로 서명 키가 요구할 수 있는 바닥으로 받음: 항목별 기준, 완화하는 항목과 서버 확인의 `--relaxes` 줄), 루트 키가 서명하는 정책(어느 빌드 때문인지와 그 기기가 설치할 빌드), seq가 10 넘게 뛰는 것.
  - **서버에 넣는 즉시 일어나는 일**: 유예 없이 `min`을 올림, 유예 없는 새 항목(첫 정책 제외), 남은 유예를 없애거나 앞당김, 이미 지난 유예 끝, 이미 지났거나 지금 시작하는 무인 설치, 패키지 거둬들임.
  - 유예 중의 올림: "`<옛 min>` 이상 `<새 min>` 미만은 지금 유예와 같은 `<기한>`까지만", 또는 더 늦은 기한이면 "유예 중이던 `<grace_min>` 이상 `<옛 min>` 미만이 바로 막힘".
  - 기한을 늦추거나 새로 두는 완화: "지금부터 `<기한>`까지 `<grace_min>` 이상 `<min>` 미만을 막지 않음".
- 묻지 않고 알리는 것: 유예가 있는 항목마다 "지금은 `<grace_min>` 미만, `<기한>`부터는 `<min>` 미만을 막음", 키를 폐기하는 선언이면 정책의 모든 패키지(파일, 크기, SHA-256: 태그 노트와 대조).
- `policy`가 만들지 않는 초안은 무엇을 입력해도 서명하지 않습니다: 같은 버전인데 패키지가 다른 초안, 새 무인 설치 시작이 정책 발행 시각보다 이른 초안.
- 초안은 만든 때보다 늦게 서명합니다. 그래서 새 유예 끝과 새 무인 설치 시작이 **지금부터** 얼마나 남았는지 보여 줍니다.
- 필요한 키(서명 키, 루트 키, 또는 둘)를 먼저 알려 줍니다. `--key`로 준 파일 수가 다르면 비밀번호를 묻기 전에 멈춥니다. 정책은 서명 키로, 새 선언은 루트 키로 서명합니다. 둘 다 기록된 모든 키 집합이 박은 키여야 합니다(X12).
- 키 파일의 공개키가 `client/update-keys.env`의 같은 번호와 다르면 서명하지 않습니다. 보관소에 키 집합 기록이 있는데 이 키 파일의 키 집합이 기록되지 않았으면 서명하지 않습니다(새 빌드의 키 파일이면 `floor --live`가 먼저 기록).
- 비밀번호 입력 중에 Ctrl-C를 눌러도 터미널의 입력 표시는 원래대로 돌아옵니다. Ctrl-Z(멈춤)는 듣지 않습니다.
- 서명한 봉투는 앱의 규칙(직전 정책을 가진 앱과 새로 설치한 앱이 받는지, X4)과 이 도구의 규칙으로 다시 확인한 뒤에만 파일로 쓰고, 보관소에 넣습니다. 출력에 파일의 SHA-256이 나옵니다. 서버에 넣은 뒤 `curl -s https://<서버>/api/hjv/version | sha256sum`과 같아야 합니다.

## 3. 비상 절차와 운영 규칙 (런북)

신뢰 규칙의 운영 절차입니다. 규칙 자체는 참조 모델 `tests/vectors/model.py`와 시험 벡터가 정합니다(6장).

먼저 지킬 규칙:

- **서명 키로는 서버에 걸린 정책보다 덜 요구하지 않는 것만 냅니다. 덜 요구하는 것과 키 폐기는 루트 선언 한 번(새 세대)으로 하고, 그 뒤로는 다시 서명 키로 합니다.**
- **루트 키는 리허설을 포함해 언제나 깨끗한 컴퓨터(5-0)에서만 엽니다.** 루트 키 비밀번호를 개발 PC에서 치지 않습니다.
- `--prev`는 늘 보관소의 마지막 파일입니다. 보관소에는 `sign`, `floor --live`, `void`, `archive adopt`만 씁니다. `sign` 뒤에는 보관소를 서명 키의 오프라인 매체에 복사합니다.
- 선언은 서버에 걸린 파일이 내 파일일 때만, 그 파일로 만듭니다: `policy`와 `sign`에 `--live <https://<서버>/api/hjv/version에서 받은 파일>`을 줍니다. 이 파일은 `--prev`와 바이트까지 같고, 보관소에 있어야 합니다(X10).
- 모든 서명은 기록된 모든 키 집합이 박은 키로 합니다(X12). 키 집합 기록(`rm <보관소>/keyset-<…>.env`)은 관리자 보고에 그 빌드의 기기가 하나도 없을 때만 지웁니다. 그 뒤에 돌아온 그 빌드의 기기는 손으로 설치합니다.
- 허브-운영은 일부러 완화한 항목이 있을 때만 서버 확인에 `--relaxes <항목>`을 줍니다(`sign`이 출력). 그 밖에는 주지 않습니다.

| 상황 | 절차 | 서명 |
|---|---|---|
| 잘못된 릴리스가 무인 설치되고 있음 | 5-6 | 서명 키 |
| 너무 엄격한 정책을 냄 | 5-7 | 루트 선언(깨끗한 컴퓨터) + 서명 키 |
| 서명 키가 새어 나감 | 5-8 | 루트 선언(깨끗한 컴퓨터) + 도난당하지 않은 서명 키 |
| 업데이트 경로가 오래 멈춤 | 5-12 | 루트 선언 + 서명 키 |
| 서명했지만 내지 않은 파일 | 5-13 | 없음(`void`) 또는 루트 선언 |

### 5-0. 루트 키 의식 (5-7, 5-8, 5-10, 5-12, 5-13, 5-14에서 씀)

1. 깨끗한 컴퓨터: 개발 PC의 시스템, 소프트웨어, 에이전트가 하나도 돌지 않는 컴퓨터입니다. 예를 들어 이 일에만 쓰는 라이브 리눅스 USB로, 내장 디스크를 붙이지 않고 부팅합니다. 도구는 거기서 공개 저장소의 최신 릴리스 태그로 빌드합니다(`tools/hjv-release`에서 `cargo build --release --locked`). 개발 PC에서 만든 실행 파일은 쓰지 않습니다.
2. 가져갈 것: 루트 키 매체(101이나 102), 정책을 서명할 서명 키가 있으면 그 오프라인 사본, 서명 키 오프라인 매체에 있는 보관소 사본, 초안(개발 PC에서 `policy`로 만든 것, 또는 그 자리에서 보관소 사본으로 만든 것).
3. 그 컴퓨터에서 서버의 파일을 받고, `sign --archive <사본> --key <루트 키> [--key <서명 키>] --live <받은 파일> --out <파일> <초안>`을 실행합니다. `sign`은 보관소 사본과 서버의 파일로 다시 확인하고(X10, X11, X12), 기준 표와 완화 항목과 모든 패키지를 보여 주고, "깨끗한 컴퓨터"를 포함해 `yes`를 묻습니다. 시계도 확인합니다(발행 시각이 이 컴퓨터의 시계).
4. 서명한 파일과 `sign`이 출력한 보관소 파일을 키 매체와 개발 PC의 보관소에 복사하고, 평소대로 게시합니다.

### 5-1. 첫 정책, 5-2. hbbs의 첫 파일

- 5-1: 2장 "첫 정책 (1.6.1)"을 봅니다.
- 5-2: 따로 강제하는 정책은 없습니다(옛 계획의 "첫 강제"). 남은 것은 hbbs의 첫 파일이고, 넣을지와 때는 사용자가 정합니다. 서버에 파일이 없으므로 `hbbs-conf --policy <첫 정책> --current none`이 새 파일을 바로 씁니다(4장). 그 파일은 넣는 즉시 1.6.1 미만을 거절하므로 실제로는 배포 단계입니다. 보통은 런북 7-9의 관문과 날짜를 적은 사용자 안내 뒤에 넣습니다(런북 8-3). 2026-10-14 23:43(KST)에 사용자 결정으로 그 전에 넣었습니다. 그 뒤의 `hbbs-conf`에는 `--current none` 대신 서버에 넣은 그 파일의 사본(`~/hjviewer-secrets/door2/min-controller.conf`)을 줍니다.

### 5-3. 최소 버전 올리기 (유예 포함, 서명 키)

- `policy --prev P --min all=1.6.1 [--grace-days 7] [--ios-valid B] [--play-live C]` → `sign --key <서명 키>`.
- `grace_min`에는 지금 강제 중인 최소 버전이 들어갑니다. 기한까지 그 미만은 막히고, 그 위는 유예를 받습니다.
- hbbs: `hbbs-conf --current <서버 파일 사본>`을 돌리면, 올림 중에는 파일을 쓰지 않고 다시 돌릴 시각(새 기한)을 알려 줍니다. 그때 쓴 파일을 허브-운영이 설치합니다.
- 기한 전에 또 올리면 기본은 같은 기한입니다. 더 늦은 기한을 주면 예고된 최소 버전이 바로 강제되고, 도구가 유예를 잃는 버전을 알려 주며 `yes`를 받습니다.

### 5-4. 새 최신 버전 (서명 키)

`policy --prev P --release-dir build/release-<v> [--auto-after windows=+2d]` (2장).

### 5-5. 새 플랫폼 항목 (서명 키)

- `android_play`는 `android`와 같은 수준으로 넣습니다(`--min android_play=<android의 min> --play-live C`). 기한 쌍은 도구가 복사합니다. Play에 그 버전이 나온 뒤에만 넣습니다. 더 낮게 넣거나 기한을 늦추면 완화이므로 루트 선언이 필요합니다.
- `windows`·`ios` 새 항목은 자기 유예를 받습니다(`grace_min` 0.0.0).

### 5-6. 무인 설치 비상 멈춤 (서명 키)

```sh
hjv-release policy --prev <보관소의 마지막 파일> --auto-after windows=none --withdraw-package windows \
    --out build/policy/draft-stop.json
```

- `--auto-after windows=none`은 **고리별 무인 설치만** 멈춥니다. 최소 버전보다 낮은 PC는 `latest`를 **강제로 설치**합니다(유예 끝이나 정책 발행 시각 기준, 3-4). 최소 버전을 방금 올렸거나 유예가 남아 있으면 도구가 이것을 경고합니다.
- 나쁜 버전의 강제 설치까지 막으려면 `--withdraw-package windows`를 함께 줍니다. 패키지를 거둬들이면 앱 안 내려받기, 무인 설치, 강제 설치가 모두 멈춥니다(`MAY_INSTALL`이어도 설치할 패키지가 없음). 완화가 아니어서 서명 키로 합니다. Android는 `--withdraw-package android`(`--move-to-play`를 함께 주면 Play로 옮기기 안내도 켭니다).
- 내려받는 중이거나 600초 알림 중인 Windows PC도 설치 직전에 정책을 다시 읽어 멈춥니다(3-4).
- 그 항목은 더 높은 `latest`가 나올 때까지 패키지 없이 갑니다. **거둬들인 패키지는 같은 버전으로 되돌리지 않습니다**: 고친 빌드는 더 높은 버전으로 내고(`--release-dir`), 그때 패키지가 다시 붙습니다.
- 서명한 뒤에는 2장 5-6번처럼 확인하고 보냅니다. `publish-dir`는 거둬들인 항목에 "패키지를 거둬들인 항목입니다. 넣을 파일이 없습니다"라고 알리고, 그 패키지는 넣지 않습니다. `--release-dir`에는 다른 항목의 지금 릴리스 디렉터리를 줍니다.
- 최소 버전 자체가 잘못이면(너무 높음) 5-7입니다.

### 5-7. 잘못된 정책을 냈을 때

- 너무 엄격함(최소 버전이 너무 높음, 기한이 너무 이름, 실수로 예고한 올림): `policy --prev <잘못된 정책> --live <받은 파일> --relax <고친 옵션>`. 기한이 없던 항목에 기한을 줄 때는 `--grace-min P=<기다려 줄 가장 낮은 버전>`도 줍니다.
- 깨끗한 컴퓨터에서 루트 키와 서명 키로 서명합니다(5-0). `sign`이 출력한 완화 항목을 허브-운영에게 `--relaxes`로 넘깁니다.
- 꺼져 있던 기기를 포함해 모든 기기가 받습니다. 로그인을 거절하던 PC는 다음 거절 뒤 60초 안에, 늦어도 6.6시간 안에 다시 확인합니다.
- 너무 느슨하거나 문구가 틀림: 서명 키로 고친 다음 정책을 냅니다.

### 5-8. 서명 키 유출 (도둑이 무엇을 냈든 같은 절차)

1. 루트 키를 쓰는 단계는 모두 깨끗한 컴퓨터(5-0)에서 합니다. 도난당하지 않은 서명 키(보통 다음 키)의 오프라인 매체와, 키 매체에 있는 보관소 사본을 씁니다. 개발 PC에서 키가 샜을 수 있기 때문입니다.
2. 서버의 파일을 받습니다. 보관소에 없는 파일이면(`check --live`가 경고하고 `policy`가 거부: X10), 허브-운영이 먼저 보관소의 마지막 내 파일로 되돌립니다(확인 스크립트를 거치지 않는 단순 복사). 그리고 다시 받습니다.
3. `policy --prev <그 보관소 파일> --live <받은 파일> --revoke-key <도난 키> [--revoke-key <아직 폐기하지 않은 은퇴 키>] --out <초안>`: 선언(세대 +1, 키 폐기, 기준 = 그 정책의 요구 부분)과 같은 내용의 정책.
   - `policy`가 서명자를 알려 줍니다. 기록된 모든 빌드가 박은 서명 키가 있으면 그 키입니다.
   - 없으면 루트 키입니다(`--root-signs-policy`). 교체 중(5-9)에 두 빌드가 공유하는 키를 도난당했거나, 서명 키를 모두 잃은 경우입니다.
4. 깨끗한 컴퓨터에서 루트 키와 `policy`가 알려 준 서명 키(또는 루트 키만)로 `sign`합니다. 기준 표를 읽고, 폐기와 새 세대에 `yes`를 치고, 나열된 패키지 해시를 모두 태그 메모와 대조합니다.
5. 평소대로 게시합니다(`--relaxes` 없음). hbbs 파일은 `hbbs-conf`가 바꾸라고 할 때만 바꿉니다.
6. `policy`가 "기록된 모든 빌드가 박은 서명 키가 없음"이라고 하는 동안은, 이후 정책도 모두 깨끗한 컴퓨터에서 루트 키로 서명합니다(`--root-signs-policy`). `windows` 항목에는 최신 빌드와 `auto_install_after`를 둡니다(옛 빌드의 PC가 쓸 수 있는 키를 박은 빌드로 스스로 올라감). 옛 빌드의 Android·iOS 사용자에게는 업데이트하라고 알립니다. 관리자 보고에 옛 빌드가 보이지 않으면 그 키 집합 기록을 지웁니다. 그때부터 서명 키로 서명합니다.
7. 다음 빌드: `update-keys.env`에 남은 서명 키와 새 키(예: 키 2와 3)를 넣고, 하한은 `floor --live`로 정합니다. 폐기된 키가 남아 있으면 `floor`와 `keys --production`이 거부합니다(X6). 서버의 키 파일은 그 빌드의 태그 뒤에 바꿉니다.
8. 의식에서 생긴 보관소 파일을 개발 PC의 보관소로 복사합니다.

결과: 기기는 다음 확인 때 선언을 받아 도난 키를 믿지 않고, 기준으로 강제하고, 새 정책을 기준과 비교해 받습니다. 가짜 엄격 정책(min 99.0.0)을 받은 기기는 선언만 통과해도 기준으로 풀립니다. 가짜 완화 정책은 상태가 있는 기기가 모두 거부했고, 그것을 받은 새 설치본은 기준으로 올라옵니다.

### 5-9. 정해진 서명 키 교체 (루트 키 필요 없음, 이 순서로)

1. 쓰는 모든 빌드가 다음 키를 박고 있습니다(1.6.0은 1과 2). `sign`에 다음 키의 키 파일을 주어 그 키로 서명합니다. 모든 기록된 빌드가 그 키를 박고 있으면 X12가 허용합니다. 그 키로 정책을 하나 이상 게시하고, 은퇴한 키의 비밀키는 지웁니다.
2. 다음 빌드는 (지금 쓰는 키, 새 다음 키), 예를 들어 (2, 3)을 박습니다. 하한은 `floor --live`로 정하고, 이때 새 키 집합이 기록됩니다. 그 태그 뒤에 허브-운영이 서버의 키 파일을 바꿉니다.
3. (1, 2) 빌드와 (2, 3) 빌드를 함께 쓰는 동안 두 빌드가 함께 박은 키는 2뿐입니다. 키 2를 도난당하면 5-8대로 (1, 2) 빌드가 사라질 때까지 루트 키가 정책에 서명합니다.
4. 관리자 보고에 (1, 2) 빌드가 하나도 없으면 그 키 집합 기록을 지웁니다. 그 뒤에야 키 3으로 서명할 수 있습니다(X12).
5. 은퇴한 키는 다른 일로 다음 선언을 낼 때 함께 폐기합니다.

### 5-10. 루트 키

- 둘(101, 102)입니다. 비밀번호를 따로 두고, 각자 다른 오프라인 매체에 따로 보관하며, 깨끗한 컴퓨터(5-0)에서만 엽니다. 기록된 모든 빌드가 박고 있으면 어느 쪽으로도 선언에 서명할 수 있습니다.
- 하나를 잃거나 비밀번호를 잊으면: 다른 하나로 서명합니다. **루트 키 번호는 절대 폐기하지 않습니다**(X2: 그 키를 박은 빌드가 그 선언과 이후 모든 선언을 거부함). 다음 빌드는 (남은 키, 새 키), 예를 들어 (102, 103)을 박습니다. 서버의 선언이 잃은 키의 것이면, 먼저 남은 키로 새 세대를 냅니다(`policy --new-epoch --live`, 5-0): 그 전에는 `floor --live`가 새 키 파일로 서버의 파일을 확인하지 못해 거부합니다. 새 키로 선언하는 것은 옛 빌드의 키 집합 기록을 지운 뒤입니다(X12).
- 둘 다 잃으면: 옛 루트 키 하나와 새 키를 박은 빌드를 냅니다. 옛 빌드는 지금 선언 아래의 서명 키 정책은 계속 받지만 다음 선언은 RootKey로 거부하므로, 선언이 필요해지기 전에 새 빌드를 손으로 설치합니다.

### 5-11. 몇 달 꺼져 있던 기기

할 일이 없습니다. 켜지면 최신 봉투를 선언부터 받습니다. 손 설치는 꺼져 있는 동안 키 집합 기록이 지워진 빌드, 한 세대 안에서 정책 1000개 넘게 뒤처진 기기, TestFlight 90일이 지난 iOS 빌드, 루트 키를 둘 다 잃은 경우에만 필요합니다.

### 5-12. 업데이트 경로가 오래 멈췄을 때

깨끗한 컴퓨터에서 루트 선언으로 완화합니다(`--relax --live <받은 파일> --min all=<낮은 버전>`, 서버 확인은 `--relaxes`와 함께). 고친 뒤 서명 키로 다시 올립니다(유예는 두어도 되고 안 두어도 됨). 완화를 놓친 기기도 새 정책을 받습니다: 선언을 먼저 받고 그 기준과 비교하기 때문입니다.

### 5-13. 서명했지만 서버에 없는 파일

- 서버 확인이 입력 때문에 거부함(`--relaxes`가 빠지거나 틀림, `incoming/`에 패키지가 아직 없음, 서버 시계): 입력을 고쳐 같은 파일로 확인을 다시 돌립니다.
- 내지 않을 정책이고 내 컴퓨터 밖으로 나간 적이 없음: `void --live <받은 파일> <파일>`(`yes`를 물음). 다음 정책은 무효가 아닌 보관소의 마지막 파일에서, 더 높은 seq로 만듭니다. 누군가에게 갔을 수 있으면(서버에 보냄, 다른 곳에 복사함) void하지 않습니다: 그 파일에서 다음 정책을 만들거나(그만큼은 요구해야 함) 선언을 냅니다.
- 내지 않을 선언: 곧 그보다 높은 선언을 냅니다(`policy --new-epoch --live <받은 파일>`, 5-0). 선언은 void하지 않습니다.
- 서버 확인은 거부한 파일을 지우고, 보관소에는 남습니다. 보관소와 그 사본을 잃으면 안 됩니다. 잃었으면 `archive adopt <파일>`(내가 서명했다고 확실한 파일만, `yes`를 물음)과 `archive adopt --keys <태그의 update-keys.env> --version <버전> --server <서버>`(관리자 보고에 아직 보이는 버전마다)로 다시 만듭니다.

### 5-14. 리허설 (두 번, 첫 정책을 서버에 넣은 뒤 운영자 기기만 1.6.1일 때)

깨끗한 컴퓨터에서 `policy --prev <보관소의 마지막 파일> --live <받은 파일> --new-epoch` → 루트 키 101과 서명 키 1로 서명 → 게시(`--relaxes` 없음) → 운영자 기기 정보 화면에서 `policy_epoch 2`를 확인합니다. 같은 것을 루트 키 102로 한 번 더 합니다(세대 3). 비상 전에 루트 키마다 매체와 비밀번호, 깨끗한 컴퓨터, 의식 전체를 시험할 유일한 기회입니다.

### 5-15. 새 빌드의 하한

`floor --live <받은 서버 파일>`이 출력한 `HJV_POLICY_FLOOR` 줄을 씁니다(2장 1번). 서명만 하고 아직 걸리지 않은 정책의 위치는 쓰지 않습니다.

### 5-16. 주 1회 점검

5장을 봅니다. 보관소에 없는 서버의 파일이 서명 키 도난의 첫 신호입니다(5-8).

## 4. 서버 설정 값

### hbbs의 최소 컨트롤러 버전 (`/etc/hjviewer/min-controller.conf`)

hbbs는 플랫폼을 모르므로 기준이 하나입니다.

```sh
# 첫 파일(3장 5-2): 첫 정책으로, 서버에 파일이 없을 때. 문 2를 열지 않으면 --door2-out 대신 --text s2 --out <파일>
# --door2-out은 그 디렉터리의 door2.conf 코드로 S1을 씀. door2.conf가 없을 때 --door2-until을 주면 새 코드(새 문 2)
hjv-release hbbs-conf --policy ~/hjviewer-policy-archive/policy-e1-s1.json --current none \
    --door2-out ~/hjviewer-secrets/door2
```

- 첫 정책에는 유예가 없으므로 첫 파일은 `MIN=1.6.1`, `FROM`=정책의 발행 시각입니다. 도구가 "FROM(…)이 이미 지났습니다. 이 파일을 넣는 즉시 1.6.1 미만을 거절합니다"라고 알립니다. 넣을지와 때는 사용자가 따로 정합니다(런북 8-3).
- 그래서 `FROM`이 지난 파일을 넣는 것은 실제로는 배포 단계입니다. 보통은 런북 7-9의 관문과, 거절이 시작되는 날짜를 적은 사용자 안내 뒤에 넣습니다. S1 파일은 서버에 `door2.conf`가 먼저 있어야 합니다(런북 8-4의 열기를 먼저). 2026-10-14에는 사용자 결정으로 관문과 안내 전에 넣었습니다(23:43 KST, `FROM=2026-10-14T14:06:02Z`, 그날 23:24에 연 문 2의 S1).
- `MIN` = 정책의 모든 항목 `min` 중 가장 낮은 값.
- `FROM`은 `MIN`이 바뀔 때만 다시 정합니다. 새 `MIN`에 방금 이른 항목들의 유예 끝 중 가장 늦은 값입니다(유예가 없으면 정책 발행 시각).
- `--current`에는 지금 서버에 있는 파일의 사본을 줍니다(없으면 `none`: 새 파일을 바로 씀, 5-2). `MIN`이 그대로면 `hbbs 파일은 바꾸지 않음`이라고 답합니다.
- `FROM`은 뒤로 가지 않습니다: 새 파일의 `FROM`은 계산한 값과 지금 파일의 `FROM` 중 늦은 쪽입니다. 이미 알린 시각보다 일찍 거절하지 않습니다.
- **올림 중에는 기다립니다.** hbbs는 기준이 하나라(`FROM`부터 `MIN` 미만을 거절하고 그 전에는 아무도 거절하지 않음), 새 파일의 `FROM`이 지금 시각과 지금 파일의 `FROM`보다 늦으면 지금 넣는 순간 덜 거절하게 됩니다. 그때는 파일을 쓰지 않고 `hbbs 파일을 아직 바꾸지 않음: 지금 파일을 그대로 두세요. <FROM> 뒤에 hbbs-conf를 다시 실행하세요`라고 답합니다. 그 시각 뒤에 다시 돌려 나온 파일을 허브-운영이 설치합니다. 그래서 써 준 파일은 그때부터 언제나 지금 파일 이상을 거절합니다(INV-16). 늦게 설치하면 hbbs는 옛 기준에 머물 뿐(늦을 뿐 느슨하지 않음), 손으로 만든 파일을 일찍 설치하면 그 `FROM`까지 아무도 거절하지 않습니다.
- `MIN`이 지금 파일보다 **내려가면 항상 경고**합니다. hbbs가 지금 거절하는 버전을 다시 받게 되기 때문입니다. 완화하는 루트 선언이나, 더 낮은 `min`으로 들어온 새 항목에서 생깁니다.
- 지금 파일은 이 도구가 쓰는 꼴로만 읽습니다: `MIN=1.6.0`(앞의 0 없이), `FROM=2026-11-22T15:00:00Z`(UTC, `Z`). 손으로 `+09:00` 같은 다른 꼴로 고친 파일은 추측하지 않고 거부합니다. hbbs도 같은 꼴만 받습니다(서버 패치 0005: `FROM`은 이 꼴만, `=` 앞에 공백 없이). hbbs가 쓰지 않는 파일도 거부합니다: 마지막 줄바꿈이 없거나, `MIN` 줄이 없거나, `MIN`이 있는데 `FROM`이나 `TEXT` 줄이 없거나, `TEXT`가 아래 문구 규칙에 맞지 않는 파일입니다. hbbs는 그런 파일 대신 이전 규칙을 지키므로 파일만 보고는 지금 규칙을 알 수 없습니다. 서버 로그의 `min-controller` 줄로 지금 규칙을 확인하고 서버 파일을 고친 뒤 다시 실행합니다.
- 문구는 `--door2-out`이면 문 2 링크가 든 S1, 문 2를 열지 않았거나 닫은 뒤에는 `--text s2 --out FILE`입니다. `--door2-out`의 디렉터리에 `door2.conf`가 없으면 도구는 `--door2-until`을 요구하고, 그것을 주면 새 코드의 `door2.conf`(새 문 2)를 함께 씁니다. 그 `door2.conf`를 서버에 먼저 넣습니다(런북 8-4). `--text-file`로 직접 쓴 문구는 옛 앱이 지켜야 하는 규칙(`version not allowed` 포함, URL 뒤 공백, 첫 단어가 `_tip`으로 끝나지 않음 등)을 검사합니다. 첫 단어는 hbbs와 앱처럼 ASCII 공백으로 나눕니다.

### 문 2 (`/etc/hjviewer/door2.conf`)

```sh
# 문 2 열기(여는 때는 사용자가 정함, 런북 8-4): door2.conf만 만듦
hjv-release hbbs-conf --door2-out ~/hjviewer-secrets/door2 --door2-only --door2-until 2026-12-27
# 코드 바꾸기: --door2-rotate. 닫는 시각 바꾸기: --door2-until
```

- 디렉터리는 다른 사용자가 읽을 수 없어야 합니다(0700). 파일은 0600으로 씁니다.
- 기록: 운영 서버의 문 2는 2026-10-14 23:24(KST)에 열었습니다. `UNTIL=2026-11-29T15:00:00Z`(2026-11-30 0시 KST)입니다(런북 8-4).
- **코드는 두 파일에만 있습니다.** 도구는 코드를 화면에 쓰지 않습니다. 문서, 메모, 대화에 옮기지 않습니다.

### 빌드 하한

```sh
curl -s https://rd.example.com/api/hjv/version -o /tmp/live.json
hjv-release floor --live /tmp/live.json     # HJV_POLICY_FLOOR=1:8
```

다음 빌드를 내기 전에 `client/update-keys.env`의 줄을 이 값으로 바꿉니다. 그 빌드는 이보다 오래된 정책을 받지 않습니다.

- 서버에 걸린 파일이어야 하고, 보관소에 있는 파일이어야 합니다(내가 서명해서 낸 것). 보관소에 없는 서버의 파일은 하한이 되지 않습니다(도둑맞은 키의 파일일 수 있음).
- 그 파일이 새 키 파일로 확인되어야 합니다(정책의 서명 키와 루트 선언의 루트 키를 새 키 파일이 박음). 새 키 파일이 서버의 선언이 폐기한 서명 키를 박고 있으면 거부합니다(X6).
- 이 빌드의 키 집합을 보관소에 기록합니다(`client/version.env`의 버전과 함께). 이 기록이 있는 동안 모든 서명은 이 빌드가 박은 키로 합니다(X12).
- 서명만 하고 아직 서버에 없는 정책의 위치를 하한으로 쓰지 않습니다: 그 빌드를 새로 설치한 앱이 서버의 정책을 거부합니다.

## 5. 주 1회 점검

```sh
curl -s https://rd.example.com/api/hjv/version -o /tmp/live.json
hjv-release check --door2 ~/hjviewer-secrets/door2/door2.conf --live /tmp/live.json
```

`--policy`를 주지 않으면 보관소의 마지막 파일을 이 PC의 정책으로 봅니다. 경고가 있으면 종료 코드 3입니다.

- TestFlight 빌드가 올린 지 75일을 넘음(90일에 만료되면 모든 아이폰 앱이 실행되지 않음).
- 문 2의 `UNTIL`이 지났거나 7일 안에 닫힘.
- 서버가 내주는 정책이 이 PC의 정책과 다름(옛 정책, 더 새로운 정책, 같은 위치의 다른 내용).
- seq가 빌드 하한에서 1000에 가까워짐.
- **서버의 정책이 보관소에 없음**: 다른 곳에서 서명된 것입니다. 서명 키를 도둑맞았거나(3장 5-8), 깨끗한 컴퓨터에서 한 서명의 파일을 옮기지 않았습니다(5-0).
- 세대 2 이상인데 루트 선언이 붙어 있지 않음, 서버의 루트 선언이 보관소에 없거나 다름.
- 보관소에 서버의 위치보다 높은 파일이 있음(서명하고 내지 않음: 5-13).
- 키 파일의 하한이 서버의 위치보다 높음(그 키 파일로 만든 빌드는 서버의 정책을 받지 않음).
- 기록된 모든 빌드가 박은 서명 키가 없음(루트 키가 정책에 서명: 5-8 6번). 기록된 키 집합과 그것들이 모두 박은 키도 보여 줍니다.
- 남은 1.5.x PC는 이 도구가 볼 수 없습니다. 1.5.x PC는 계정에 묶이지 않아 서버의 `hjv-api admin report`에도 나오지 않습니다. 운영자 PC 목록으로 확인합니다.

## 6. 시험용 명령과 벡터

- `hjv-release test-keys`: 이 저장소에 비밀키가 공개된 시험 키 목록. `--env`는 시험 빌드용 `update-keys.env` 내용입니다. 실서버 빌드는 이 키를 믿으면 안 됩니다.
- `hjv-release test-sign --policy FILE [--root-decl FILE] [--key NAME] [--root-key NAME] [--out FILE]`: 손으로 쓴 정책 JSON(과 루트 선언)을 **시험 키로만** 서명합니다(E2E와 다른 묶음의 시험용). 터미널이 필요 없습니다. 실제 키를 받는 옵션은 없습니다. `--raw`는 규칙을 어긴 봉투를 일부러 만들 때 씁니다. 시험 키는 서명 키 1, 2, 루트 키 101, 102(시험 키 파일이 박음)와 어느 빌드도 박지 않는 3, 103입니다.
- `tests/vectors/`: 앱이 받아야 하는 봉투와 거부해야 하는 봉투 141건(`manifest.json`, 거절 코드와 그 뒤의 상태까지), `covers.json`. `generate.py`가 참조 모델(`model.py`, 신뢰 규칙을 실행할 수 있게 옮긴 것)로 만들고 확인합니다. 클라이언트 코어와 서버 확인 스크립트가 같은 파일을 읽습니다. 설명은 `tests/vectors/README.md`.
- `tests/gh/`: 출처 확인 시험에 쓰는 기록된 `gh` 출력.

## 7. 파일 형식

**봉투**(서버가 내주는 파일, 한 줄):

```json
{"v":1,"k":1,"p":"<정책 JSON 텍스트>","s":"<서명>","root":{"k":101,"p":"<루트 선언 텍스트>","s":"<서명>"}}
```

- 정책 서명은 `"hjv-version-v1"` + 0 바이트 + `p`의 바이트, 루트 선언 서명은 `"hjv-version-root-v1"` + 0 바이트 + `root.p`의 바이트에 대한 Ed25519 서명입니다(표준 base64, 64바이트, 88자).
- `root`는 그 세대의 루트 선언이고, 세대 2 이상의 모든 봉투에 그대로 붙습니다(세대 1에는 선언이 없음).
- 정책 텍스트: `v, epoch, seq, issued, server, contact_ko, platforms{windows, android, android_play, ios}`. 항목: `min, latest, grace_until, grace_min, os_min, notes_ko, source, package{file, size, sha256, build}, auto_install_after, move_to_play, version_code, testflight_build`. `grace_until`과 `grace_min`은 함께 있거나 함께 없고, `grace_min`은 `min`보다 낮습니다(`"0.0.0"` 가능).
- 루트 선언 텍스트: `v, server, epoch(2 이상), revoked(1-100, 오름차순, 누적), issued, base{windows, android, android_play, ios}`. base 항목은 `min, latest, grace_until, grace_min`이고, 그 세대 첫 정책의 요구 부분입니다. 도구가 서버의 정책에서 계산합니다.
- 필드와 규칙은 `src/policy.rs`, 앱이 받는 규칙은 `src/trust.rs`(참조 모델 `tests/vectors/model.py`와 같은 판정)에 있습니다. 시각은 앱이 0001-9999년을 읽고, 도구는 2000-2199년만 쓰고 서명합니다(도구의 규칙).

**키 파일**: age 형식(age-encryption.org/v1)의 비밀번호 암호화 파일입니다(scrypt 작업 계수 18). 이 도구가 없어도 `age -d`로 열 수 있습니다. 안에는 역할, 번호, 32바이트 seed, 공개키가 들어 있습니다.

**초안**: `policy`가 만들고 `sign`이 읽는 JSON입니다. 서명할 텍스트 그대로와 직전 봉투, `policy`가 확인한 것을 적은 줄(notes)이 들어 있고 서명은 없습니다. notes는 한 줄에 300자까지, 20줄까지이고 한글과 ASCII 글자만 씁니다(공백은 하나씩). `sign`은 그 밖의 초안을 읽지 않습니다.

**게시 디렉터리**: `publish-dir`는 링크를 따라 쓰지 않습니다. `--out` 안에 링크나 보통 파일이 아닌 것이 있으면 아무것도 쓰기 전에 멈춥니다.
